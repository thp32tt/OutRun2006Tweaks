## 1. DX9EX-DISPATCH-XYZRHW-001 — final draw owner bypasses the specialized XYZRHW path

**Status proposal:** READY for B_FIX  
**Priority proposal:** 10  
**Verification:** LEVEL0 source-flow/build first; visual result remains LEVEL1 HMD.

### Exact code-flow evidence

`src/vr/d3d9/stereo_renderer_r30.cpp` has a bounded specialized path for every D3D9 draw family:

- `DrawPrimitiveDestR30 -> R30TryXyzrhwPrimitiveVB`
- `DrawIndexedPrimitiveDestR30 -> R30TryXyzrhwIndexedPrimitiveVB`
- `DrawPrimitiveUPDestR30 -> R30TryXyzrhwPrimitiveUP`
- `DrawIndexedPrimitiveUPDestR30 -> R30TryXyzrhwIndexedPrimitiveUP`

Only after an XYZRHW helper returns `E_NOTIMPL` does R30 enter the ordinary screen-space/R29 fallback.

The specialized gate is narrow rather than broad WVP ownership: `R30PrepareXyzrhwState` requires no live vertex shader and `D3DFVF_XYZRHW`. `R30XyzrhwHasProjectedDepthSignature` then checks the vertex Z/RHW relation against the current base projection. `R30ConfigureXyzrhwWorldEffect` uses that evidence to distinguish CPU-projected smoke/skid/decal world effects from white rank/score-style HUD glyphs.

However the active final chain no longer enters those R30 draw wrappers:

- R31 draw entries contain no `R30TryXyzrhw*` call. Their generic fallback calls `R30Draw*R29Hook.stdcall(...)`, which is R30's trampoline back to R29.
- R32 wraps R31 but contains no XYZRHW pre-dispatch.
- R33 again contains no `R30TryXyzrhw*`. Its final fallback deliberately invokes `R30Draw*R29Hook.stdcall(...)` through `R32LowerFailClosed`.
- R34 wraps R33 only with raster/reset safety and therefore does not restore the missing XYZRHW routing.

The R33 install log accurately describes the resulting topology as `R33TryFastWorld/R33TryHud + direct R29 fallback`.

### Why this matters

This makes the code written specifically for two unresolved symptom classes unreachable from the active final draw owner:

1. fixed-function XYZRHW HUD/white glyphs such as rank/score-like overlays;
2. CPU-projected XYZRHW world effects such as smoke/skid/decal billboards.

A generic HUD WVP adjustment is not an equivalent substitute for pre-transformed XYZRHW vertices, because their screen-space position is already contained in the vertex data. This also explains why widening WVP classification is the wrong next move.

### Minimal implementation direction

Do **not** route the whole final owner recursively through the old R30 wrapper. Instead expose/reuse the four bounded `R30TryXyzrhw*` helpers at the R33 final draw entry, before generic `R33TryHud/R33TryFastWorld`. If the helper returns a handled HRESULT, return it exactly once; only `E_NOTIMPL` should continue into the current R33 dispatch.

Add a deterministic verifier that proves each final R33 draw family checks its matching XYZRHW helper before generic dispatch and that a handled result cannot fall through to a second draw.

## 3. DX9EX-SKYGLOW-001 — composite source is reversed

**Status proposal:** READY for B_FIX  
**Priority proposal:** 8  
**Verification:** LEVEL0 logic/build; final appearance LEVEL1 HMD.

In `R30ApplyStereoSkyGlow` the actual texture flow is:

1. bright extraction: `reduced -> temp`;
2. horizontal blur: `temp -> reduced`;
3. optional vertical blur: `reduced -> temp`.

Therefore:
- one-step must composite **reduced**;
- two-step must composite **temp** after the vertical pass.

Current code does the opposite: it initializes `compositeSource = temp`, then when two-step is enabled changes it to `reduced`. The nearby comment explicitly says the vertical pass should become the composite source, so source and intent contradict each other.

At `SkyGlowFactor=1`, effective two-step is disabled by design. The current code therefore composites the pre-blur bright-extraction texture and skips the horizontal-blur output.

Minimal fix: initialize the source to `reduced`; after a successful vertical pass set it to `temp`. Add a deterministic flow assertion/test around the one-step/two-step target-source sequence.
