### P0-B: 3D projected rank/rival anchor validity is **unscoped to producer instance or frame**
- **Confidence: source-proven stale-data possibility; actual producer timing unknown.**
- `src/hooks_uiscaling.cpp` ~103–105 defines persistent, non-thread-local `RankMarkerProjectedInfo{}` and `RivalMarkerProjectedInfo{}`. `Calc3D2D_dest` (~240–280) resets/recomputes them **only** for return addresses `0xBAEE7` (rank) and `0xBB6F5` (rival); there is no reset on arbitrary frame/vehicle/mode change.
- `RankMarker_sprani`, `RankMarker_putClipSprite`, and `RivalMarker_sprani` (~350–475) accept `.valid` alone to select `ProjectedWorldMarker2D` and attach the payload to newly queued nodes. If no fresh Calc3D2D update precedes an eligible producer call, a previous vehicle's/previous frame's view coordinates may be projected into the new draw; this is a **conditional stale-owner hazard** even though producer CALL addresses and node tags are statically correct.
- `src/hooks_framerate.cpp::SumoUISpriteReplay::capture/replay` (~205–290) retains `ProjectedMarkerInfo` with old nodes, and renders replays on zero-tick frames, making explicit frame/owner stamping more valuable. `Interp::AfterTicks` is called **after** replay update (~570–579), and interpolates vehicles and the camera (`src/interpolation.cpp` ~885–1020), so sprite-placement inputs may be from a different motion sample than the final drawn world. This mismatch can explain marker drift only after reproducing the actual producer order.
- **One diagnostic contract:** for each rank 1–5 / rival marker record producer CALL, vehicle identity, Calc3D2D sample sequence, node ID, render frame ID, interpolation alpha, pose sequence. Negative test missing/cross-vehicle sample must fail closed to safe world path; preserve proper multi-node siblings and prior proven all-node `TagAppendedNodes`. Do not casually clear all markers every frame (would discard legitimate delayed sprites).

- **Confidence: source-proof classifier ambiguity; device draw symptom conditional.**

### P1-B: R30 lazy shadow capture becomes **process-global** and lacks a total VB/IB memory budget
- **Confidence: exact control-flow, conditional pressure/performance impact.**
- `R30BufferShadowCaptureArmed` initially false (~197), flips true after first eligible XYZRHW VB or IB Draw (~3082/3191). `R30VertexBufferLockDest` and index equivalent (~449/494) copy **all subsequently intercepted write-lock byte ranges**, and `R30CreateVertexBufferDest/IndexBufferDest` (~582–614) installs hooks on generic game-created buffers, not only identified HUD FVF.
- Each buffer is accepted up to `R30MaxShadowBytes=16 MiB` (~153); `R30VertexShadows` and `R30IndexShadows` unordered maps (~190–192) have **no global byte cap** in this file. `R30FinishObservedLock` (~344–380) copies written ranges to separate CPU vectors. Thus after the first HUD buffer draw the claim that 'ordinary world buffers no longer pay per-Lock shadow memcpy cost' is not strictly true, and 32-bit address pressure / Lock/Unlock CPU cost can grow with number of buffers. This is **different from** the already-known first-draw shadow miss in the prior review.
- Contrast: `src/vr/d3d9/ex_device_upgrade_r14.cpp` independently caps texture CPU shadows at **384 MiB** (~73–75) and `src/hooks_textures.cpp` bounds VR DDS cache at **64 MiB**. These caps do not bound R30 VB/IB registry.
- Verify total live shadow bytes/high watermarks, per-source FVF classification, writes per Present, and 95th/99th percentile frame time. If proven, scope capture to identified XYZRHW candidates with a total budget or a bounded donor shadow; preserve dynamic DISCARD/NOOVERWRITE integrity.

## P0-A elaboration: ImGui active clip/scissor and vertex-buffer overhead

- The pinned DX9 ImGui code `ImGui_ImplDX9_RenderDrawData` (~193–260) allocates a **D3DUSAGE_DYNAMIC | D3DUSAGE_WRITEONLY** VB and IB, then locks both with `D3DLOCK_DISCARD` on every nonempty render; its `DrawIndexedPrimitive` (~298) applies a scissor rectangle per ImDrawCmd (~291). It subsequently restores fixed-function matrices and a D3DSBT_ALL state block (~306–311).
- The active R30 process-wide lazy buffer observer intercepts corresponding VB/IB Lock/Unlock once armed, even though R30 cannot execute the ImGui FVF XYZ path. This couples optional F11 on-screen drawing to **unnecessary CPU-shadow memcpy** and memory accounting. Prove actual cost with lock-byte and frame-time telemetry before claiming a measured FPS regression.
- Any F11 stereo implementation must transform/clip its scissor rects per eye or instead draw the complete ImGui UI into a dedicated texture and composite into a correctly located finite/recentered HUD surface. Simply changing the FVF eligibility condition and replaying the stock viewport/scissor can truncate the right eye. Preserve `SetTexture`, alpha blend, texture atlas lifetime, `D3DTS_WORLD/VIEW/PROJECTION`, full state block, R22 state tracker and R23 depth/target restoration. Prevent overlay from stealing a queued game sprite token.
- The current P0 verifier `tools/verify_vr_visual_composition_p0.py` checks the F11 RAII semantic wrapper but not pinned upstream ImGui FVF/XYZ/orthographic shape or actual R30 raster ownership. This explains how an exact-SHA Inspector PASS can coexist with this unhandled path.

## P0-B temporal witness and concurrency constraint

- **Source-admissible witness**: `Calc3D2D_dest` updates `RankMarkerProjectedInfo` for car A (valid=true); later producer for another car B calls `RankMarker_sprani` without a preceding exact `0xBAEE7` Calc3D2D return. The B draw is tagged `ProjectedWorldMarker2D` and copies **car A's** view-space point to B's node. There is no owner, producer invocation serial, car identity or frame-epoch equality gate. This is a testable *source-admitted* incorrect result, **not evidence that the real game produces this ordering**.
- `RankMarkerProjectedInfo` and `RivalMarkerProjectedInfo` are non-atomic global structs while `src/vr/game/render_semantics.hpp` explicitly locks the queue-node registry because producers and renderer may run on different threads. If this exact Calc3D2D writer and wrapper reader can execute concurrently, the bare struct has a possible data race. Need runtime thread-id trace of those exact hooks before classifying concurrency as an observed defect.
- `SumoUISpriteReplay` intentionally captures both projected payload and semantic scope, but the stored payload has no frame/vehicle identity; a consistency check must allow deliberate single-tick replays while refusing incorrect cross-vehicle reuse.
