# QuestCockpitV2 experimental original-player F0 render alias — 2026-11-02

Branch: `vr-quest-cockpit-v2` only. Stable `vr-d3d9ex-focus` and published v0.01 beta untouched.

## Original Quest vs original PC evidence
- Quest original ARM64 `PcSceneRenderer::render_frame`, ELF `0x10CBE9C` first computes body correction C from original player `matrix_B0` and `matrix_F0`, then stages F0 to 4x4 identity only during qualified cockpit rendering. Exact 16-float normal restoration `0x10CC78C..0x10CC7D0`, unwind restoration `0x10CC910..0x10CC968`. It requires native event `(flags & ~2) == 0x10`, cockpit enabled, valid provider and camera mode1. The original caller uses native render-frame scope; event flags are not the game's STATE_GAME enum or Present sequence.
- The authorized original PC `OR2006C2C.EXE` SHA256 `68ceb386829066f8455b9d027320af962584321f3e2e8a79c72841495a6134c3` has 1-argument cdecl `0x49F3E0` from exact original x86 bytes `56 8B 74 24 08 56 E8 45 C9 FC FF 68 F0 E7 82 00 56 E8 5A B2 FF FF 83 C4 0C 5E C3`. It forwards the original player EVWORK_CAR* to the original player model renderer `0x46BD30` and a second original callback, and returns in its own stack frame. The original stable V2 used a *read-only midhook* on entry for native frame correlation. Replacing it with an atomic original-signature-checked **inline wrapper** supplies an exact call scope for F0 without stealing an unknown global call context.
- The original Quest F0 scope is **larger than** this PC per-player callback, and the PC source's original game-frame->OpenXR pairing remains **UNVERIFIED**. This is strictly an experimental A/B approximation, not exact parity.

## Implemented behavior
- Changed the existing `QuestCockpitV2NativeFrameProbe` original player callback hook from mid to inline, preserving `NativeFrameTrace.OnPlayerCallback()` and original signature verification. The correct `SafetyHookInline.ccall<void>(EVWORK_CAR*)` keeps the original gameplay draw.
- New `ScopedOriginalPlayerF0` in `src/vr/game/quest_cockpit_v2_occupant.hpp` copies all 16 original F0 floats, stages exact `Identity` only inside the original synchronous player-car model call, and restores the original 64 bytes even on a thrown exception. Reentrant player callback scopes are rejected; no other-car, NPC, 2D, scene effect or HMD matrix writes.
- Gate requires `QuestCockpitV2Enabled && QuestCockpitV2F0RenderScope`, exact `EVWORK_CAR* == Game::pl_car()`, original game-frame probe active, native camera mode1 and currently valid XR stereo pose. It validates pre-staged original B0/F0 and computes the original `C` BEFORE F0 identity. It does not keep an across-frame fallback or alter MOZA R3 FFB, wheel, render pipeline, HUD, menu or original game assets.
- Default INI `QuestCockpitV2F0RenderScope=false`. The normal `RUN-QUEST-COCKPIT-V2.cmd` also keeps F0 OFF; use the **separate** `RUN-QUEST-COCKPIT-V2-F0.cmd` for the opt-in experiment with F0 ON. Existing original player event362 `W*C` correction is a different scoped draw path, and will run only if its own original work/event/frame/XR ownership predicates pass. Robot W*C reads original F0 after the player-car callback restores it.
- C++17 regression checks: owner predicates, changing invalid owner/scene/frame/mode, 64-byte F0 restoration after normal and exceptional exits, no staging when disabled, distinct original `W*C` model restoration tests.

## Important missing parity
- Quest original F0 identity covers the **entire native rendering frame**, whereas this PC experimental wrapper covers only one original player car draw callback. Additional native source/draw ownership and Quest3 runtime observation must prove whether this local staging suffices for the player vehicle PMT. Do not silently widen to physics tick, general camera, BeginScene, all car displays, or all game frames.
- Original Quest occupant conditional TLS has two work-token slots (362 and 363), while this V2 only accepts exact original driver event 362 and original PC 0x4879B0. The original near-seat forced-visible LOD0, glass queued descriptor ownership/opacity, driver/passenger boundaries and exact native game frame to XR pose correlation remain unresolved.
- Windows x86 game DLL + x64 OpenXR host build and headset runtime verification are separate; **RUNTIME_VALIDATION=UNTESTED** until user test. Reject promotion to public release before physical mode1 stable body/driver and FFB checks.
