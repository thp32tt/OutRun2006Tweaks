## 발견 A — Quest 추가 운전석 좌표 분기의 기본 비활성화

`race_camera_eye_look_485590`의 시점1 분기는 차량 번호별 36바이트 원본 카메라 항목을 선택한다. 입력 구조체 첫 바이트가 참이면 오프셋 +4/+8/+12의 세 좌표로 시점 시작점·목표점을 대체한다.

원본 `PcSceneRenderer::invoke`의 주소 `0x10C71F4`는 카메라 입력 객체 시작 위치 `sp+0x260`을 0으로 초기화한다. 해당 명령의 ELF 기계어 `0x390983FF`를 직접 검증했다. 별도로 REA로 분석한 `attach_pc_scene::$_7` 입력 콜백은 +0x50/+0x52/+0x54/+0x5C/+0x60/+0x64/+0x70/+0xA8/+0xB0/+0xC8/+0xD0/+0xD8/+0xE0 등의 필드를 처리하지만 첫 바이트를 설정하지 않는다.

**판정:** 일반적인 렌더러 입력 생성 경로에서는 추가 좌표 덮어쓰기 기능이 꺼진 상태로 시작한다. 다른 호출 경로까지 영구 비활성이라고 단정할 수는 없다. Windows에 새 보정을 무조건 적용하면 Quest 원본을 재현하지 못할 수 있다.

## 발견 B — 시점 좌표 함수의 ARM64 직접 호출 지점 5개

실행 가능한 ELF 세그먼트의 직접 BL 명령을 별도 검사했다. `race_camera_eye_look_485590@plt (0x12336A0)` 호출 위치:

- `0x10C69B0`: 카메라 재설정
- `0x11944E8`: 일반 레이스
- `0x1194ED8`, `0x1195188`: 데모 내 두 경로
- `0x1195C18`: 타임오버

가상 호출 BLR과 동적 변경 경로까지 포함한 전체 호출 집합은 아니다.

## 발견 C — OpenXR view_matrix의 정확한 행렬 의미

REA가 400바이트의 `view_matrix(XrPosef)`를 **경고 없이** 복원했다. 입력은 쿼터니언(x,y,z,w)+위치(px,py,pz)이며, 4×4 행렬의 회전 성분은 쿼터니언 회전, 이동 성분은 수학적으로 `-R^T * p`와 동등하다(정규화된 쿼터니언 가정). 512개 결정적 무작위 샘플의 독립 수학 비교에서 최대 오차 약 `5.33e-15`(double 정밀도)를 확인했다. 이는 실기 VR 검증이 아니라 수식 대조다.

`XrRig::locate`가 재중심화 기준 역자세와 양안 위치를 합성하는 구조도 일치한다. 게임 월드 좌표·차량별 운전석 앵커·HMD의 양안 좌표·탑승자 모델 보정은 각기 별도로 유지해야 한다.

## PCVR 적용 순서와 미해결 사항

1. 실제 시점 `camera[+0x34A]==1` 및 유효 차량 모델에만 원본 차종별 카메라 테이블을 적용.
2. 같은 게임 프레임의 차량/카메라/재중심화 세대를 고정해 양안이 공유. 게임 카메라를 매 드로우마다 변조하지 않음.
3. 추가 좌표 덮어쓰기는 원본 활성화 조건을 입증한 경우에만 허용.
4. 운전석 차체 행렬과 탑승자 보정은 별도 적용, 정상·예외 종료 양쪽에서 복구.
5. 남은 항목: 정확한 물리 스케일과 행렬 합성 순서, 차량별 유리 삼각형, 운전자 본/손·핸들 리그, Quest3 실기 비교.
