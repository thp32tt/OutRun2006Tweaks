## Scope and authority

This supplements `docs/KOREAN_LOCALIZATION_AUTOMATION_CONTRACT.md`, `docs/KOREAN_LOCALIZATION_QUALITY_PIPELINE.md`, `docs/KOREAN_LOCALIZATION_EVIDENCE_GATE.md`, and `localization/graphics/INGAME_REWORK_BACKLOG.csv`. Those remain authoritative for A/B/C/C3 roles, queue ownership, exact-byte approvals, and open user defects. Do not introduce another queue, approval SSOT, controller, platform-specific ROM workflow, or change the six-launch schedule.

**Claim boundary:** producer QA, persisted-DDS C/C3, a compiled Win32 Release patch, a generated ZIP, and a current-byte JPG are distinct evidence types. None alone proves the game loaded the corrected data, composited it correctly, or that a user-reported defect is closed. A failed actual-game screen outranks historical static PASS; retain `OPEN_USER_INGAME_FAIL` until the user retests the exact repaired candidate. Use `RUNTIME_VALIDATION=UNTESTED` when no real game run occurred.

## 1. Consumer-chain proof before claiming an in-game fix

For each materially changed DDS, font atlas, runtime string, or hook, identify the **first unproven link** in the applicable chain:

`canonical English source (revision+SHA) -> target queue/text ID -> translation/renderer -> persisted candidate bytes (SHA) -> preview/build manifest (commit+SHA) -> asset selection/lookup -> actual load/transform -> residency/cache/state transitions -> composed screen -> player interaction/observed acceptance`.

- A/B record evidence for source identity, editable regions, protected consumers, exact on-disk DDS format/alpha/MIPs and regenerated byte identity using the existing production QA. C independently validates persisted bytes and source/CLEAN/FINAL comparisons. These are **static** evidence only.
- For runtime-only or mixed screenshot failures (notably HUD, Stage 2, ranking and dynamic labels), first distinguish `GRAPHICS`, `RUNTIME_TEXT` and `MIXED` from load/draw evidence. Do not modify an arbitrary DDS to fix a runtime overlay, or assume a successful text DLL build repairs a baked texture.
- If an image/text resource is cached, preloaded, reused across scene transitions, or switched by UI state, verify the applicable load/selection and re-entry boundary. Seeing the resource in a screenshot does not establish *which* replacement was consumed. Do not interpret a missing log event as proof of no load until log coverage is established.
- When changing a glyph map, encoding or atlas, verify the full required corpus and active state repertoire. Unknown characters, missing glyphs or unsupported codes must not silently become blanks, Latin fallback or substitute characters. Fail the applicable product input verification and record the first unsatisfied consumer; do not claim an unimplemented fail-closed guard exists.
- Existing `txet` lossless round-trip evidence and DDS save/decode checks remain required; a reversible file format alone does not prove the UI consumer.

## 2. Shared-atlas and pixel-impact accounting

A texture or font atlas may feed multiple screens, selected/unselected variants, rank states or palettes. A single visually correct crop does **not** close every consumer.

- For a changed atlas, enumerate affected label cells, scene/UI variants, preserved brand/song/model pixels, and known shared consumers. Cross-reference existing `asset_queue.csv`, `INGAME_REWORK_BACKLOG.csv` and observed in-game state; record `UNRESOLVED_MAPPING` when an affected consumer cannot yet be tied to a stable source region.
- Plan a single owner for each final text/effect/plate pixel write against immutable native English source bytes. Keep protected masks and source-justified glyph/effect writes disjoint; if intentional overlap is necessary, define the one composed final output before writing. Any unexplained protected pixel, alpha/palette/BC block, border or background delta fails even if the bbox count is zero.
- Check whether non-text pixels from a shared texture supply color, selection-state graphics, UI panels or shadow/gradient layers. Preserve such consumers, not merely the visibly labeled cell. Never widen a mask to make a regression disappear.
- A clean English-source -> CLEAN -> FINAL image audit must remain independent of consumer/path mapping. If pixel correctness is evidenced but actual in-game selection is unknown, preserve static PASS/HOLD according to its own gate and mark the runtime link `UNTESTED`; do not rerender the same good DDS merely because game evidence is missing.

## 3. Minimum user-game review matrix

The next `USER_REVIEW_NOT_APPROVED` build should provide an **exact build/ZIP SHA and source commit** and a concise, reviewable route checklist (not a fictional test result). Use only actual evidence when completing it. The routes below are priority examples from the 2026-10-09 user screenshot review; expand or revise from the current backlog rather than treating this table as a new denominator.

| Route / consumer family | Scenes and state variation to inspect | Key failure evidence to collect |
|---|---|---|
| Title/main menu/chrome header | Options, Ranking, Single Player, Coast 2 Coast; default/selected and return | Cropping, native type hierarchy, italic sign, source text residue |
| Car select/showroom | Car selection, detail panels, mode switch, exit/re-entry | Low-res Korean, protected Ferrari/model marks, mismatched tiny text, panel/box seams |
| Goal/transmission selectors | Open, change selection, confirm, cancel, reopen | Both focused/unfocused glyphs, overlap, residual box/alpha effects |
| Driving HUD/Heart Attack | Actual race HUD, dynamic elapsed/time/heart values, updates | Font provider, composited foreground, transient glyph corruption, collision with icons |
| Stage/rank/OutRun Miles | Stage transition including Stage 2, changing rank and HUD overlay, before/after frames | Stack order, duplicate source+Korean, text/rank overlap, dynamic clipping |
| Name entry (only if Korean player-input scope is selected) | Input -> partial edit -> commit -> redisplay -> save -> reload | Missing glyph/provider, input-state mismatch, persistence or later-screen corruption |

For every **executed** route, bind the result to the exact build/ZIP SHA, source branch commit, game executable/region, applied assets, scene/state, user input sequence, before/during/after screenshots or recording, and reviewer verdict `PASS/FAIL/NOT_TESTED`. Save an **unmarked** screenshot in addition to any annotated markup so drawn review rectangles cannot be mistaken for texture defects. Preserve a reproducible checkpoint/next action for deferred paths where available. A static JPG comparison, user annotation or ZIP assembly cannot be recorded as game-route PASS.

- A route may cover multiple assets only when they demonstrably share the same selection/load/consumer path. A different renderer, state, dynamic overlay, cache transition or source mapping warrants a separate targeted route.
- Prioritize outstanding P0 actual-game failures, then P1; collect multiple non-blocking defects on the **same exact artifact** before rebuilding when remaining observations would still be interpretable. Rebuild immediately if the defect blocks progress or corrupts useful evidence.
- Report **coverage numerator/denominator by distinct route and state**, with `NOT_TESTED` and `MAPPING_UNRESOLVED` explicitly visible; no invented green status for unreached branches. Attach results to existing backlog notes/role evidence instead of introducing a parallel workflow.
- A successful launch, CI, or single screenshot never implies full-play completion. Report the exact reached endpoint and unresolved route/consumer gaps. User-only real-game closure remains subject to existing backlog rules.

## 4. Agent handoff checklist (mandatory when applicable)

**A/B producer:** preserve the current 10-stage CLEAN/composite/native-DDS gates; record changed atlas cell -> observed consumer candidates and safe write regions; reject missing glyph coverage or unexplained pixel changes. Do not fabricate runtime results.

**C/C3 QA:** independently review exact saved bytes and affected shared cells. In C findings distinguish `STATIC_VISUAL`, `CONSUMER_MAPPING`, and `REAL_GAME` evidence. A missing runtime link does not transform a proven visual FAIL into PASS or trigger automatic recreation of a current good file.

**Build/review handoff:** identify exact packed build and included DDS/text/hook SHAs, suppress open user-failed candidates as required by existing preview policies, and provide the route/state checklist above. `USER_REVIEW_NOT_APPROVED` must remain explicit until actual-game acceptance.

**Issue closure:** reproduce -> identify first bad link -> apply a source-verified correction -> recheck the exact route and related shared consumers -> obtain newer user in-game retest. Keep actual result, inferred root cause and still-untested paths separate. Only then close the corresponding `INGAME_REWORK_BACKLOG.csv` row.
