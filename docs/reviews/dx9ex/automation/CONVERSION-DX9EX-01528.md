## NEW_FINDING — source-grounded negative control, not a verified flare fix

- NEW_FINDING=HOST_NORMAL_GAMEPLAY_ONE_PROJECTION_LAYER_NEGATIVE_CONTROL_WITH_TEMPORAL_CACHE_REUSE; NEW_CONFIRMED_OPTICAL_DEFECT=NONE.
- Compiled host entrypoint is `vrhost/src/main_r23.cpp`, NOT the legacy `vrhost/src/main.cpp` (`vrhost/CMakeLists.txt:40-47`). R23 rejects an in-flight candidate; in classic SBS it correlates a stable complete ring frame with desktop capture Present time; in DirectGPU it selects the newest eligible run/slot and rejects in-flight frames. Selected source is re-read with same sequence, pid, frameId, pose, flags, eyes, transport identity BEFORE committing the host source. Thus a game `PublishRenderFrame(...inFlight)` marker does not on its own pass into a completed host eye pair.
- In normal gameplay the host stages either a **fresh** `XrCompositionLayerProjection` or a **cached** one via mutually exclusive branches and sets `end.layerCount = layerReady ? 1 : 0` with `layers[1]` before exactly one `xrEndFrame` call in its XR loop. `viewCount=2` means two intended **eye views inside one layer**, NOT two simultaneous projection layers. A repeated game `EndScene`, two physical R30 L/R draws, or two view slots does not establish same-eye duplicate blending.
- On intermediate XR ticks **without a newly committed producer frame**, R23 deliberately re-submits `cachedProjectionViews` instead of refreshing/blitting eyes. R23 publishes the verified source/pose bundle only after successful fresh projection render; `lastProcessedStereoFrame` advances there, not on speculative in-flight metadata. This is a *temporal* reuse of one previously released stereo source across separate `xrEndFrame` invocations; it is not an extra layer in the same frame. It might contribute to perceived stale motion under an actual mismatch, but no head-lock or duplicate pixels follow solely from this static mechanism.
- The compile-forced R32 `xrEndFrame` wrapper, when fast DirectGPU is validated, forwards the existing `endInfo` **once** to `OutRunVrFinalTest::EndFrame` and returns; otherwise it delegates to R26/R24. R24 fallback's reviewed replacement paths set `patched.layerCount=1` for one projection/quad, and the verified-original case passes the incoming layer. The inspected standard path shows no function that appends the in-flight and final source as **two** projection layers during one host XR tick.
- Precise limit: this rules down E2a ('R23 normally consumes pre+post Present states as two same-tick OpenXR projection layers'), not every possible host fallback, API-layer mutation, runtime reprojection artifact, source texture recycling, source flare duplication or optically wrong cached-eye image. R32 may reuse one valid producer slot for multiple XR ticks while an async ACK is pending; repeated `xrEndFrame` timestamps alone must not be counted as duplicate **same-eye raster**.
