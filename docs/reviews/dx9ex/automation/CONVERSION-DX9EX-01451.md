## Whole-path static simulation: producer → semantic/queue → native GPU → L/R → restore → Present/OpenXR

1. **Original producer / independently preserved disassembly.** Bounded Quest↔PC original mapping `docs/research/QUEST_CAMERA_GUEST_CORRESPONDENCE_20261016.md:4-15` associates the original PC `CalcCameraMatrix` with EXE RVA `0x84BD0` / VA `0x484BD0`; the native `race_camera_view_switch_484a40` can touch `+0x340/+0x344/+0x34A` camera controls. The native Quest `cockpit_body_correction` has distinct writer/reader sites, but the PC implementation is not proven bitwise equivalent. This is **archived analysis evidence**, not fresh binary execution.
2. **Game-side View matrix production can occur more than once.** `src/hooks_graphics.cpp::CalcCameraMatrix_dest:2065-2135` computes one `driverSeatFrame` eligibility result, temporarily replaces `cam_pos_F8/look_pos_104` using `ApplyDriverSeatCameraOffset`, calls the original `CalcCameraMatrix`, then restores the original camera **work position/look**. Only the generated game's View matrix retains the seat offset; restoring work fields is **not** restoration of the generated View. Separately `Clr_SceneEffect_dest:2139-2171` deliberately calls `CalcCameraMatrix_dest` inside a SceneEffect scope with the original short-near camera and calls it again after the scoped effect to rebuild the world/cockpit View. `driver_seat_render_pass.hpp:11-20,40-63` makes this scope separation intentional. The actual order of *physical world geometry GPU submissions* relative to the temporary View rebuild has not been traced.
3. **Producer-versus-queue negative control.** `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:19-42` establishes original Sprite queue `0x0042D710` type-0 D3DX Draw vs UP, and type-1 animation/mask paths, with D3DX End/Flush potentially deferring GPU submission. Those `SpriteNode` tokens and `src/vr/game/render_semantics.hpp::ConsumeForDraw:998-1027` are essential *negative* controls: they do not identify which camera View built a car/world shader WVP, nor does a queued +TIME/GOAL semantic imply a cockpit geometry owner. A camera producer serial would have to be associated with the **actual GPU world draw**, independently of Sprite queue node/epoch and D3DX batch lifetime.
4. **Raw shader WVP provenance and world eligibility.** `src/vr/d3d9/stereo_renderer_r7.inc::BuildEyeConstants:902-955` obtains `GetLastVerifiedWvp` (16 floats, verified generation, verified pose, shader identity/serial), checks the **shader epoch** and `verifiedPoseSequence == stereo.poseSequence`, compares the current device c64 WVP with the verified register values, reconstructs WorldView and computes independent L/R eye WVP/FOV. The verified generation is a renderer WVP-generation value; these checks do **not visibly compare a generation of the game's original `CalcCameraMatrix` View**. Fixed-function world path `:785-901` instead reads live `D3DTS_VIEW/PROJECTION`, checks finite matrices and HMD pose, and forms eye transforms. Neither branch, by itself, proves game-camera temporal continuity. `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::R30TryScreenSpaceFovDraw:5024-5100` explicitly requires screen semantic for HUD/overlay, so this observation must not be addressed by blindly widening HUD finite-plane routing to world meshes.
5. **Physical native draw and two-eye state transaction.** `stereo_renderer_r7.inc::PrepareDuplicatedDraw:1521-1530` rejects unavailable right-depth/stencil, MRT or unsafe occlusion conditions, latches host stereo, and classifies a physically reached world candidate. `ExecuteStereoDraw:1531-1556` then sets the left eye world WVP (or fixed function), performs original physical Draw, moves to right RT/depth/viewport and right WVP, repeats original Draw, restores original WVP/fixed transforms and RT/depth/viewport, and marks failures. `FrameStereoPoseSequence` is compared to `draw.poseSequence` for world draws; it is **a host-latched HMD pose sequence comparison, not a camera View producer counter**. If two different but valid game camera View/WVP generations are fed to different physically executed world draws under the same HMD pose sequence, this particular mismatch gate need not fire. Other existing renderer checks or actual game sequencing may still prevent the hypothesized occurrence.
6. **Published frame and actual XR projection.** `stereo_renderer_r7.inc::PresentDest:1625-1741` requires world stereo and duplicated draw, consistent pose metadata, absence of incomplete/right-eye failure, and valid composition/direct path and D3D9 Present before publishing. It does not compare successive native View matrices for positional continuity. `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` independently selects direct-L/R sources or splits captured SBS UV, executes two D3D11 `RenderTo` calls, releases the XR image, then submits `views[eye].pose/fov/imageRect`. Thus a reported stereo-pose-valid frame is not proof of a stable in-game camera origin; and perceived judder in HMD without corresponding native View/WVP discontinuity must be investigated in host capture/pacing and XR timing rather than forced onto cockpit math.
7. **Reset and later dispatch controls.** `stereo_renderer_r7.inc::ResetDest:1744+` disables published stereo, invalidates tracked states and releases eye resources before Reset/ResetEx. This is independent of an in-frame game-camera View rebuild. Deferred D3DX UI End/Flush, F11 external, R62 fixed-function HUD and StateBlock resync are separate owners. No B9200 post-CALL/+5 instrumentation, shader-global rebind, model source patch or forced Reset is proposed.
