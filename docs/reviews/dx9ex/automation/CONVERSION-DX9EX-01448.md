## REVIEW_SCOPE — source-pinned control-flow simulation

1. **Producer and negative controls.** Archived original-EXE REA evidence (`docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:1-39`, EXE SHA-256 `68ceb386829066f8455b9d027320af962584321f3e2e8a79c72841495a6134c3`) establishes 0x0042D710's separate type-0 D3DX Draw 0x0042A0A0, direct-UP 0x0042C0F0, type-1 animated 0x0042A3A0 and masked 0x0042A800 routes. A CPU D3DX Draw may defer physical GPU work until Flush/End; therefore neither producer tagging nor queue epoch alone establishes this review's physical indexed Draw. `src/vr/game/render_semantics.hpp:960-1027` binds the effective semantic at the D3D9 draw boundary; external ImGui/F11 must remain a separate producer.
2. **Physical DIP routing.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5555-5628` captures `ConsumeForDraw()`, invokes SkyGlow pre-HUD, tries external F11 first, then `R62TryFixedFunctionSpriteIndexed`, then XYZRHW and original R29/native fallback **only if the previous candidate returned `E_NOTIMPL`**. `R62TryFixedFunctionSpriteIndexed:5304-5368` admits game backbuffer, TRIANGLELIST, safe stereo, corroborated ProjectedWorldMarker/ScreenHud semantics, live null VS, and exact FVF 0x142; the result-HUD classification additionally permits bypassing a potentially stale cached VS *hint* but never an actually active VS. No widening to arbitrary fixed-function/alpha draws is warranted.
3. **Projection construction and physical L/R draw.** `R62TryFixedFunctionSpriteIndexed:5368-5460` requires live pose/viewport and independent eye projections; projected marker applies source anchor delta while exact ScreenHud requires a finite `hudWorldLockValid` projective plane. `drawEye` first calls `SetTransform(D3DTS_PROJECTION, eyeProjection[eye])` then the **original native** `DrawIndexedPrimitiveHook`; failures stay in `eyeHr[eye]`. `R30ExecuteXyzrhwStereo:3954-4071` runs left draw, then right RT/depth/viewport setup and right draw, and calls `RestoreRightPassState` for RT/depth/viewport. Its failure handling marks right/error or restore failure and arms the safe fallback, but otherwise it returns the **left** HRESULT, even when the right path failed. `src/vr/d3d9/stereo_renderer_r7.inc:1461-1462` confirms `NoteRestoreFailure` sets `FrameRightDrawFailed`, poisons the frame and increments `RestoreFailures`; `RestoreRightPassState` does NOT restore original fixed-function PROJECTION here (`originalConstants=nullptr`, `restoreWvp=false`).
4. **Separate post-execute projection restore and result-scope asymmetry.** Back in `R62TryFixedFunctionSpriteIndexed:5473-5521`, after `R30ExecuteXyzrhwStereo` returns, R62 **separately** calls `device->SetTransform(D3DTS_PROJECTION, &originalProjection)`. If it fails, `NoteRestoreFailure("R62 D3DXSprite fixed-function projection restore")` and `R30ArmSafeFallback()` veto the stereo frame. Nevertheless, the function increments its R62 fixed-function `hits` and (for exact result with telemetry) emits `VR R26 RESULT_HUD_EYES`, including `projectionRestored`, `left/right` HRESULT and `frameIncomplete`. The final return expression at line 5521 is `exactResult && !restored && SUCCEEDED(hr) ? E_FAIL : hr`. Thus **an identical successful-left / failed original-projection-restore event returns E_FAIL for exact result and successful left HRESULT for non-result R62 sprites**. Both mark frame incomplete/restore failure; neither return code can alone establish bilateral success.
5. **Bounded counterexample (static branch only).** Assume one accepted R62 non-result ScreenHud/marker DIP, finite per-eye projection, successful left and right native Draw, successful right RT/depth/viewport restore, then failed `SetTransform(originalProjection)`. This records R62 hit, `FrameRightDrawFailed=1` and `FrameStereoIncomplete=1`, but `DrawIndexedPrimitiveDestR30` returns the successful R62 HRESULT and never tries R29/native again. With otherwise same draw state marked exact result, R62 instead returns `E_FAIL`; still no `E_NOTIMPL` fallback. A successful HRESULT from caller **does not imply the game D3D9 projection state was restored**, and the exact-result E_FAIL branch is not proof that the original physical Draw failed. This is demonstrable source control flow, not an observed GPU error or headset artifact.
6. **Present, reset and OpenXR control.** `src/vr/d3d9/stereo_renderer_r7.inc::PresentDest:1625-1740` rejects newly active stereo if `FrameRightDrawFailed` or `FrameStereoIncomplete` is set; successful composition and D3D9 Present are additional gates. Direct-only may hold previous safe frame, not certify this draw. `ResetDest:1744` separately invalidates tracked render state, releases eye resources and publishes Disabled before native Reset/ResetEx and re-prime; this is a reset/device-loss control boundary, not recovery proof for an already failed in-frame `SetTransform`. `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` subsequently requires independent pair of host `RenderTo` successes, OpenXR swapchain release and per-eye pose/FOV/imageRect; the R62 `hits` or successful left HRESULT have no same-frame link to displayed Quest3 pixels.
7. **StateBlock distinction.** `src/vr/state/state_block_tracker.hpp:44-88` and `state_block_recovery.hpp:25-76` track deferred Apply/coverage resync; this is not the same transaction as R62's immediate original PROJECTION restore. A D3DX StateBlock may leave the cached shader identity stale (`R62TryFixedFunctionSpriteIndexed:5328-5341`), but does not by itself establish `SetTransform` failure. Require evidence of the exact call and state before attributing a runtime fault.
