For D3DX Begin/Draw, eligible homogeneous +TIME/GOAL batches can borrow the exact owner only at actual FlushDest/EndDest; foreign/mixed/unknown/live-queue batches remain fail-closed.
3. During game CreateTexture(D3DPOOL_MANAGED), R13 translation and R14 CreateTextureCompatDestR14 may register a direct-lockable DEFAULT|DYNAMIC GPU texture, a SYSTEMMEM-backed shadow, or a DirectOnly fallback. R14Track/R14TrackDirectOnly store `gpu` as an identity-only pointer (no GPU texture AddRef), `device` with one AddRef, and for shadow mode an owned `cpu` texture. Failed creation can release the newly created texture without installing a registered entry; it does not establish a later native draw.
4. On a registered texture's **original COM Release** returning zero, `TextureReleaseDestR14` calls `R14Erase(texture)` only if `R14InternalReleaseDepth==0`. Erase removes the registry map's R14EntryPtr under R14RegistryMutex, then increments `R14ShadowReleased`; it does not force-drain other R14EntryPtr copies and does not set `R14RegistryDevice=nullptr`. A `R14Find` that ran before erasure may still own a shared_ptr while operating under entry->mutex. Thus the registry's "released" counter and map size are **not by themselves proof** that the CPU/device COM references were destroyed at that exact instant.
5. `~R14ShadowEntry` eventually Releases its nonnull CPU texture and device AddRef, debits any unreleased shadow budget, under thread-local `R14InternalReleaseDepth`. CPU texture Release uses a shared hooked vtable but must not be confused with a GPU registry entry solely because the same hook runs. The normal `R14Erase` path's last local entry destruction occurs when its last shared_ptr exits; if a different callback holds `R14EntryPtr`, destruction can be later. No mutex protects against caller misuse of an already-finally-Released GPU raw identity: a final COM Release plus overlapping operation is **a scenario to disprove**, not a demonstrated use-after-free.
6. `R14RegistryDevice` is identity-only, and only `R14AbandonCompatDevice` clears it on a matching device with an empty map. Subsequent successful `R14AdoptCompatDevice` can switch the identity, subject to core `InstallManagedResourceCompat` veto for different simultaneously-live CompatDevice. An empty map after final Texture Release does not, by itself, prove the device pointer or its hook targets are still live (or dead); `R14RegistryDevice` equality must not be treated as a COM ownership claim.
7. If valid textures survive into GPU execution, R30 physical indexed draw orders F11 external ImGui, R62 fixed-function sprite candidate, XYZRHW, R29/original fallback, with only actual native HRESULT establishing dispatch. R13 policy/occlusion and R9 mono-shadow/R7 L/R device hook ownership must be established independently; any stale texture identity would be tested at a real draw/SetTexture/GetSurfaceLevel/UpdateSurface, not inferred from CPU registry accounting. No B9200 +5 hook.

R9 Present requires real frame eligibility, duplicated world draw and valid pose; it can compose SBS/direct transport or publish mono fallback after physical Present HRESULT. ## NEW_FINDING — confirmed ordering, not a demonstrated bug

- NEW_FINDING=CONFIRMED_STATIC_R14_FINAL_TEXTURE_RELEASE_MAP_ERASE_AND_RELEASE_COUNTER_PRECEDE_LAST_SHARED_ENTRY_COM_DESTRUCTION; EMPTY_REGISTRY_DOES_NOT_CLEAR_REGISTRY_DEVICE_IDENTITY.
- SOURCE FACT: The GPU texture is **not** AddRef-held by the shadow registry; final observed external Release==0 triggers map erase (unless internal-release-depth guard). R14Erase's released statistic counts **registry removal**, whereas entry destruction and device/CPU Releases occur on last shared_ptr destruction; a still-active R14Find holder may delay this. A vacated map need not null `R14RegistryDevice`.
- HYPOTHESIS (not proved): A teardown metric or device-generation transition that assumes `R14ShadowReleased` means all COM shadow/device refs are already gone may misattribute lifetime, GPU pacing/resource churn or registry generation. A reentrant/same-thread nested GPU texture final Release during internal CPU Release would be suppressed by the thread-local guard, but **such a nested callback is unobserved and is not proof of a leaked map**. A concurrent caller accessing a raw GPU texture after its final COM Release would already violate normal ownership expectations; no source-only UAF assertion is warranted.
- REFUTATION / CONTRARY: Real engine texture final Release may never overlap any R14Find scope; CPU-backed shadows may retire before final texture release; the last shared_ptr may destruct immediately after counter increment; normal generation adoption reassigns stale identity; an old device can remain valid through an independent game COM reference. Instrumented traces showing matching counter/map/last-entry destructor within the same transition, no invalid GPU use, no stale hook mismatch and stable L/R/host frames would refute the practical-risk hypothesis.
