The latter can update native camera orientation/mode during an active race; that observation does not by itself prove a specific oscillatory frame sequence. Cockpit source is game camera + player-car `matrix_B0`, **not** a +TIME/GOAL/ESC SpriteNode producer.
2. **Config/eligibility mismatch, before semantic ownership.** `src/vr/settings.cpp:146-159` defaults `VRDriverSeatView=true`, `VRDriverSeatCarSpaceBasis=false` and exposes `VRDriverSeatNativeMode=1`. The operational owner in `src/hooks_graphics.cpp::VRDriverSeatCameraEligible:254-275` only requires active world/cockpit pass, a camera/player, `enabled && gameplayActive`, and a computable seat pose. It explicitly **does not veto** native camera mode/timer/switch changes. Neither this eligibility function nor `VRDriverSeatCameraPose:169-238` reads the published `VRDriverSeatNativeMode` setting. Thus configuration describes a synchronized native mode, but the actual cockpit gate does not restrict its incoming native mode.
3. **Pose dependency contrary to persistent-space intent.** `VRDriverSeatCameraPose:178-219` reads `camera->cam_pos_F8` and `look_pos_104` on every calculation. Because `DriverSeatCarSpaceBasis=false` by default, `driver_seat_car_space.hpp::ComputeStableSeatPose:177-198` goes straight to `ComputeTranslatedCamera` in `driver_seat_camera_math.hpp:18-83`, where the forward/right/up offset is a **translation of the current native camera**. Enabling the optional car-space path still uses that native eye/look as its absolute anchor (`ComputeCarSpaceTranslatedCamera:89-166`); it changes the offset's axes, not the anchor. Therefore two different native camera modes with different eye/look positions produce two different synthetic 'seat' views while the driver-seat gate can remain true. This **mode-to-pose dependency is source-confirmed**, not a confirmed live jitter reproduction.
4. **Latch and reentrant conditions.** `VRDriverSeatCameraPose:198-237` retains the last valid pair only after a **failed** new pose; any newly valid but discontinuous native eye/look overwrites it immediately. It only clears that cache when the player pointer changes or gameplay becomes inactive. Thus it cannot smooth two *finite, valid* but alternating native camera poses. `FixZBufferPrecision::CalcCameraMatrix_dest:2065-2135` determines `driverSeatFrame`, assigns a computed pose temporarily, invokes the original `CalcCameraMatrix.call`, then restores original camera work fields; this blocks feedback into the next simulation tick but does **not** guarantee generated game View-matrix continuity across distinct native camera modes. The second `VRDriverSeatCameraPose` call is before the original matrix calculation; do not infer that the hook always double-applies a seat offset.
5. **Geometry semantic, deferred queue negative control and physical draw.** `src/hooks_graphics.cpp:278-319` gates full player-car render state 1; `:390-425` restricts visual model scaling to the player's temporary draw matrix; `:342-364` restricts native driver suppression. These are *game model/world geometry* producers downstream of the camera matrix, not ordinary queued 2D UI. Original sprite REA `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md` separately identifies 0x0042D710 queue type-0 D3DX Draw/UP and type-1 native sprite/mask paths. Their source tokens, queue epoch and deferred D3DX End/Flush are **negative controls**: a later queued HUD Draw's semantic token cannot prove which camera generated a world/car shader WVP. `render_semantics.hpp::ConsumeForDraw:998-1027` supplies the effective draw semantic at the physical D3D9 call. Trace native game world draw + shader WVP/pose identity through R26 owner (`src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp`), then distinguish R30 XYZ/R62 HUD and R29/original fallback; do not classify the car as exact R62 ScreenHud or force a generic D3DX route. No exact cockpit physical draw fingerprint was collected on this task.
6. **L/R transaction, restoration and publication.** `stereo_renderer_r30_r26_safe.cpp::R30ExecuteXyzrhwStereo:3950-4060` provides a concrete *eligible draw* L→right RT/depth/viewport→right draw→restore boundary, but its XYZRHW helper is **not proof the cockpit mesh used that helper**. It can mark duplicated/world stereo on authoritative world-effect evidence; right/restore failures separately poison the frame. The selected world mesh's actual draw owner, eye WVP, RT, right-eye HRESULT, original View/restoration and whether a canted-eye pose was latched must be sampled, not inferred from camera gate or R30 counters. `stereo_renderer_r7.inc::PresentDest:1625-1741` then requires world-stereo+duplicated draws, pose metadata, absence of right/incomplete failures and composition/direct transport/Present before publishing the stereo frame; it does **not** test whether two consecutive native camera base poses were spatially continuous. `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` independently requires both host-eye `RenderTo` calls and defines per-eye pose/FOV/rects; subsequent `xrEndFrame` at `:3570` is another gate. A valid two-eye submit is not evidence of correct cockpit origin.
7. **SceneEffect and Reset isolation.** `src/vr/game/driver_seat_render_pass.hpp:11-20,40-63` suppresses seat use within SceneEffect and restores the world camera afterward; `src/hooks_graphics.cpp::Clr_SceneEffect_dest:2139-2171` explicitly calls camera reconstruction within and after the scoped effect. Repeated near-plane/View rebuilding is a separate hypothesis that requires identifying which physical draws ran between the two calls. `stereo_renderer_r7.inc::ResetDest:1744+` device loss/state reset is yet another boundary; it is not proof of a mode-induced cockpit oscillation.
