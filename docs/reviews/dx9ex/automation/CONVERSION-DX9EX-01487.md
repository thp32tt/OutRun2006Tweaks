## REVIEW_SCOPE — original producer through actual presentation boundaries (static)

- Original TITLE/MENU/+TIME/result producer -> 0x00449050 scheduler / 0x0042D710 SpriteNode consumer -> semantic producer and queue-node/epoch -> type-0 D3DX 0x0042A0A0 (possible deferred Begin/Flush/End), type-0 direct UP 0x0042C0F0, type-1 animated quad 0x0042A3A0 or type-1 masked/composite 0x0042A800 -> D3D9 physical Draw/DrawIndexed/UP -> R30/R62 FVF142 or XYZRHW two-eye eligibility -> R7 L/R target/depth/viewport restore -> original game D3D9 Present / stereo Frame.v2. This describes possible source ancestry, NOT a newly observed physical +TIME/masked GPU draw.
- Actual TITLE/MENU headset image takes an independent HOST route: captured **mono game/client pixels** from Desktop Duplication -> GetGameUv / 4:3-title versus wide-selector geometry -> per-tick xrLocateViews result -> intersect finite binocular FOV -> fixed LOCAL menu anchor -> D3D11 RenderMenuPlaneTo eye 0, CopySubresourceRegion to eye 1 (or fallback second draw) -> release projection image -> cache two XrCompositionLayerProjectionView -> R24 xrEndFrame submission. Unlike GAME, this path cannot prove physical native stereo +TIME/result/rank/lens. 
- QUESTION: after a prior valid menu anchor, when xrLocateViews returns two views and finite overlapping FOV but its orientation/position-valid bits are absent during transient tracking loss, may a new mono MENU projection overwrite the last-good cached MENU image and be submitted as if the current view publication had established validity?

## EVIDENCE — exact pinned GitHub line ranges and distinctions

1. Original executable REA archive `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:19-43` lists 0x42D710 four physical branches with unresolved indirect edges; `src/hooks_uiscaling.cpp:3740-3868` distinguishes queued node/epoch from deferred D3DX ownership, including fail-closed Flush. `src/vr/d3d9/stereo_renderer_r30.cpp:6873-7051` limits exact R62 FVF142 stereo to corroborated rank/HUD/pause owners, checks live shader/FVF, and restores original projection. `src/vr/d3d9/stereo_renderer_r7.inc:1524-1560,1693-1741` covers original physical stereo Draw/restore and original Present/publication. These do **not** verify present HMD pixels.
2. `vrhost/src/main_r23.cpp:2823-2862`: each XR tick performs xrLocateSpace and xrLocateViews; view count `vc` and `vs.viewStateFlags` are separate. The host passes the raw views and flags to `shared.Write`. For GAME-oriented `viewHistory.Store`, it **explicitly requires** `vc >= 2` and both `XR_VIEW_STATE_ORIENTATION_VALID_BIT | XR_VIEW_STATE_POSITION_VALID_BIT`. This proves a validity predicate exists but applies to another consumer.
3. `vrhost/src/main_r23.cpp:2840-2852,2698-2714`: the LOCAL menu anchor is captured from `head.pose` only when both head location validity bits are present, setting `menuProjectionAnchorValid=true`. The stored anchor is not automatically retired solely because a later xrLocateViews sample lacks its own validity flags. Correct initial-anchor protection is a negative control.
4. `vrhost/src/main_r23.cpp:2955-2958` gates subsequent composition by `fs.shouldRender == XR_TRUE && vc >= 2`, **not** `vs.viewStateFlags`. Therefore false shouldRender and fewer than two views are already correctly excluded; this finding must not be described as an unconditional no-tracking submit.
5. `vrhost/src/main_r23.cpp:3549-3592` permits a new MENU render on `capture.available && menuProjectionAnchorValid && (!cachedMenuProjectionValid || capture.fresh)` after the outer shouldRender/count guard. Neither this predicate nor the call of `R23RenderWorldLockedMenuProjection(compositor, views, ...)` checks `vs.viewStateFlags`. A successful render overwrites `cachedMenuProjectionViews`, sets validity, and makes the result eligible for the final layer.
6. `vrhost/src/main_r23.cpp:1540-1571`, `vrhost/src/runtime/menu_content_aspect.hpp:103-157`: menu code validates mathematical finiteness/range/overlap of both view **FOVs**, not the XR view-state **pose-validity flags**. These are independent kinds of evidence. FOV overlap rejection is a real guard, but cannot logically prove that `XR_VIEW_STATE_..._VALID_BIT` was present.
7. `vrhost/src/main_r23.cpp:1794-1862`: after eye-0 D3D11 draw and eye-1 copy/draw, the released image's two projection views use a saved LOCAL anchor and shared common FOV, not `views[eye].pose`. This limits potential impact: a fixed LOCAL 2D layer might be perfectly valid during tracking loss even if live head pose flags are absent.
8. `vrhost/src/main_r23.cpp:3596-3625`: prepared layer is submitted to xrEndFrame and compared to runtime hook counters. Historical open Issue #119 tracks MENU 4:3, HUD/F11/ESC visual concerns but **does not** supply new evidence of tracking loss or this condition. No XR invalid-view trace, compositor image or real headset observation was collected.
