Four confirmed original GPU exits differ: type0 D3DX `0x42A0A0`, type0 direct UP `0x42C0F0`, type1 quad `0x42A3A0`, type1 mask/composite `0x42A800`. Its 36 indirect CALLs remain unresolved. None establishes that an actual +TIME/GOAL/rank/particle texture has this R14 shadow/write overlap.
2. **Creation and resource eligibility:** `CreateManagedTextureCompat` may translate a legacy MANAGED 2D texture via a dynamic DEFAULT GPU resource or non-dynamic fallback. R14 tracks dynamic GPU textures as DirectOnly; the SYSTEMMEM CPU Shadow is a conditional, successfully registered non-dynamic 2D fallback. `R14ShadowEntry` records texture-wide `lockedMask`, per-mip `validMask/dirtyMask/readOnlyMask`, `retirePending`, and texture-wide `externalWriteDuringLock`. An unregistered or DirectOnly object cannot be assumed to pass through this state machine.
3. **CPU Lock then external GPU write:** `TextureLockRectR14` locks the CPU peer, sets the mip's `lockedMask` bit and `readOnlyMask` or `dirtyMask`. External UpdateSurface/UpdateTexture/StretchRect/ColorFill callback first executes native API; only a successful result with matching destination 2D texture identity and zero `R14InternalUploadDepth` calls `R14MarkExternalGpuWrite`. Successful writable borrowed level-surface LockRect/GetDC also marks the parent 2D texture (with surface-hook coverage); a failed native operation and internal R14/R15 UpdateSurface do not count as external writes.
4. **Conflict bookkeeping is texture-wide, not restricted to the written mip:** `R14MarkExternalGpuWrite` locks the entry mutex, clears *all* `validMask`, sets `retirePending`, and, if `lockedMask != 0`, latches `externalWriteDuringLock=true`. It does not detach a CPU peer with outstanding locks. If no outstanding lock exists, it detaches immediately to DirectOnly. This is conservative across mips and not evidence of wrong texel content.
5. **R14/R15 Unlock ordering:** On a tracked locked mip, both implementations call CPU `UnlockRect` and clear its lock and read-only bits. CPU Unlock failure already invalidates/retires. Otherwise `externalWriteDuringLock` is examined **before** the writable `R14UploadLevel`/`R15UploadLevel` branch; if set, that Unlock returns `D3DERR_INVALIDCALL` without uploading CPU pixels, even when that particular Lock was read-only or on a different mip. When another mip is still locked, retirement is deferred; on the final locked-bit drain it detaches the CPU peer and clears masks/flags. It does **not** turn the suppressed upload into a successful dirty clear.
6. **Negative-control split:** (A) external write with no CPU locks -> immediate retire; (B) external write with one writable CPU lock -> conflicting Unlock error and last-lock retire; (C) external write with only read-only CPU Lock -> still conservative invalid-call on Unlock, but no previous dirty upload to suppress; (D) write to mip X while mip Y locked -> whole-texture conflict flag, not per-mip exemption; (E) two locked mips -> first Unlock remains pending, last Unlock retires; (F) external API failure, no matched 2D identity, DirectOnly, or `R14InternalUploadDepth>0` -> no *new* external-write retirement from that API; (G) R15 successful generated-mip call without in-flight locks -> `validMask &= 1u` and lower mip invalidation without immediate whole-shadow retire, unlike generic external texture writes. These are source-branch outcomes, **not** executed test observations.
7. **Time-order limitation:** External hooks record coherent invalidation after the wrapped native operation returns successfully; `TextureGenerateMipSubLevelsDestR15` likewise calls its native void trampoline before checking internal depth and updating the shadow masks. A theoretical concurrently running CPU Unlock that completes *between* native call and later bookkeeping would need a real multi-threaded device/call interleaving to establish any hazard. Nothing in this review proves such an overlap exists or that D3D device threading contracts permit it. The source entry mutex serializes bookkeeping/Unlock bodies but does not cover the entire external native call. Treat this strictly as a bounded instrumentation question, not a demonstrated lost-update bug.
8. **Physical visibility and stereo:** `PhysicalDrawCommand` binds the actual GPU primitive's producer/scope/queueNode/queueEpoch, not merely a CPU sprite node. Deferred D3DX `FlushDest/EndDest` restores only exact homogeneous +TIME/GOAL ownership during actual native submission; unknown/mixed/foreign queues remain unclaimed. R30 indexed route checks external F11 ImGui -> R62 fixed-function candidate -> XYZRHW -> guarded R29/native; `R62 E_NOTIMPL` is a route refusal, not final failed draw. R7 hooks real DP/DIP/UP and RT/depth/Present. Any binocular symptom requires both actual L/R native HRESULTs and correct StateBlock/RT0..N/depth/stencil/viewport/WVP/texture-binding restore, valid pose/eye extents and the real R9 Present result. `stereo_renderer.cpp::PresentDest` can restore mono on incomplete stereo; x64 `vrhost/src/main_r23.cpp` ties actual submitted frameId/sourceKind and `xrEndFrame` layer, distinct from a CPU shadow upload. No texture->physical draw->L/R->restore->Present->OpenXR trace was captured.
