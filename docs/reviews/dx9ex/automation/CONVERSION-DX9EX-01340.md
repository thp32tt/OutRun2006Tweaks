1. **Original producer and physical draw are not equivalent.** `docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md:62-79` maps +TIME `0x00498670`, digit helpers `0x004973C0/0x004974E0`, B9200 queue glyphs, and deferred D3DX End. `src/hooks_uiscaling.cpp:3431-3507,3660-3835` tracks exact native D3DX Flush/End and queue boundaries; `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:3118-3128` consumes an actual captured physical semantic. A numeric CPU registration does not prove a particular FVF142 GPU DIP.
2. **Default renderer contract.** `AGENTS.md:1-10` and `docs/DX9EX_OPTICAL_ROUTE_PROBE_POLICY_20261020.md:9-50` specify R26+HUD default and a physical draw probe; older AGENTS text saying R84 mainline is superseded. No renderer or switch is changed by this audit.
3. **Horizontal asymmetric FOV affine is guarded but not itself a cant rotation.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::R30BuildEyeAffine:2459-2496` computes finite eye-relative X scale/offset from each eye's tan(angleLeft/right), with positivity and scale/offset bounds. Its inputs contain FOV but no eye quaternion, so a call to *this helper alone* cannot prove optical correction for nonzero eye cant. That is a **scope distinction**, not a source-confirmed defect, because the exact-result finite HUD plane has a later independent eye-pose matrix.
4. **Shader/c64 exact-result path explicitly handles cant.** `::R30BuildScreenSpaceEyeConstants:4544-4730,4770-4923` requires source-owned same-shader raw game c64 or bounded exact original game upload, game base projection, matching latched head pose sequence and finite matrices. For `PerspectiveHud/Hud2D`, `StageExtensionPlane::BuildStageEyePoses` is required for exact result; per eye it builds `MatrixFromQuaternionTranslation(resultEyeOrientation, resultEyeOffset)`, inverts that pose and multiplies the eye-specific FOV projection after common head-inverse. For non-result HUD the intentional identity orientation remains; applying exact-result cant indiscriminately would be a regression. This is positive static evidence against the hypothesis that all result sprites necessarily drop eye cant.
5. **R62 FVF142 uses the same exact-result pose contract.** `::R62TryFixedFunctionSpriteIndexed:5171-5355` requires TRIANGLELIST, backbuffer, no live VS, precise FVF `0x142`, nonempty viewport and matching stereo pose sequence. `::R30ConfigureXyzrhwWorldEffect:3130-3345` requires an exact HUD semantic and for exact result builds `BuildStageEyePoses` from latched eye offset + eye orientation, then head inverse + per-eye inverse + projection. `::R62TryFixedFunctionSpriteIndexed:5230-5365` applies the finite HUD clip mapping as a fixed-function projection matrix around each physical DIP. R30 stereo helper draws left then right and restores RT/DS/viewport; R62 separately attempts to restore original D3DTS_PROJECTION. These source branches do not prove their runtime HRESULTs or matching pixels.
6. **Viewport/game-pixel and output aspect are separate coordinate planes.** `::R30PrepareXyzrhwState:2550-2590` and `::R30TransformXyzrhwVertices:3470-3530` use the *current* D3D viewport X/Y/Width/Height to translate XYZRHW pixel coordinates into per-eye clip mapping; this is not an assumption that XR recommended extent equals desktop/game dimensions. `::R30HudContainScale:1765-1798` applies uniform scale in both axes after 1080p reference fit, deliberately avoiding double aspect correction. `::R30HudAspectCompensation:1684-1765` computes a guarded source-backbuffer to host-recommended-eye average aspect (or angular fallback); this helper's existence does NOT prove that the fixed-function result path scales every eye using that average.
7. **Host eye extents are published and used independently of source pixel grid.** `vrhost/src/main_r23.cpp:2584-2624` resolves startup expected eye allocation from each `xrEnumerateViewConfigurationViews` recommended/max size and publishes it before creating the D3D9 game window. `vrhost/src/main_r23.cpp:1450-1517` takes each half of the source SBS UV *only in the classic path*, whereas DirectGPU supplies per-eye SRVs; each view is rendered into a separate array eye RTV and `XrCompositionLayerProjectionView` uses each physical swapchain eye extent plus actual `views[eye].pose/fov`. Do not conflate source UV, game BackBufferDesc, current D3D9 viewport or OpenXR extent.
8. **Submission/restore gate is separate from optical acceptance.** `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:676-822` publishes active stereo Frame.v2 only after world/duplicate/pose/compose checks and successful native Present, with fallback cases. `vrhost/src/main_r23.cpp:3089-3140,3522-3616` checks candidate frame flags, tracks actual `xrEndFrame` layer/frame and does not equate a stale candidate with submitted pixels. We did not observe native Draw HRESULTs, per-eye physical GPU output, StateBlock Apply/SetTransform restoration, frame join, nonzero eye cant, nor a Quest 3/VDXR HMD image in this task.
