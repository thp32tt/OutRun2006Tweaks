## REVIEW_SCOPE / pipeline walk

This audit concerns **the owner of the pre-HUD image sampled for stereo SkyGlow**, not 01149's native UP-to-XR frame-pacing costs, 01148's result-glyph R62 DIP counters, 01147's viewport sizing, or 01146's Reset/TLS node epoch.

1. **Original producer / REA limitation:** checked-in REA `docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md:14-26,33-50,76-81` maps stage render scheduling `0x00449050` and sprite queue consumer `0x0042D710`; kind-0 queue uses D3DXSprite Draw with potentially deferred Flush/End, kind-1/flagged sprites use native UP. **A particular base-sky/cloud/light shader Draw is not physically identified by this map**. The centre sun `D3A5→C980→C993`, outer `CABE` circles, original world sky and post-process SkyGlow are distinct ownership candidates. Unknown indirect original shader dispatch is not promoted to a known GPU call.
2. **Semantic → queue → physical screen draw:** `src/vr/game/render_semantics.hpp:1083-1101` defines `IsSkyGlowPreHudBoundary` as exactly `ScreenHud` or `ScreenOverlay2D`, explicitly rejecting `WorldBillboard`, `SceneEffect`, `ProjectedWorldMarker2D`, `SkyGlow`, particles and unknown. The selected queued node, or a direct producer's scoped semantic, must survive to `ConsumeForDraw` at the real API boundary; D3DX Draw scope alone does not prove when a deferred DIP is submitted. Default R26+HUD `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:5339-5505` calls `R30BeforeScreenDrawForSkyGlow` from all four physical Draw*/UP entry points, before R62/XYZRHW/R29 or original fallback. Native UP and kind-0 deferred DIP must remain distinguishable by API and queue/batch fingerprint.
3. **Stock game glow versus stereo bloom:** `src/hooks_graphics.cpp::RestoreSkyGlow::SkyGlowAllowed:930-935` disables stock mono glow in true stereo; `BlurGlowImage_dest:1252-1274` skips the stock chain when disallowed; `GlowInit_dest:1314-1329` declines mono glow buffers. In contrast, the R26+HUD implementation `R30CaptureSkyGlowSceneBeforeHud:1156-1191` copies **both** game backbuffer and right-eye surface into reduced textures; `R30ApplyStereoSkyGlow:1213-1429` separately bright-extracts, blurs and additively composites each eye. This is a screen-space post-process after world/sky draw, **not** proof that a base-sky shader draw chose RotationOnly, WorldStereo or any specific optical route.
4. **State and end-to-end eligibility:** R26 `R30ApplyStereoSkyGlow:1215-1257` requires world-stereo and duplicated-draw frame, no failed right eye/incomplete frame, stereo surfaces, and skips WARP/RESTART/GOAL/TIMEUP/LINK_TIMEUP/GIVEUP. It rejects a dirty post-HUD source only if the first-screen `R30SkyGlowScreenDrawEpoch` was stamped. `:1260-1405` saves the game StateBlock, RT/depth/viewport, performs per-eye glow and restores these bindings, with explicit failure handling. `PresentDestR30:1491-1507` executes this pass before lower Present. `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:692-805` separately decides valid stereo or mono fallback and actual D3D9 Present; `vrhost/src/runtime/d3d9ex_direct_passthrough_r32.hpp:253-321` admits a new SafeEye pair only after copy/fence, while `vrhost/src/main_r23.cpp:3562-3608` queries actual `xrEndFrame` layer/submitted-frame identity. None of those gates demonstrates how a SkyGlow pixel appears in a Quest 3 lens.

## NEW_FINDING — conditional R26/R84 frame-fence mismatch (static fact, NOT an observed glitch)

NEW_FINDING=CONFIRMED_STATIC_R26_PREHUD_FENCE_DEPENDS_ON_SKYGLOW_SETTING_WHILE_R84_FENCE_CONSUMES_FIRST_SCREEN_BOUNDARY_EVEN_WITH_GLOW_OFF.
HUD_BLOOM_CAUSED_IN_LIVE_GAME=UNCONFIRMED; SAME_PRESENT_SETTING_TOGGLE=UNOBSERVED; SKY_SHADER_PHYSICAL_OWNER=UNKNOWN; HMD_PASS=NO.

- **Default R26 code:** `R30BeforeScreenDrawForSkyGlow:1196-1211` returns immediately on `Settings::SkyGlowFactor <= 0` BEFORE stamping `R30SkyGlowScreenDrawEpoch=PresentEpoch`. If glow stays enabled, it stamps first screen draw and tries to capture clean left/right scene; any capture failure is then fenced, so `R30ApplyStereoSkyGlow:1243-1255` skips the dirty fallback.
- **Nondefault R84 comparison:** `src/vr/d3d9/stereo_renderer_r33.cpp:1615-1624` forwards the exact physical pre-screen semantic into `R30SupportBeforeScreenDrawForSkyGlow`; `src/vr/d3d9/stereo_renderer_r30.cpp:8676-8693` calls `R30CaptureSkyGlowSceneBeforeHud`. Its `:1483-1512` first stamps `R30SkyGlowScreenDrawEpoch=frame.presentEpoch`, **even when SkyGlowFactor is OFF or original game glow is inactive**, before checking whether a clean capture can be made. Its Present-time `:1567-1593` refuses to sample a now HUD-painted source when the attempted pre-HUD copy was absent.
- **Conditional counterexample, not measured runtime:** In one Present epoch, if (a) a physical ScreenHud/ScreenOverlay2D is submitted while `SkyGlowFactor=0`, (b) the setting becomes positive before the same epoch's R26 Present, (c) both-eye world/duplicate gates become or remain eligible, and (d) the state is not excluded by the scene-mode switch, the R26 pre-screen stamp was skipped. Its `R30ApplyStereoSkyGlow:1305-1310` then permits a fallback `StretchRect` from the *current*, potentially HUD-painted left/right surfaces before bright-extract/blur/composite. This is a **reachable conditional source-flow difference**; no evidence establishes the user can trigger such a toggle inside one frame, that the resulting HUD pixels pass the brightness filter, that a frame is actually XR-submitted, or that this caused an observed screen defect.
- **Other fail-closed scenario:** when first UI draw arrives before `FrameHadWorldStereo && FrameHadDuplicatedDraw`, R26 stamps its boundary but fails the clean copy, so a later eligible Present suppresses glow rather than sampling UI. This prioritizes HUD correctness over bloom continuity; do not call it a proven missing-sky bug. R84 likewise consumes the first screen boundary when no valid clean pair exists.
