## Pinned original producer → GPU → eye → ResetEx → Present → OpenXR static simulation

1. **Original producers and draw ownership.** Checked-in REA evidence `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:6-32` maps +TIME's six E8 calls, scheduler 0x00449050 → 0x0042D710, and type-0 D3DX, flagged type-0 native UP, type-1 animation and type-1 masked native branches. These are original CPU/queue candidates, **not measured physical GPU submissions**. `src/vr/game/render_semantics.hpp::SelectSpriteQueueNode:1789-1837` binds a node + queue epoch and only grants exact screen/world owner when source-proven; unknown defaults to ScreenOverlay2D. D3DX Begin/Draw can defer an actual DIP until Flush/End; native UP can bypass that ledger. Physical API/DrawSerial for any exact +TIME, GOAL or lens glyph is unknown.
2. **R30/R62 and bilateral state gates.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5377-5461` tries R62 fixed-function indexed non-UP D3DX candidate and separate later routes; `::DrawPrimitiveUPDestR30:5464-5490` / `::DrawIndexedPrimitiveUPDestR30:5493-5525` use separate XYZRHW/screen-space/lower fallbacks. `::R30ExecuteXyzrhwStereo:3829-3945` checks actual left/right draw and right RT/depth/viewport restoration, flagging right failure. Semantic classification and stereo callback entry alone do not prove eye pixels or physical draw count; ResetEx cannot turn a previous queue epoch into proof of a new current-frame owner.
3. **Game ResetEx has an explicit invalidation boundary.** In compiled R26+HUD comparison conditions `src/vr/d3d9/stereo_renderer_r13.cpp::ResetDestR13:425-463` forces `GameSemantic::EndSpriteQueueFrame(true)` for the game device. For the compatible R13 owner it calls `R13ResetCommonPre:380-423`: release mono/depth and stereo resources, drop transport ACK view, reset R9 seeded and frame state, `PublishStereoState(StereoDisabled, false,...)`, and `PublishRenderFrame(StereoDisabled, 0,...)`. `ResetCompatDevice` and subsequent resource/depth rebuild are guarded. A reset is therefore **not permission** to reuse pre-reset source/queue/eye metadata as a new game stereo frame; these guards are positive counterevidence against unconditional stale game Frame.v2 acceptance.
4. **A later native Present must independently re-prove stereo.** `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:693-811` demands seeded world stereo, duplicated draw, valid pose, no right-eye/incomplete errors and resources before compose/direct ring; after native Present success it publishes `StereoSbsActive`, otherwise disabled/fallback state. R13 reset itself does **not** generate a new successful stereo game Present. If the fresh post-reset game draw has not completed, the host should reject the current `StereoDisabled` descriptor.
5. **Host new-candidate gate works, but cached projection has a distinct lifetime.** `vrhost/src/main_r23.cpp:3091-3127` rejects `before.state != StereoSbsActive`, missing frame/pose/flags and in-flight Present. Separately, `main_r23.cpp:2666-2679` holds `cachedProjectionViews/cachedProjectionValid`; `:3292-3343` refreshes only after newStereoCommitted or absence of a valid cached projection. If no eligible post-reset source exists, `:3369-3409` chooses a prior released `projection-cached` whenever `cachedProjectionValid` remains true, because `cachedHold=cachedProjectionValid`. This preserves the last released image on a producer disruption **by design**, but it is not a fresh current-reset optical draw. Neither the R13 reset-side disabled descriptor nor the candidate-rejection branch in these inspected lines directly sets `cachedProjectionValid=false`.
6. **Reset-related invalidators and protective exceptions.** Host invalidates released gameplay cache on `xrEndSession` (`main_r23.cpp:2733-2744`), reference-space change (`:2780-2792`), transition away from Gameplay (`:2874-2905`) and new direct producer run epoch (`:2964-2988`). The direct-run path explicitly comments that a *same-run Reset/recenter does not clear cadence* (`:2964-2968`); this comment is about cadence, **not** proof that every ResetEx leaves the projection valid. A presentation/game state transition to Theater **does clear** the cache and refutes the scenario. Startup XR eye extent is resolved against recommended/max per-eye view extents and checked against allocation (`:2583-2636`): that extent check is not a frame-by-frame game ResetEx/source-extent generation join. A game viewport change does not imply a new XR swapchain allocation.
7. **Requested cache does not equal actually submitted layer.** A successful host eye projection draws two D3D11 RTV array slices and releases the OpenXR image (`R23RenderProjection:1440-1513`). Cached re-submission reuses released projection image/views; `main_r23.cpp:3562-3615` invokes `xrEndFrame` and separately reads the *actual* R23/R24/R32 intercepted final layer/source/frame. `01204` already documents that verified-bundle TTL and final interception can override requested cached gameplay projection. This review makes **no claim** that an old image necessarily reaches Quest3 after ResetEx, nor that a game-pixel/XR-extent change demonstrably produces double +TIME or blurred HUD.
