## EVIDENCE — source-pinned static walk

1. **Source-to-logical-pixel mapping is a separate owner.** `src/hooks_uiscaling.cpp:510-575` maps original 640x480-style UI sprite transforms through game screen scale/resolution, `LogicalUI::Contain` and the physical selected render target; it conditionally adds logicalViewport.y for portrait-compatible source containment. The commented purpose explicitly separates this game-side coordinate mapping from OpenXR projection/pose. Thus one correctly identified result glyph producer/queued SpriteNode does **not** by itself prove its source coordinates were already mapped to the actual target extent.
2. **GOAL producer/queue/native D3DX source before GPU API.** `src/hooks_uiscaling.cpp:414-469,3097-3105,3292-3393,3504-3580,3733-4020` distinguishes exact B9200 entry, queued child node/epoch, direct proven D3DX Draw and deferred native Flush/End, with foreign/mixed owner fallback. `src/vr/game/hud_command_batch.hpp:23-42,99-142,179-285` holds lifetime evidence. These facts are inherited as *input context* from 01459; no new x86 source CALL site or runtime glyph is claimed. At the final API, distinguish D3DX `DrawIndexedPrimitive` FVF 0x142/null VS from XYZRHW Draw(UP) and shader/c64 routes; no semantic-only global promotion.
3. **XYZRHW uses *live D3D9 viewport*, not automatically XR image pixels.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:2565-2616` checks device, live VS, XYZRHW FVF, GetViewport nonzero width/height, depth range, latched pose sequence and FOV affine bounds. `:3566-3569,3816-3835,3902-3913` normalizes original (x,y) using `viewport.X/Y/Width/Height`, changes per-eye NDC and converts back using the **same** viewport. This is internally consistent pixel math; the observed guard does **not independently compare** that viewport rectangle with `Game::screen_resolution`, selected logical UI source extent or the host XR projection extent. This is a **diagnostic observability seam**, not proof of wrong pixels in a real frame.
4. **Asymmetric horizontal FOV is explicitly handled and bounded.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:2484-2520` calculates each eye's tan(left/right), a common tangent span, and per-eye scale/offset; it rejects invalid width, scale outside 0.50..1.50 or absolute offset above 0.50. `:2804-2849` independently derives finite-world-lock HUD clip coefficients from base projection, HUD plane and `hudViewProjection[eye]`. Therefore a nonzero eye cant or asymmetry must **not** be labeled unsupported just because the affine helper uses horizontal FOV: orientation/pose have another stage. Missing live latched pose, rejected affine and mispaired frame epochs are separate fail-closed possibilities, not observed HMD defects.
5. **R62 uses a different physical geometry contract.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:5289-5384,5390-5469` requires exact ScreenHud/projected semantic, TRIANGLELIST, live null VS and FVF 0x142; it obtains the current viewport and latched stereo, then transforms **D3DXSprite XYZ** by per-eye fixed-function projection matrices (not rewriting XYZRHW screen pixels), calls the two physical indexed draws through `R30ExecuteXyzrhwStereo`, and attempts original-projection restore. Rejecting FVF/pose/semantic leaves native fallback; never treat a count of semantic tokens as proof the indexed eyes drew successfully. `:5033-5140` separately gates shader/c64/other screen-space paths by corroborated semantic, resources, depth/stencil state, pose and eye constants.
6. **R7 D3D9 stereo and transport guard differ from source/UI mapping.** `src/vr/d3d9/stereo_renderer_r7.inc:1134-1145` has a strict full-backbuffer viewport check for particular clear/depth decisions, but this is not a universal invariant over the R30/R62 accepted HUD rectangle. `:1299-1351` reads atomically published per-eye recommended target dimensions, requires both eye extents equal and resolves a device-cap-limited DirectGPU texture extent; `:1540-1557` saves D3D9 viewport, draws left, binds right RT/depth, sets viewport, restores state and poisons frame on failure. The result still needs actual per-eye draw/restore receipt and the real Present/Frame.v2 publication; matching texture dimensions alone do not establish correct optical source coordinates.
7. **Host XR scale is a separate, real boundary.** `vrhost/src/main_r23.cpp:2590-2638` obtains the runtime's two view-configuration extents, resolves/publishes startup eye allocation before the game window, and fails if later allocated swapchain size differs. `:1440-1513` samples either two DirectGPU SRVs with full UV or left/right halves of `GetGameUv`, draws separate D3D11 image array slices at projection_.width/height, and publishes each eye's actual XrView pose/FOV and imageRect. `:3562-3593` checks the actual `xrEndFrame` submission kind separately. A successful XR allocation equality gate is **not** a per-glyph game-coordinate/viewport equality gate; source crop, native-vs-DirectGPU path, each eye's current texture and final layer must be correlated.
