**Independent source proof:**

1. The current mod's `Game::DrawObjectAlpha_Internal` targets original EXE+0x56D0 (0x4056D0), while the source wrapper increments `LensOuter570008Ordinal` and optionally logs `VR LENS 570008 ORIGINAL BOTH DRAWN` **before** entering this function. That log label is a source-call observation, not an opaque-queue admission or pixel receipt.
2. At `render_object_override_4056d0`, the independent original-game reconstruction reads `n = bank.system.u32(obj.info + 0x30)`, then checks `int32(uint32(c.opaque.undo.size()) + n) >= 0x80`. If true it returns **before modifying colours or calling `render_object_405360`**. This is a concrete original admission/skip mechanism, distinct from deferred-vs-immediate execution timing and from D3DX SpriteNode queue tagging. The threshold is inclusive: `127` is admissible, `128` is rejected (assuming a valid object, matching count and no other failure).
3. In the reconstructed `sun_flare_40cbc0`, the first 0x570008 is queued after **five** preceding flare-ring `4056D0` calls (57000e/003/004/005/007) while `immediate_8999b0=0`. Those calls can already have populated the *same opaque colour-undo vector*. The first 570008 therefore faces `previousUndoCount + itsColourCount >= 128`.
4. The original 4052C0 flush following the ring list restores colour overrides in reverse and `opaque.undo.clear()`, resets opaque queue counts and sets `immediate_8999b0=1`. The **second** intentional 0x570008 call (near-centre glow, size=1.5, different alpha) comes **after** that clear and therefore faces `0 + itsColourCount >= 128` in the reconstructed normal ordering. This does not guarantee it draws: missing bank/invalid object, mesh culling, stage state and native GPU submission remain separate gates. It establishes an *asymmetric admission test* for two calls using the same handle.
5. The baseline R26+HUD wrapper already calls the same original EXE target; its older CABE logger lacks today's explicit 0x570008 ordinal. Thus this gate is not a newly proven regression or a game optical explanation. Current game render may or may not encounter the threshold; the decomp is a reconstruction, NOT new runtime evidence.

**Counterexample to the misleading inference:** Under a hypothetical valid scene with undoCount=120 immediately before first 0x570008, and this object's colourCount=8, first call logs ordinal=1 but is dropped by 4056D0 (`120+8=128`). After the batch 4052C0 clear, second call logs ordinal=2 and *passes this particular gate* (`0+8=8`). No duplicated source object is involved. This is a conditional input example, NOT claimed measured colour counts for 0x570008. If actual undo never approaches 128 in the affected scene, reject this mechanism as an explanation.
