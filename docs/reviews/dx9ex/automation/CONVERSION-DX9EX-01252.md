- FACT: Under preconditions `StereoInstallState==Ready` and `newDevice != StereoInstalledDevice`, `InstallStereoHooks(newDevice)` returns `false` without a new hook transaction or CreateQuery probe and without clearing the previous `QueryIssueHook`. The synchronous caller propagates `false`. The worker's Ready exit does not re-evaluate a new game device.
- FACT: `IsGameDevice` is based on the current game pointer, and `QueryIssueDest` filters by the current query's game device; this is distinct from the installation's saved device identity. `CreateQueryDest` does **not** associate a non-null `QueryIssueHook` with a particular current device or `Issue` function pointer.
- HYPOTHESIS A (different COM pointer): a genuine in-process D3D9 device replacement could leave newly current game draws/queries dependent on previous method detours, if hook targets differ and no upstream recovery owner re-installs. The visible effect could be missing stereo eligibility, incorrect query tracking, mono fallback, or wasted retry work. **None** is an observed game defect.
- HYPOTHESIS B (same-address COM reuse): a destroyed/reconstructed COM device allocated at the same pointer might pass the Ready pointer check without proving identical vtable, generation or query `Issue` implementation. This also lacks an observed lifetime trace.
- CONTRARY: OutRun may only Reset/ResetEx a single stable device for the entire process; driver COM implementations and query vtables may share exact method addresses; an upstream CreateDevice owner may abort/restart on false; or process restart may reset globals. These outcomes defeat a runtime failure inference without changing the confirmed guard logic.
