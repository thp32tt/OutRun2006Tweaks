## 2. EVIDENCE — end-to-end static call/ownership simulation

1. **Original game producer and deferred queue are partially resolved, water is not.** `docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md:1-42,83-112` maps frame scheduling `0x00417B20 -> 0x00449050`, scene's indirect dispatch, sprite queue `0x0042D710`, D3DX Begin `0x00429C60` / Draw `0x0042A0A0` / End `0x00429F60`, and native `DrawPrimitiveUP` via `0x0042A3A0/0x0042A800`. D3DX Draw can physically submit at End/Flush and native UP is a distinct path; no generic D3DX draw proves water/reflection. The original water/reflective/glass producer and its final physical API **remain UNKNOWN** without original RT, texture, depth and producer fingerprint.
2. **Semantic and physical R26/R30 draw gate.** `src/vr/game/render_semantics.hpp:14-34,1018-1052` defines `ReflectionCube` separately from `WorldParticle`, `WorldBillboard` and `SceneEffect`; `ConsumeForDraw` preserves exact queued owners and some one-shot scopes, not a generic water tag. `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:5293-5405,5408-5468` routes all four DP/DIP/DPUP/DIPUP physical interceptors through semantic consumption and pre-HUD SkyGlow fencing, offers conditional fixed/XYZRHW stereo, and otherwise calls guarded native/R29 fallback. A shader/VB reflection draw is **not** proved to take the R30 UP path merely because an unrelated particle does. R26 stereo eye draw restores target/depth/viewport and poisons failed right eye or restore (`R30ExecuteXyzrhwStereo():3784-3900`); this is conditional to admission, not proof that every water draw duplicates.
3. **Host's actual stereo image extent has one common size.** `src/vr/ipc/xr_eye_extent.hpp:16-45` resolves the host left/right OpenXR recommended rects to a common capped per-slice size, then `ResolveGame` rejects a requested target exceeding D3D9 caps instead of silently downscaling. `vrhost/src/main.cpp::CreateProjectionSwapchain():1924-1942` obtains this extent, configures a two-array-slice swapchain and passes it to `xrCreateSwapchain` at `:1955-1966`; the theater mirror uses the projection extent independently. These sizes are **not necessarily** the original game backbuffer or 640x480 logical HUD dimensions.
4. **Game-side snapshot distinguishes seqlock contention from mismatched eyes.** `src/vr/d3d9/stereo_renderer_r7.inc::DirectTransportTargetSize():1300-1347` reads both eyes' `recommendedWidth/Height` under a bounded seqlock retry. If either pair differs (`w0 != w1 || h0 != h1`), it rejects direct target sizing immediately. If snapshot stability cannot be attained after four attempts, it instead uses the existing `DirectTransportWidth/Height` before `ResolveGame`. A sustained mismatch or invalid/caps-exceeding extent can cause direct-transport fallback; *which cause, frequency and visible behavior have not been measured*. This does not prove a host bug because the ABI requires equal eye-array extents.
5. **NEW_FINDING: the resource-rebuild gate is by size generation, not by every Present.** `src/vr/d3d9/stereo_renderer_r7.inc::EnsureDirectTransportResources():1353-1356` fast-returns when `DirectTransportResourcesReady`, `DirectEyeExtentGeneration.Matches()` and both cached target dimensions match. Otherwise it retires/releases the existing direct transport slots and creates **two default-pool shared textures + associated surfaces + one D3DQUERYTYPE_EVENT fence per slot**. `ResolveDirectTransport():1357-1359` calls this gate from the game Present path. Four-slot ownership is visible at `:1361-1411` and logged by the creation function; therefore a successful generation rebuild creates 8 eye textures and 4 EVENT fences, *not* an 8-texture allocation per frame in stable extent. A genuine sequence of extent changes/recovery or persistent failed allocations could induce repeated work; there is no trace proving it happens or is a current bottleneck.
6. **Per-frame GPU transport work is a separate cost from allocation.** `src/vr/d3d9/stereo_renderer_r7.inc::ResolveDirectTransport():1364-1425` checks existing fence/ACK ownership, selects an available slot without blocking on pending `S_FALSE`, submits two `StretchRect` eye copies and one `Issue(D3DISSUE_END)`, then marks the slot producer-pending. `DirectTransportFrameReadyAfterPresent():1428-1447` permits at most 1 ms of bounded post-Present completion grace and does not inject additional FLUSH. These per-frame copies can coexist with GPU reflection/water work; they **do not imply** 8 new textures per frame. 01077 already covered pending EVENT/publication; do not count the same EVENT suspicion again.
7. **Present, fallback and OpenXR correlation.** `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9():676-823` requires completed world stereo and pose before `ResolveDirectTransport`; if direct fails with `directOnly=false`, `ComposeSbs` attempts fallback; `directOnly=true` suppresses SBS fallback and keeps PC mirror mono/left, not proof of a new game failure. It calls actual D3D9 Present and publishes `StereoSbsActive` only on successful eligibility; otherwise mono/disabled fallback. `stereo_renderer_r7.inc::ComposeSbs():1498-1516` explicitly restores StateBlock, RT/depth/viewport and rejects failure. ## 3. NEW_FINDING / hypotheses and falsification

**Confirmed from source:** the R26 default's downstream DirectGPU path preserves shared eye textures across successful stable-extent Presents. A *valid changed extent* (or resource-ready invalidation) goes through retire/release and reconstruction of a four-slot × two-eye texture ring and four EVENT fences; a mismatched eyes snapshot rejects direct sizing while bounded seqlock contention alone has a guarded cached-extent path. These are distinct control-flow outcomes.

**UNPROVEN symptom/performance hypothesis:** at startup, host swapchain resizes, render-scale transitions, Reset/device-loss recovery or repeated resource-ready failures, the rebuild could produce a CPU/GPU allocation spike or a temporary switch to SBS/direct-only mono. Dense buildings, water/reflection shaders, per-eye draw duplication, alpha overdraw, the two obligatory copies, initial interoperability probe, host capture/commit/wait and OpenXR scheduling can produce similar frame spikes. There is no evidence here that a *steady* water scene causes extent changes, or that any rebuild repeats during normal gameplay.

**Falsification / acceptance inputs:**
- Record same exact active `dinput8.dll`/host hashes, R26+HUD vs explicitly separate R84_TEST, game source resolution/logical UI viewport, host projection per-eye extent, requested scale, D3D9 caps, actual swapchain width/height, and DirectGPU vs SBS/direct-only setting.
- Correlate `recommendedWidth/Height[0/1]` sequence and seqlock state with `DirectEyeExtentGeneration`, generation commit/reset, releases, CreateTexture/CreateQuery results, Reset/device-loss epoch, DirectTransportFallbacks and ring backpressure per **frameId**. Capture *only bounded* state-transition records; do not add per-draw unbounded logs.
- Measure GPU game draw time for exact verified water/reflection producer + RT/texture/depth fingerprint, CPU Present/Resize/alloc time, StretchRect/Issue/fence, host capture/copy/render/wait, xrEndFrame, and p95/p99 under matched empty-road/dense-buildings/water scenes at 72 Hz. Identify whether the final eye and actual submitted frame used DirectGPU, SBS, cached/menu or fallback.
- If the extent/generation stays unchanged and resources remain ready across lag spikes, **reject repeated DirectGPU allocation as the cause** and profile actual shader/overdraw/copies/waits separately. If rebuilds occur only at startup/reset and p99 spikes happen later, the rebuild is not the steady-scene culprit. If same-frame trace proves resize-driven repeated retire/recreate and corresponding frame delays, prioritize a separately authorized narrowly gated remediation; do not preemptively rewrite.
- An eyepair size mismatch rejects direct transport by design; it is not itself a code defect. It can only be called an unexpected host-contract failure after capture proves a valid stable published mixed pair in a real run.
