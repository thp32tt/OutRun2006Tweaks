## EVIDENCE — GitHub source/REA/issue; fact versus hypothesis separated

1. **Active baseline and independent original producer.** Root `AGENTS.md:1-5` and option-free `CMakeLists.txt:95-148,230-246,269-303` designate R26+HUD and `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp` as current default; R84 is explicit nondefault, despite older contradictory historical AGENTS paragraphs. `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:7-43` reports original EXE SHA256 `68ceb386829066f8455b9d027320af962584321f3e2e8a79c72841495a6134c3`, +TIME six verified E8 calls, and four queue branches. `docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md:7-72` maps D3DX Begin/Draw/End and subsequent physical DIP versus direct DPUP; producer label alone is NOT proof of R62 DIP.
2. **R62 admission is physical and narrow.** `stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5550-5635` consumes the current physical draw semantic and tries external F11 ImGui first, R62 second, and XYZRHW/shader/R29/original paths if declined. `R62TryFixedFunctionSpriteIndexed:5304-5366` requires backbuffer stereo, corroborated projected marker or HUD scope, trianglelist, null live VS, exact FVF 0x142, stereo resources, nonzero viewport width/height, latched pose and finite projection; exact result provenance can bypass *stale cached VS identity* but not a nonnull live VS. This does not imply every +TIME/GOAL sprite qualifies.
3. **Eye-specific XY clip changes with a stock D3D9 viewport.** In `R62TryFixedFunctionSpriteIndexed:5368-5453`, projected marker uses `originalProjection * clipShift[eye]`, while finite ScreenHud uses `originalProjection * clipMap[eye]`, where `clipMap` contains eye-dependent hudClipX/Y/W. `drawEye:5455-5471` sets that eye's PROJECTION then calls original hooked DIP. `R30ExecuteXyzrhwStereo:3957-4003` switches to the right-eye RT/depth and explicitly reapplies `state.viewport` for the right pass; it does not change scissor state. The viewport is the current game-device pixel domain, not the host XR eye swapchain extent.
4. **New, concrete R62 scissor ownership boundary.** The entire R62 body `5304-5523` makes no `GetRenderState(D3DRS_SCISSORTESTENABLE)`, `GetScissorRect` or `SetScissorRect` call. Shared `R30ExecuteXyzrhwStereo:3957-4073` and `stereo_renderer_r7.inc::RestoreRightPassState:1462-1464` restore/modify RT, depth, viewport and optionally WVP, but **do not capture, transform, or restore the raster scissor**. Thus **if** an admitted original D3DX physical DIP arrives with scissor testing enabled and a non-full scissor rectangle, R62 changes projected eye coordinates but leaves that identical original pixel clip rectangle in force for both eyes. This conditional mismatch is source-confirmed; it is NOT evidence that D3DXSprite actually enabled clipping in this run or that a pixel was lost.
5. **Negative control: F11 has dedicated scissor handling.** `R30PrepareExternalImGuiProjection:2872-3066` explicitly requires active scissor and captures it, computes eye-specific corner projections in viewport pixels (including `state.viewport.X/Y`), clamps both per-eye rectangles, and fails closed on invalid rectangles. `R30TryExternalImGuiIndexed:3069-3194` sets/restores both PROJECTION and scissor for L/R. F11 is a different external `ScreenOverlay2D` owner; this code cannot be assumed to fix game D3DXSprite. #01423 already isolated an **F11 telemetry field mismatch**, not the R62 raster ownership gap discussed here.
6. **Restoration, frame gates and host do not certify raster pixels.** R62 restores original PROJECTION after `R30ExecuteXyzrhwStereo` at `5469-5496`; right-eye failure or RT/depth/viewport restore failure poisons the frame in `R30ExecuteXyzrhwStereo:4047-4073`. For exact result it returns failure if projection restoration failed; non-exact failure still arms fallback. R7 `stereo_renderer_r7.inc::PresentDest:1625-1741` gates frame eligibility, native Present and post-Present DirectGPU EVENT/SBS/hold. R23 `vrhost/src/main_r23.cpp::R23RenderProjection:1438-1515` draws each source eye into independently sized OpenXR projection images using source UVs or full-range DirectGPU eye SRVs. Once physical pixels are clipped on D3D9's source RT (if that happens), host UV scaling cannot recreate them. A successful DIP HRESULT or R7 frame eligibility is not pixel correctness proof.
7. **Evidence limit.** GitHub Issue #13 is an append-only runtime regression ledger, not a same-SHA R62 scissor/viewport/HMD proof. No live D3DX scissor state, physical batch mapping, nonzero-origin screenshot, GPU fragment capture, current compiled DLL SHA, Quest3/VDXR comparison or p95/p99 profile was obtained. Reuse original REA mappings as static context only.

- **Confirmed static fact:** R62 eye-dependent fixed-function projective transform is not accompanied by an eye-specific scissor rect calculation or update, while F11's separately owned projection path explicitly remaps its active scissor. Right RT/viewport restoration does not implicitly implement a matching scissor transform.
- **Hypothesis:** if scissor testing is active on an admitted R62 D3DXSprite batch and its stock rectangle is tight relative to an eye-dependent shifted/reprojected quad, one eye can lose edge glyph/sprite fragments while DIP returns success and an eligible stereo frame is published. Window/viewport origin or source extent changes may affect this relation, but this review has not measured it.
- **Falsifiers / narrowing:** (a) authentic original D3DXSprite R62 batches have scissor disabled or full-target covering all projected quads; (b) R62 is not physically entered for suspected HUD; (c) at nonzero origin both eye rasterized sprite bounds remain inside the inherited clip rectangle with no lost pixels; (d) a separately traced, actual stock D3DX StateBlock/driver state already supplies sufficient eye scissor (not demonstrated in this source); (e) exact-SHA matched HMD/RT captures show no differential clipping. F11 positive scissor correction is a comparison only, not a license to generalize F11's implementation.
