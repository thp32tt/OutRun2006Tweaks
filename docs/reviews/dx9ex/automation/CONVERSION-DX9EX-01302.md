3. **Captured D3D11 source transaction:** `vrhost/src/main_r23.cpp::R23Capture:1018-1205` obtains a Desktop Duplication frame via `AcquireNextFrame`, avoids pointer-only redundant copies, validates/reuses its output texture descriptor, enqueues `context_->CopyResource(c.source_, texture)` (~1164) and calls `duplication_->ReleaseFrame` (~1172). On failed Release it invalidates `haveFrame_` and `stereoSourceValid_`; only a successful copied frame gets `haveFrame_=true`. Queue submission is visible; completion of that GPU copy is **not separately measured** there. 01301 already examined the distinct output QPC/pixel-provenance question and is not re-claimed.
4. **Classic source ownership after admission:** `vrhost/src/main_r23.cpp::R23SelectClassicFrameForCapture:1257-1320` picks a stable complete SBS Frame.v2 under a 100 ms QPC bound; `::R23FrameUnchanged:1237-1254` rechecks identity. `::R23CommitClassicAfterValidation:1429-1437` clears the DirectGPU state, calls `StereoCompositor::CommitStereoSource` in `vrhost/src/main.cpp:1399-1432`, and then marks classic source valid. That function creates/reuses a separate `stereoSource_` texture/SRV and enqueues `context_->CopyResource(stereoSource_, source_)`. It returns after **enqueuing**, without a synchronous completion fence. Distinguish `source_` (continuously refreshed desktop) from `stereoSource_` (committed classic source) and OpenXR projection target.
5. **Ordered pipeline; not a demonstrated GPU race:** `vrhost/src/main_r23.cpp:3215-3335` checks pose history and unchanged Frame.v2, stages classic source, then calls `R23RenderProjection`. The observed calls enqueue source copy and L/R Draw on the compositor D3D11 immediate context (`c.context_`) in that order. The next loop's desktop source update cannot *by itself* prove this earlier queued copy or draw is reordered; a normal single D3D11 immediate-context command stream preserves command ordering. However this audit did not instrument the driver/GPU, prove every possible separate context or verify OpenXR runtime fencing. Therefore no source-only evidence of asynchronous-copy corruption has been established.
6. **Paired eye draw and fail-close release:** `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` takes `stereoSourceSrv_`, selects SBS left/right UV halves, acquires an XR projection image, independently submits left and right `RenderTo` with array-slice RTVs. Common-pipeline reuse is conditional on left success; first-eye unbind may be deferred only for adjacent compatible eyes. When eye 1 fails after deferred left state, code explicitly unbinds SRV/RTV; `c.Release(c.projection_)` runs and `return false` precedes both `pv[0/1]` construction and fresh-projection acceptance. The source does not silently label a single successful eye as a new stereo projection. This is a **static control invariant**, not tested HRESULTs.
7. **Fresh/cached authority & last GPU API:** `vrhost/src/main_r23.cpp:3215-3415` sets `pendingBundlePublish` after commit but calls `OutRunVrR23VerifiedBundle::Publish` and advances `lastProcessedStereoFrame` only after `R23RenderProjection` succeeds; otherwise a previously released `cachedProjectionViews` may be resubmitted as `projection-cached`. R42 avoids redundant full-eye blits on unchanged frames. `::xrEndFrame:3562-3595` hands a projection layer or no layer to OpenXR and reads final route counters; `xrEndFrame` call/result does not independently prove GPU-completed pixels, eye optics, updated head pose or visual PASS. Previously released cached images may be intentionally old, not evidence of an erroneous new half-eye frame.
8. **Issue/runtime boundary & prior-review distinction:** GitHub Issue #6 is an open continuous-review inbox, not a current Quest3/VDXR trace. No linked exact-sha capture, right-eye HRESULT trace, GPU fence log or performance measurement was obtained. 01301 discusses capture *pixel/time identity*; this pass inspects the next **D3D11 source texture → ordered copy → L/R swapchain target → Release → cached/fresh authority** boundary without repeating that finding.
