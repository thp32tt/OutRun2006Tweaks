1. **Physical candidate admission is narrow (confirmed):** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5370-5455` first rejects the external F11 ImGui owner, then tries R62 before XYZRHW/native/R29 fallback. `R62TryFixedFunctionSpriteIndexed:5116-5203` gates backbuffer, triangle list, corroborated projected-marker or HUD scope, live null VS, FVF 0x142, resources, nonzero viewport and latched pose. `R30IsExactResultHudDraw:3063-3072` requires exact physical-command semantic and live node/epoch for queued results; no source semantic alone proves that the game really executed a particular DIP.
2. **Per-eye actual-Draw evidence is not a simple success count (confirmed):** `R62TryFixedFunctionSpriteIndexed:5260-5300` initializes `eyeHr[2]=E_PENDING`; each `drawEye` first assigns `SetTransform(PROJECTION)` HRESULT to `eyeHr[eye]`, returns `E_FAIL` **without calling the DIP** if that transform failed, and otherwise overwrites it with the original `DrawIndexedPrimitiveHook` HRESULT. Consequently the `RESULT_HUD_EYES ... api=DIP ... left/right` fields can represent a failed projection setup rather than *an issued physical GPU Draw* for that eye. Existing logs do not independently report `projectionSetHr` versus `dipIssued` versus `dipHr` for each eye.
3. **Right failure is poisoned downstream, not reflected in the hook's return (confirmed):** `R30ExecuteXyzrhwStereo:3820-3935` returns immediately on failed left draw; otherwise it tries SetRT, depth, viewport and the right callback under `InternalPassScope`, restores right-pass state, marks an attempted duplicated draw, and returns **leftHr** after recording/poisoning `FrameRightDrawFailed` or restore failure and arming safe fallback. It can therefore return success after a failed right eye; this is intentional-looking one-call D3D9 behavior protected by frame state, **not** a claim that an incomplete stereo image passed Present.
4. **Log labels/counters do not encode final success (confirmed):** `R62TryFixedFunctionSpriteIndexed:5297-5337` increments `projectedDraws` or `hudDraws` after the attempt and increments `resultDraws` for the exact-result predicate even when left/right/restore failed. The conditional `RESULT_HUD_EYES` log says `route=FiniteHud` as a hard-coded string, while the same routine can choose `projected` clip-shift matrices rather than the ScreenHud finite-plane matrices (`:5180-5258`). This route label is only potentially wrong **if** a projected path also satisfies `exactResult`; co-occurrence is NOT established. `projectionRestored` and `frameIncomplete` are diagnostic state at that point, not evidence of a successful later Present.
5. **Frame/host safety boundaries make false-positive diagnostic interpretation distinct from a proven screen bug:** `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:692-805` requires world stereo, duplicated draw, no right-eye/frame incompleteness, a valid latched pose and resources before composing; otherwise it restores a mono backup when available, calls actual Present and publishes active stereo only after successful Present. `vrhost/src/runtime/d3d9ex_direct_passthrough_r32.hpp:253-322` swaps completed safe eyes/frame ID only after successful copy/fence; `vrhost/src/main_r23.cpp:3559-3609` observes actual `xrEndFrame` layer/submission. The presence of `R62 FIXEDFN KIND0` or `RESULT_HUD_EYES` alone does not establish complete L/R images or headset optical alignment.
6. **Consequential interpretation:** a bounded trace that counts exact-result `RESULT_HUD_EYES` lines or `hits` as a successful stereo draw can overcount when one eye did not issue DIP, or label projected/FiniteHud ambiguously. This can misdirect later +TIME/GOAL diagnosis and per-API performance accounting. No trace was collected that demonstrates real occurrence, wrong right-eye HUD, GPU stall, or overdraw in the user's build.
