## REVIEW_SCOPE — original producer -> semantic -> physical draw/dual-eye restore -> R9/R13/DirectGPU -> host Present/OpenXR

1. **Original producer and physical API separation.** Committed original REA `docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md:5-42,46-51` establishes original scheduler `0x00449050`, normal queue consumer `0x0042D710` and conditional priority `0x004C50A0`; queue type-0 uses `ID3DXSprite::Draw` whose physical draw may be deferred to Flush/End, while type-1 `0x0042A3A0/0x0042A800` uses native `DrawPrimitiveUP`. Original `0x00498670` +TIME, `0x004979E0` GOAL and numeral branches remain separate provenance; neither a queued sprite nor alpha blend implies WorldParticle. The REA has no new sand/particle producer disassembly or live call stack in this run.
2. **Crucial build/feature boundary.** `cmake.toml:84-90,117-129,212-228` selects R26+HUD on fresh option-free configure and compiles `stereo_renderer_r30_r26_safe.cpp` (R33 excluded), not independently compiled R84 `stereo_renderer_r30.cpp`. The R26+HUD safe translation unit includes `stereo_renderer_r26.cpp` and safe XYZRHW path, but **does not include or invoke** `r30_particle_dual_eye_ring.hpp`; `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::R30TryXyzrhwPrimitiveUP:3947-3990` uses two `DrawPrimitiveUPHook` physical eye calls after creating distinct L/R scratch, through `R30ExecuteXyzrhwStereo:3829-3945`. The separate `DrawPrimitiveUPDestR30:5464-5490` first consumes physical semantic then tries this path and lower fail-closed fallback. This baseline must not be credited with a DynamicVB speedup solely because the alternate R30 header/file exists.
3. **Explicit comparison-only opt-in optimization.** `src/vr/d3d9/stereo_renderer_r30.cpp:21-23,165-176,6478-6594` includes the GPU ring and requires `OUTRUN_VR_R30_PARTICLE_VB=1`, exact `RenderScope::WorldParticle`, accepted world effect, reliable effect snapshot, alpha blend, depth writes off, no StateBlock recording, nonindexed and 1KiB..1MiB per eye with valid stride (`r30_particle_upload_policy.hpp:8-52`). `r30_particle_dual_eye_ring.hpp:20-76` uses a mutex, 4MiB dynamic default-pool VB, one Lock/Unlock containing **different** left and right vertex arrays, DISCARD/NOOVERWRITE with alignment and per-eye stream offsets; `finishUp` deliberately emulates UP's stream-0 null side effect. Ineligible, Lock/create failure or try-lock failure retains the existing two-UP path. It is not safe to infer that arbitrary blended sand/water/flare receives the fast path.
4. **NEW static counterexample: pre-draw failure and frame veto ordering in alternate R84 opt-in.** After eligible successful `prepare`, `stereo_renderer_r30.cpp:6534-6557` creates `physicalEye`: a failed first `bindEye(0)` returns its HRESULT **before** setting `physicalDrawAttempted=true` and before `R29OwnerCallRawDrawPrimitive`. Nevertheless, the shared `R30ExecuteXyzrhwStereo:6233-6255` already called `R29OwnerNoteStereoDrawWithoutMonoBackup` and, upon a failed left callback, calls `R29OwnerMarkRightDrawFailed`, `R29OwnerReportStereoFailure(StereoFailureLeftDrawFailed)` and `R29OwnerArmMonoSafety`. `stereo_renderer_r29.cpp:1325-1334` maps those two calls to `R9Poison` and `FrameRightDrawFailed=true`. If `finishUp()` then succeeds, `stereo_renderer_r30.cpp:6558-6576` permits `E_NOTIMPL` by `MayUseNativeUpAfterGpuAttempt(false,true,true)` and `::DrawPrimitiveUPDestR30:8442-8460` tries the original lower guarded UP path. No local undo of prior failure/flag exists in this branch. **Conditional, source-proven ordering asymmetry**, not a witnessed driver failure or confirmed visual bug: original UP replay can be logically allowed while the same frame remains conservative mono/fallback for an earlier attempted-but-not-executed GPU eye.
5. **Per-eye and restore ownership.** The **safe baseline** `stereo_renderer_r30_r26_safe.cpp:3830-3945` submits left UP, switches right RT/depth/viewport and draws right, restores via `RestoreRightPassState`; failed right/restore poisons Present. The **alternate R84** `stereo_renderer_r30.cpp:6158-6255,6350-6475` checks exact source gates, physical left, right RT/depth/viewport/source identity and restores; only both-eye+restore success records completed stereo. DynamicVB success still pays two physical DrawPrimitive calls and the projection scratch construction. Reverting to UP after an actual GPU draw is prohibited to avoid double-blend/half-eye output (`r30_particle_upload_policy.hpp:33-45`).
6. **Frame and transport fence are distinct from logical UP count.** `stereo_renderer_r26.cpp:74-129,142-305,846-925` samples five-second `R28 FRAME DIP/WINDOW/CPU WINDOW` using QPC Present-end intervals, `TopLevelDrawSerial`, per-thread CPU and estimated non-CPU residual. Draws here are *logical* serial deltas, not proven two-eye physical draws; non-CPU residual is not by itself a GPU or XR wait. Sampling is off when `VRTelemetry` is false. `stereo_renderer.cpp::PresentDestR9:676-822` publishes active stereo only with world proof, duplicate eye draw, valid pose and absence of right/restore poison; otherwise restores eligible mono, and always forwards native Present. R26+HUD's `stereo_renderer_r13.cpp::PresentDestR13:718-749` retires sprite tags after lower Present, not at the particle draw. `stereo_renderer_r13.cpp::ResolveDirectTransportR13:222-377` independently requires published-slot host GPU ACK AND producer EVENT completion before reuse, then StretchRect-copies both eyes and arms an EVENT; ring backpressure/fallback is not demonstrated by R28 draw count alone.
7. **Host consumer and optical submission.** `vrhost/src/main_r23.cpp::R23StageDirectHold:550-640` creates/reuses host-owned D3D11 eye textures and queues exactly one left/right `CopyResource` pair for a new immutable producer frame key, not per-XR-tick unconditional copies; host direct EVENT covers copy/projection until ACK. `::R23RenderProjection:1440-1513` writes the two XR swapchain eye views from direct SRVs or SBS source. `::xrEndFrame:3562-3599` independently sends the XR composition layer, and `:3600-3695` joins **actual** submitted frame ID / generation, capture/copy/render, `xrWaitFrameMs` and `xrEndMs` for opt-in pacing diagnostics. Captured original frame identity and a successful Quest3 visible bilateral sand effect are NOT supplied in this review.
