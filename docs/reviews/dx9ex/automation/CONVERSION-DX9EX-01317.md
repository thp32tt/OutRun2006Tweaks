This is a static path simulation, not a claim of an observed sand or particle problem.

1. **Producer → semantic → queue:** Historical original-game REA and whole-path audit categorize dense-world/sand as world/effect/XYZRHW candidate draws, not an exact proven WorldParticle native API trace. Current `RenderScope::WorldParticle` is a semantic category, not proof of a sand draw or texture. The original sprite-node D3DX queue/0x42D710 → 0x2D762 → 0x2DCB4 path may own HUD sprites, but must **not** be invented as the source of an unverified particle draw. The specific WorldParticle UP route requires independently demonstrated original source/queue (or direct producer) → exact semantic and actual GPU API. For the review branch only, inspect `R30TryXyzrhwPrimitiveUP` after exact semantic and per-eye CPU transform; no untrusted alpha-state promotion.
2. **R84 opt-in gate/physical draw:** `OUTRUN_VR_R30_PARTICLE_VB=1`, exact WorldParticle, worldEffect, reliable effect-state, alpha on, Z-write off, non-indexed, no StateBlock recording and bounded 16–256 byte stride/1KiB–1MiB per-eye are all necessary. The 4MiB dynamic VB takes two *distinct* per-eye XYZRHW scratch arrays in one Lock/Unlock with NOOVERWRITE or DISCARD on wrap. The code holds a try-lock across two eye submissions. `R30ParticleGpuRing.bindEye(eye)` calls `IDirect3DDevice9::SetStreamSource` before setting `physicalDrawAttempted=true` and calling the raw `DrawPrimitive`. A failed **left** bind therefore means zero particle GPU DrawPrimitive submitted by this optimized route.
3. **Pre-draw exception → stereo state → fallback:** `R30ExecuteXyzrhwStereo` calls `R29OwnerNoteStereoDrawWithoutMonoBackup()` before `leftDraw()`. A failed left bind enters the generic failed-left branch: right-draw-failed indication, depth/stencil invalidation path, stereo failure report and mono safety. Control returns to `R30TryXyzrhwPrimitiveUP`, which calls `finishUp()` (stream zero reset) and `MayUseNativeUpAfterGpuAttempt(false,true,true)`; when successful, it returns `E_NOTIMPL`, and outer `DrawPrimitiveUPDestR30` enters `R30GuardScreenSpace` to use conservative R29/native UP fallback. Thus a *pre-physical-draw* failure is currently eligible for native raster fallback but can already have set a stereo-incomplete/failure reason. This is a **source-confirmed ordering/diagnostic boundary**, not proof of a persistent bad frame or a broken API contract.
4. **Two-eye/restore/Present/OpenXR:** Normal optimized success submits separate left and right `DrawPrimitive` using ring offsets; R30 switches right RT/depth/viewport and restores, `finishUp()` resets stream zero. If any eye is physically attempted, replaying native UP is correctly forbidden to avoid double alpha/half-eye. On failure R9 `PresentDestR9` requires complete world/duplicated/pose and no right failure or incomplete flag before active stereo; otherwise conservative mono/transport fallback. Host `main_r23.cpp` selects actual source/Frame.v2, projection layer and calls `xrEndFrame`. None of CPU fallback, gate counters or xrEndFrame submission proves that original sand pixels or both eye images were correct.
5. **R26+HUD compiled baseline:** protected `stereo_renderer_r30_r26_safe.cpp::R30TryXyzrhwPrimitiveUP` directly issues two `DrawPrimitiveUP` callbacks. It does not refer to `DualEyeGpuRing` or `OUTRUN_VR_R30_PARTICLE_VB`. The identified GPU ring scenario is **not active in the default R26+HUD build** and cannot justify automatic R84 promotion or a performance fix claim.
