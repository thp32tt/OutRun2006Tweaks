## REVIEW_SCOPE — original producer → physical draw / both eyes → transport → R23/R32 host → OpenXR

1. **Original game provenance is conditional, not frame-cost evidence.** Checked-in historical REA `docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md:31-105` maps original `0x00449050` frame scheduling, `0x00429530→0x00428A10→0x00429460→0x00429350→0x00428BD0` sprite producers, D3DXSprite Begin/Draw/deferred Flush/End and native DP/DIP/UP. Static EXE inventory `docs/automation/OUTRUN_VR_REA_RESOURCE_EVIDENCE_20261018.md:1-70` identifies original CALL RVAs and +TIME/rank/lens categories, **not** a new physical GPU trace. `src/vr/game/hud_command_batch.hpp:8-105` separates producer/queue-node/epoch and delayed D3DX physical ownership; a semantic label cannot prove a GPU draw, an eye pixel or a hotspot. No disassembler was run here.
2. **Physical draw/eye/restore precedes host timing.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawPrimitiveDestR30:5349-5375;::DrawIndexedPrimitiveDestR30:5377-5445` consume draw semantics then try XYZRHW/R62, with original/R29 fallback. `::R30ExecuteXyzrhwStereo:3829-3927` issues left draw, switches right RT/depth/viewport, issues right draw and restores; world-stereo eligibility requires authoritative world evidence and valid pose, not merely duplicated HUD. `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:676-814` gates `ResolveDirectTransport` on whole-frame eligibility, executes original D3D9 Present, and publishes an eligible direct frame only after success. No physical L/R HRESULT, restore trace, GPU draw owner or Quest3 comparison was captured.
3. **Producer ring generation is not an allocation instruction for all host textures.** `src/vr/d3d9/stereo_renderer_r7.inc::DirectTransportTargetSize:1300-1347;::EnsureDirectTransportResources:1353-1357;::ResolveDirectTransport:1358-1426` maintains four shared L/R producer slots at the host-published eye extent; a resource rebuild changes generation and shared handles. A new generation invalidates per-slot host cache identity, but it does not by itself prove that the host's *same-size* private staging texture must be re-created.
4. **Actual R23 primary path uses a separate, host-owned DirectHold pair.** `vrhost/src/main.cpp::PrepareDirectStereoSource:1342-1377` opens/validates shared ring textures and explicitly returns without the *legacy private snapshot + synchronous fence*. `vrhost/src/main_r23.cpp::R23CommitDirectAfterValidation:1412-1426` calls this method, validates per-slot dimensions/format and stages `R23DirectHold` via `::R23StageDirectHold:550-641`. That hold pair is re-created only if texture/view is missing or width/height/mips/array/format differ (`:568-603`); exact same immutable frame/slot/run/handles/source COM pointers gets reuse (`:605-623`); a genuinely new frame queues two host D3D11 `CopyResource` calls (`:625-641`). Neither this path nor a successful same-size producer generation rollover calls `R32EnsureInactiveEyes` as part of its primary copy. Scope this conclusion to inspected R23 primary path, not all runtime fallback combinations or an unknown deployed ZIP.
5. **R32 final submit is asynchronous on the normal verified path.** `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` samples R23DirectHold left/right into an OpenXR two-slice projection using matched pose/FOV, independent per-eye GPU draws, restore/unbind on eye-1 failure, current projection extent and image indices 0/1. `::R42 cached/fresh:3292-3385` renders on new source and reuses previously released projection on other XR ticks. `vrhost/src/runtime/r32_direct_submit.hpp::CanFastSubmit:426-468;::EndFrame:552-613` checks the verified DirectGPU bundle and actual projected frame; a passing fast submit arms `ArmConsumptionFence`, submits the existing projection once through `OutRunVrFinalTest::EndFrame`, and later polls/ACKs the producer event. `::ArmConsumptionFence:315-404` deliberately avoids redundant EVENT arm on the same pending frame, and `Flush()` only escalates when the exact slot remains blocked (`:370-389`). Thus an 8ms *synchronous* R32 SafeEye copy timeout must **not** be booked as a default cost on every successful R32 fast-submit XR tick.
6. **R32 SafeEye A/B is a distinguishable safety fallback, not unconditional hot path.** `vrhost/src/runtime/r32_direct_submit.hpp::EndFrame:601-613` falls through to R26/R24 when fast eligibility or ACK arm fails, where the safety composition chain may need the R32 SafeEye route. `vrhost/src/runtime/d3d9ex_direct_passthrough_r32.hpp::R32OpenSharedSlot:111-207` matches slot+transport/run/PID/handles/size/format/device; miss reopens and validates **both** shared eyes. `::R32EnsureInactiveEyes:211-250` independently reuses an inactive pair when size+format+device are equal, regardless of transport generation. `::CopySharedFrameToSafeEyesR32:253-320` copies to inactive eyes and swaps active/inactive plus `SafeFrameId` only after GPU completion and `PublishCompletedFrame`; `vrhost/src/runtime/d3d9ex_direct_passthrough.hpp::CopyFenceTimeoutMs:27-32;::WaitForCopyFence:501-541` uses a bounded 8ms synchronous EVENT/Flush/GetData loop **for this path**. On timeout old active SafeEye is preserved, not proven a display refresh. `::R32SyncDirectDeviceOwner:91-107` retires stale caches on device/context rebind.
7. **Two-step realloc boundary is conditional.** For a fallback that actually swaps an A/B pair from size X to Y, first `R32EnsureInactiveEyes` may allocate Y while active SafeEye remains X; the successful swap moves the previous active X into the inactive position. The **next** accepted Y fallback can allocate the now-mismatched inactive X as Y. After both pairs match Y and the device is stable, repeated same-size fallback copies should reuse both pairs, not allocate each frame. If producer transport generation changes G1→G2 with the **same** width/height/format/device, the per-slot shared handles may reopen while the inactive allocation check still passes. These are control-flow implications, not measured allocation counts. If one eye copy/ACK fails, swap does not occur and the inferred two-step sequence is not assured.
8. **Present/OpenXR and reported timings.** `vrhost/src/main_r23.cpp:3237-3288,3292-3385,3562-3580` separately tracks candidate R23 commit work, fresh/cached projection and final `xrEndFrame`; R32 fast/fallback counters discriminate actual final submission. Historical `docs/automation/reviews/DX9EX_FRAME_DROP_ROOT_CAUSE_TRIAGE_20261010.md:1-53` describes *older builds* with Present spikes and DirectGPU `fenceTimeout=0` in two recordings, which is neither an October-21 runtime sample nor an argument that today's R23/fallback allocation path is bottleneck-free. Issue #6 is a historical review inbox rather than a new hardware observation.
