## NEW_FINDING

NEW_FINDING=STATIC_CONDITIONAL_R24_MIXED_NONPROJECTION_FALLBACK_BYPASSES_FINAL_SUBMISSION_RECEIPT_AND_CAN_LEAVE_STALE_PREVIOUS_PROJECTION_FRAME_ID_KIND_LAYER; HMD_LENS_DOUBLE_FLARE_HEAD_LOCK_DEPTH_ROOT_CAUSE=UNPROVEN.

1. `vrhost/src/runtime/r24_black_screen_guard.hpp::EndFrame:585-636` identifies an incoming mixed frame when `hasNonProjection` and `projection.count==1`. Only the `exactBundle && ClassicSbs && ProjectionMatchesSnapshot` branch at :618-633 submits the incoming mixed frame with `RecordFinalSubmissionResult(result, verified.frameId, verified.kind, true)`. When that exact validation fails, `:635-636` instead returns `OutRunVrR23RuntimeHardening::SubmitNonProjectionOnly(session,endInfo)` *without* any receipt update.
2. `vrhost/src/runtime/r23_runtime_hardening.hpp::SubmitNonProjectionOnly:105-128` filters out projection layers, builds `safe.layerCount=count`, then calls `OutRunVrFinalTest::EndFrame(session,&safe)` directly. It does not call `RecordFinalSubmission` or `RecordFinalSubmissionResult`. The helper itself is intentionally a low-level submission helper; this is a diagnostic receipt gap in this particular R24 caller, not proof the fallback image is wrong.
3. `r23_runtime_hardening.hpp:36-53` defines process-global `LastSubmittedFrameId`, `LastSubmittedKind`, `LastSubmittedLayer` and changes them only when `RecordFinalSubmission` is invoked. No automatic per-tick reset occurs in that function. `r24_black_screen_guard.hpp:479-575` *does* record the final receipt for ordinary visible/no-layer fallbacks; the mixed early-return is a separate uncovered branch.
4. `vrhost/src/runtime/r26_recenter_hardening.hpp::EndFrame:565-624` delegates to R24 and returns its result without synthesizing a new R23 final receipt. `vrhost/src/runtime/r32_direct_submit.hpp::EndFrame:550-612` likewise delegates to R26 on the non-fast path. Thus these wrappers do not repair the uncovered mixed fallback.
5. `vrhost/src/main_r23.cpp:3873-3892` invokes the wrapped `xrEndFrame`, then reads `LastSubmittedFrameId/Kind/Layer` and calls `R23Pixels.NoteFinalSubmission`. `:3893-3950` reports these as `XR FRAME FULL actualFrameId/actualSourceKind/actualLayer`. `R23AsyncPixelProbe::NoteFinalSubmission:1037-1052` can set `finalSubmissionKnown/finalSubmitted` from the same stale triple if a pending grid probe's frame/kind happen to match the *previous* receipt. Neither log alone proves that the current XR tick submitted a projection image.
6. Constructive **static only** counterexample: tick A successfully submits ClassicSbs projection frame 41 and records `(41,ClassicSbs,true)`; tick B supplies one projection plus one quad, but its projection fails exact-bundle validation. R24 submits only the quad successfully through `SubmitNonProjectionOnly`; the three atomics remain `(41,ClassicSbs,true)`. The tick-B `XR FRAME FULL` can therefore report `actualFrameId=41 actualLayer=1` although tick B submitted **no projection layer**. If an eligible pending probe was tagged frame 41/ClassicSbs, `NoteFinalSubmission` may incorrectly mark it known/submitted on tick B.
7. **Reachability boundary:** ordinary `main_r23.cpp:3859-3863` constructs at most ONE requested layer (`end.layerCount=layerReady?1:0`). This mixed-frame counterexample therefore requires a different/mutated mixed-layer caller; this review does NOT claim that it occurs in normal Quest3 gameplay, nor that stale atomics alter actual pixels. It only refutes universal authority of these final-submission fields on the supported mixed-layer fallback path.
8. This is independent of 1204: even with an otherwise correct fresh-frame sample identity, a current mixed fallback can leave a stale final receipt. Conversely, the 1204 prepublication mislabel exists without any mixed layers. The two diagnostic hazards must be quarantined separately before attributing C993/CABE flare pixels to an XR tick.
