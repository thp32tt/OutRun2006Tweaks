Therefore the c64 upload may occur while the **previous PMT vertex shader S_old** is still bound. This order holds for both opaque pass 0 and alpha pass 1 in this reconstruction.
2. In the same original source, `draw_404700:788-798` only later calls `shader_410680(shader)` at :792, whose :726-733 calls `d.set_vertex_shader(r.vertex_shader)` at :729, then sets indices/material and finally attempts native DIP at :798 (if `stride==declaration_size`). `material_408c80` may change other shader constants, but no intervening **world c64** write is shown in this normal `load_matrices -> shader_410680 -> DIP` sequence. A PMT shader change is conditional; identical shader bindings do not advance the mod epoch.
3. The current DX9Ex `src/vr/game/outrun_renderer.cpp::RecordGameWvpWrite:1666-1710` captures `GetCurrentShaderEpoch(shaderIdentity,shaderSerial)` at :1674-1681 and stamps the original/raw c64 with the **shader active at the moment of c64 upload** at :1690-1691. If no shader is tracked, the record is invalidated; if S_old is valid, the raw matrix is stamped S_old. `src/vr/d3d9/stereo_renderer_r7.inc::SetVertexShaderDest:1695` advances `CurrentVertexShaderIdentity` and `VertexShaderSerial` only after a successful change to S_new; `GetCurrentShaderEpoch:1956` reads that epoch. It does not rewrite/relabel the prior c64 record.
4. At the later **same physical** R30 draw, `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::R30GetExtendedRawWvpForExactSceneEffect:1977-2001` and `R44GetOwnedRawOverlayWvp:2003-2043` demand `writeShader==currentShader && writeShaderSerial==currentShaderSerial`. Under the specific sequence `c64(S_old)->SetVertexShader(S_new != S_old)->DIP(S_new)`, with no second recorded c64 upload, both getters return false **even though the D3D9 c64 registers still contain the original game's intended WVP**. This is a *source-proven false-negative possibility in the mod's provenance admission*, not proof that the game rendered a wrong matrix or extra primitive.
5. For a deferred first `0x570008` whose physical scope inherits `SceneEffect` under the conditional 40BE70 wrapper, `R30ClassifyScreenSpacePass:2361-2392` requires these raw helpers before it can classify WorldBillboard/PerspectiveHud. The pre-bind epoch mismatch can cause `None` and normal lower R26/R23 fallback, rather than a successful R30 spatial-eye correction. For a projected-scope second `0x570008` or C993 family, `R30BuildScreenSpaceEyeConstants:5030-5074` similarly requires owned original c64; a mismatch can reject the per-eye build after a projected class was selected. **This gate can affect either ordinal**; no claim that the first necessarily changes shader or that the second necessarily passes.
6. A *positive control* is a real original shader transition at the 405890 PMT boundary with matrix reload and no subsequent complete c64 write: record `shaderAtC64=S_old`, `shaderAtNative=S_new`, `writeEpoch!=drawEpoch`, `rawGetter=MISS`, physical native Draw eligible. A *negative control* is S_old==S_new, or another successful complete c64 write after shader bind, in which case this particular mismatch disappears. Another negative control is a matrix-cache hit at `load_matrices` with **no** new c64 write: it is not this pre-bind stamping sequence and must be investigated under earlier source-age/owner hypotheses.
7. This does NOT prove the same source mesh was rasterized twice in one eye, head-lock, incorrect binocular depth, or host OpenXR duplication.
