## REVIEW_SCOPE

## SOURCE → SEMANTIC → QUEUE → ACTUAL DRAW → PRESENT / XR (STATIC, CONDITIONAL)

1. Checked-in original REA evidence: six +TIME E8 producers enter three animation and three text/number callees; GOAL/result may route through original 0x449050 -> 0x42D710 SpriteNode consumer. Four proven original exits remain separate: type0 D3DX (0x42A0A0), type0 direct UP (0x42C0F0), type1 quad (0x42A3A0), type1 masked/composite (0x42A800). REA queue inventory still includes 36 unresolved CALLs. No executable REA run or original binary disassembly was performed here.
2. The game producer/scope and queue node/epoch become an immutable PhysicalDrawCommand only at actual native DP/DIP/UP. For a deferred D3DX Begin/Draw, the exact homogeneous proven +TIME/GOAL GPU owner may be restored at physical Flush/End; mixed/foreign/unknown/queued batches do not borrow a direct producer.
3. Before actual draw, a game's MANAGED 2D texture can use R13 translated DEFAULT|DYNAMIC direct-lockable tracking or R14 SYSTEMMEM shadow, depending on real CreateTexture/desc/hooks/registry success. R14ShadowEntry retains an AddRef on its IDirect3DDevice9, a CPU texture reference, but only an identity pointer for the GPU texture. It is removed on final observed GPU Texture::Release==0, not merely on a CPU shadow retirement.
4. **Conditional different-device adoption:** R14AdoptCompatDevice snapshots entries for prior R14RegistryDevice and sets the new registry identity. Entries with no outstanding locks immediately detach CPU shadow; locked entries set retirePending=true but retain CPU backing so the matching Unlock can find them. R14's per-entry COM device AddRef prevents an old device from reaching zero solely due to the wrapper's outer Release while those entries remain registered.
5. **Ordering:** For an old-generation *writable* shadow with retirePending=true, TextureUnlockRectR14 and its R15 replacement first call CPU UnlockRect, clear the locked bit, then (if unlock succeeded, no overlapping external write and not read-only) invoke R14UploadLevel/R15UploadLevel on entry.device + entry.gpu. Only **after that upload attempt** do they test retirePending && lockedMask==0 and R14DetachShadowLocked. Thus the code does not skip an old-generation upload merely because replacement already marked retirement. When multiple mips remain locked, another outgoing old-device upload is possible per successful writable Unlock before the last Unlock retires. A read-only Unlock, CPU Unlock failure, or externalWriteDuringLock suppresses that upload. This is a confirmed source-level operation order; neither a reproduced crash nor an actual frame cost.
6. External GPU writes while a CPU lock is active set externalWriteDuringLock and retirePending; corresponding Unlock returns an invalid-call result instead of uploading stale CPU pixels, then detaches on the final lock. This policy is **different from replacement-only retirePending**, for which externalWriteDuringLock is not set.
7. The potential old-generation upload would happen before its content could be sampled by native physical draws or after it was already superseded, depending on unobserved timing. D3DX Flush/End, R30 external F11 ImGui precedence, R62 fixed-function candidate, XYZRHW/R29 fallback, R13 single-execution/occlusion, R9 mono-shadow and R7 native left/right draw must each be proven from callback HRESULT/query/device identity, not inferred from texture upload. After draw the independent RT0..N/depth/stencil/viewport/StateBlock restore, game Present R9 full stereo/SBS vs mono fallback and x64 host actual xrEndFrame layerCount/frameId/fresh-vs-cached projection remain terminal validation gates.
8. **Reachability guard:** core InstallManagedResourceCompat rejects a different new Ex pointer while a previous CompatDevice owner is live, *before* the R14 installer can adopt it. A first failed R15 baseline capture ordinarily occurs before the Ex device is exposed to game code, so there is no proof that game-created locked R14 shadows exist at that failure boundary. R14 replacement+locked-shadow requires a separately demonstrated valid lifecycle (e.g. cleared old owner plus still-live registered resources); otherwise the path may be unreachable in real OutRun play.

## NEW_FINDING / REFUTATION

- NEW_FINDING=CONFIRMED_STATIC_R14_R15_WRITABLE_UNLOCK_UPLOAD_PRECEDES_RETIRE_PENDING_DETACH_ON_DEVICE_REPLACEMENT.
- FACT: R14AdoptCompatDevice sets retirePending on still-locked prior-device shadow entries, without setting externalWriteDuringLock. Both R14/R15 Unlock implementations can still upload the final old CPU write to the prior GPU/device before retiring the shadow.
- HYPOTHESIS (NOT PROVED): Under actual admitted replacement while old shadow remains locked, this may add needless UpdateSurface/Lock/Unlock/driver synchronization during a frame transition and may complicate resource/refcount lifetime, device-loss and presentation pacing. It is **not** proof of visual corruption, leak, double Draw, HMD failure or lower FPS.
- CONTRARY CONDITIONS / REFUTATION: normal core owner veto may prevent all cross-device adoption; the first R15 rejected device may have no R14 textures; old locks may always drain before replacement; pending locks may be read-only; already-in-flight old-device writes may be contractually required; no native UpdateSurface may occur if no actual writable tracked texture. If same-build traces never show old-generation R14Adopt + pending lock + writable Unlock, practical concern is falsified; if they do, no measurable GPU stall/lifetime violation with valid L/R/HMD would falsify the performance-risk hypothesis.
