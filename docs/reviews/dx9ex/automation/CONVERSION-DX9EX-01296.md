## REVIEW_SCOPE

Independent physical **scissor-rectangle lifetime / eye-RT state boundary** for R62 fixed-function `D3DFVF_XYZ|DIFFUSE|TEX1` D3DX Sprite indexed quads in R26+HUD, especially exact +TIME/result HUD and scoped projected markers. Unlike 01290-01295's indexed-buffer admission, primitive family, MaxPrimitiveCount/MaxVertexIndex or 01289's type-1 source/XR extent attribution, ask whether successful left-eye R62 draw can be followed by an **implicitly reset D3D9 scissor rectangle** during right-eye render-target transition and original-target restore, without preservation of the caller's scissor state. This is **not** an observation that the actual game has scissor enabled for R62 result HUD. Do not infer shader/owner from producer tags alone.

2. **R62 physical owner and scoped guard (FACT).** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5379-5460` first offers F11 `R30TryExternalImGuiIndexed`, then `R62TryFixedFunctionSpriteIndexed:5126-5347`, then R30 indexed XYZRHW shadow, then R29/native. R62 admits only TRIANGLELIST, backbuffer, R30 safe stereo base, corroborated ProjectedWorldMarker or HUD semantic, live null vertex shader, FVF `0x142`, stereo eye/pose, finite projections and related gates. It builds per-eye projection matrices at ~5200-5273. `drawEye` at ~5275-5288 sets `D3DTS_PROJECTION` and makes the actual `DrawIndexedPrimitiveHook` call for both eyes. After stereo it restores **projection** at ~5295-5307, but this inspected R62 function does not capture, transform, apply or restore `GetScissorRect`/`SetScissorRect` or read `D3DRS_SCISSORTESTENABLE`.
3. **Left -> right -> restore boundary (FACT).** `::R30ExecuteXyzrhwStereo:3829-3944` first runs leftDraw, then inside `InternalPassScope` invokes original `SetRenderTargetHook(device,0,RightEyeSurface)`, switches right depth, `SetViewport(state.viewport)`, executes rightDraw if setup succeeds, and invokes `RestoreRightPassState(device,savedRt,savedDepth,state.viewport,nullptr,false)`. The common implementation is in `src/vr/d3d9/stereo_renderer_r7.inc:1462`: restore original RT, depth, viewport and optional WVP only; **no scissor rectangle restore**. Even when all HRESULTs are successful, there is no explicit scissor-equivalence postcondition in this R62/R30 execution chain.
4. **Official D3D9 API semantics (FACT).** Microsoft Learn's `Scissor Test (Direct3D 9)` states `IDirect3DDevice9::SetRenderTarget` resets the scissor rectangle to the full render target and that `D3DRS_SCISSORTESTENABLE` controls whether outside pixels are culled: https://learn.microsoft.com/en-us/windows/win32/direct3d9/scissor-test . `IDirect3DDevice9::SetScissorRect` specifies that the RECT is a clipping region within the render target: https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-setscissorrect . `Viewports and Clipping` independently specifies viewport coordinates and projective mapping: https://learn.microsoft.com/en-us/windows/win32/direct3d9/viewports-and-clipping . Thus restoring a viewport/projection is **not equivalent** to restoring scissor.
5. **Independent in-tree negative/control cases (FACT).** The separate F11 `R30PrepareExternalImGuiProjection:2800-2940` explicitly reads enabled scissor and stock RECT, computes per-eye RECTs from transformed projection because untranslated scissor clips shifted glyphs, and `R30TryExternalImGuiIndexed:~2950-3060` calls `SetScissorRect(&eyeScissors[eye])` for both eyes and restores `stockScissor` *after* `RestoreRightPassState`. Its earlier priority is not proof that a given R62 HUD goes through F11. The separate R22 raster replay source `src/vr/d3d9/stereo_renderer_r22.cpp:280-334` captures/explicitly restores scissor + enable and cannot be assumed to decorate the R62 calls. These control paths make the R62-specific absence bounded, not a claim that all stereo rendering lacks scissor recovery.
6. **Conditional state simulation (INFERENCE, NOT runtime trace).** Assume `R62TryFixedFunctionSpriteIndexed` passes its gates, a stable preexisting right-eye resource allocation, original RT size 1920x1080, `D3DRS_SCISSORTESTENABLE=TRUE` and initial scissor `{left=100,top=100,right=500,bottom=300}`. R62's left physical DIP sees the caller's restricted rectangle. The successful right RT bind implicitly replaces the scissor rectangle with full right RT; right DIP can therefore render pixels outside the original clipped region, even with matching viewport. The subsequent successful bind to the saved RT again resets the scissor and the common restore does not reapply `{100,100,500,300}`. A later game draw *without its own scissor/stateblock reset* can inherit widened scissor on the left. This is a deterministic **D3D9-state-contract conditional**, not proof of actual OutRun 1920x1080, scissor usage, driver result, or HMD artifact. If scissor is disabled, a full-RT rectangle, initial allocation changes state before R62, or D3DX/stateblock reapplies it before use, the visible hypothesis may be falsified or masked.
7. **Restore / Present / OpenXR does not certify pixel correctness (FACT).** `R30ExecuteXyzrhwStereo:3829-3944` poisons on failed left/right HRESULT or restore, but a successful RT/viewport/projection return does not compare the original scissor. `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:685-823` gates stereo on seeded/world/dual-eye/pose/no-poison resources, then resolves DirectGPU or ComposeSbs, has mono/fallback, publishes only after normalized Present success and resets epoch. It has no scissor equivalence pixel check. Host `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` consumes source to two D3D11 projection swapchain eyes, and `vrhost/src/main_r23.cpp:3569-3589` calls real `xrEndFrame`. Correct color content in both eye textures and an exact Quest3 observation remain unproven.
