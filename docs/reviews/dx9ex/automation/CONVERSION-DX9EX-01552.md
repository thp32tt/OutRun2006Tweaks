## Independent source-logic falsification / NEW_FINDING

NEW_FINDING=STATIC_COUNTEREXAMPLE: R30 lens `resetViewportMatchesPre=1` does NOT imply the reset viewport and the pre-physical-draw viewport have the same origin; the predicate checks only Width/Height and nonzero resetSerial, omitting recorded X/Y and explicit ResetSucceeded/ViewportValid flags. This is a diagnostic false-positive possibility, NOT proof of flare duplication, head-lock, actual viewport mismatch, failed HMD rendering, or optical root cause.

1. New commits on this branch build a read-only evidence chain: `8e8527135dad80732cb49e629a183d50f9d6318b` introduced `reset_trace.hpp`; subsequent ResetEx publisher in `ex_device_upgrade.cpp` records requested/effective/actual extent and actual viewport (including X,Y), scissor, flags; `119fbe764d0293ddaa6b0af497d09733af004e3c` samples that snapshot at R30 lens physical-eye entry, and `b8e86d17ecac0740f21749f2d83efc41065ce295` tags original C993/CABE source calls with reset epoch/QPC/flags. Earlier 01551 did not have this post-commit predicate.
2. `ex_device_upgrade.cpp::ResetCompatDest:459-587`: `NextResetSerial` is called on the compat Ex path before ResetEx; after ResetEx, it records `ResetSucceeded`, `PreserveXrPhysical`, `ClassicReplaySucceeded`, `BackBufferValid`, `ViewportValid`, and `ScissorValid` as individually conditional flags, reads `GetViewport` and `GetScissorRect` only following successful ResetEx, then `Publish(trace)`. Preserve does not guarantee success, and the last Reset snapshot alone is not the viewport at any subsequent flare draw.
3. `stereo_renderer_r30_r26_safe.cpp::R30TryScreenSpaceFovDraw:6207-6226`: `GetViewport(&savedViewport)` precedes the physical left/right draw. For `lensPhysicalCandidate`, a separate `D3D9ResetTrace::Read()` and `GetScissorRect` sample occur there, not at original source-call time. `:6380-6440` logs both preViewport X/Y/Width/Height and the resetViewport Width/Height, but `resetViewportMatchesPre` evaluates only `resetSerial != 0 && reset.viewportWidth == savedViewport.Width && reset.viewportHeight == savedViewport.Height`. It does not compare `reset.viewportX/Y` with `savedViewport.X/Y`, despite both being available in the traced struct.
4. CONSTRUCTIVE NEGATIVE CONTROL (synthetic source-logic test, not Quest3 observation): a previous successful Reset recorded viewport (X=0,Y=0,W=1200,H=900), valid flags, resetSerial=7. The original game or intervening state code later sets pre-flare viewport (X=64,Y=0,W=1200,H=900). `resetViewportMatchesPre=1` by the exact predicate even though origins differ. The metric may falsely support \"unchanged viewport from Reset to flare\". This matters for a screen-positioned centre C993/halo candidate, but the synthetic coordinates do not prove that such a state transition exists in the game.
5. POSITIVE CONTROL: same resetSerial=7, valid success/viewport flags, pre-flare viewport (0,0,1200,900), and matching scissor imply a complete *sampled viewport-rectangle* match only for those sampled states; do not infer per-eye texture/geometry/projection identity. In particular the first CABE may drain at the original 4052C0 queue boundary after the source wrapper, so same epoch does not resolve deferred ownership.
7. `reset_trace.hpp:63-127`: generation-based read explicitly retries four times then returns a zero-initialized Snapshot, with no separate read-valid bit. Further conditional risk: two concurrent `Publish` callers are not serialized by `Generation.fetch_add`; their two begin increments can make Generation even while both writers are active. No evidence confirms simultaneous Reset calls; this is a conditional telemetry integrity caveat, not asserted to have occurred or to cause an image error.
8. Therefore no two-eye physical draw or OpenXR pose is proven duplicated solely by resetViewportMatchesPre.
