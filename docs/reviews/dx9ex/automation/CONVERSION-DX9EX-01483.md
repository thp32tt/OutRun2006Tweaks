## REVIEW_SCOPE — startup source geometry through actual GPU/OpenXR boundary

R23 host publishes OpenXR allocated per-eye width/height, HostAlive/PID and QPC into legacy host pose and the v3 HostState shadow -> original game configuration hook reads HostState.v3 -> optional manual/-width override or UnifiedEyeMenuSource/AutoRenderResolution chooses game source BEFORE 640x480-to-source 2D UI scale -> game creates D3D9Ex device (alternate zero-wait XR extent choice under non-unified mode) -> +TIME/GOAL/selector original producers/0x00449050 scheduler/0x0042D710 SpriteNode queue -> type-0 D3DX Begin/Draw/Flush/End or direct-UP and type-1 quad/masked composite -> semantic/queue/physical D3D9 Draw, R30/R62 ScreenHud and world R7/R33 left/right RT/depth/viewport/WVP, restores -> D3D9 game Present/Frame.v2/DirectGPU or SBS -> R23 D3D11 projection eye array slices or theater/local fallback -> actual R24 xrEndFrame. **No original GPU frame or OpenXR pixels were observed**; upstream dimensions are not a physical stereo draw receipt.

Specific question: can a *still-running* but no-longer-updating XR host (or a reused OS PID) cause original game startup to admit an older recommended extent because HostState is coherent and HostAlive/PID liveness passes, while the writer's sampleQpc is stale?

## EVIDENCE — current SHA-pinned code (facts, not measured symptoms)

1. `src/vr/ipc/protocol_v3.hpp:37-65,72-100` defines HostState with `hostPid`, `flags`, `sampleQpc`, `referenceSpaceGeneration` and two recommended widths/heights. `src/vr/ipc/host_state_v3_reader.hpp:11-25,38-43` performs a stable seqlock/header read; its HeaderValid tests magic/version/size, not sample freshness, host process identity creation epoch or current XR session. This is a good anti-tearing gate, not a liveness or freshness guarantee.
2. `src/vr/ipc/host_process_liveness.hpp:7-20` calls `OpenProcess(SYNCHRONIZE)` and `WaitForSingleObject(process,0)`, returning alive for WAIT_TIMEOUT. A valid hung/stalled process still has an unsignaled process handle; the source does not check when it last published XR eye extent. PID reuse is a *separate possible* lifetime alias, not proven to occur.
3. `src/vr/ipc/xr_eye_extent.hpp:36-74` validates equal L/R sizes and numeric limits, then `ResolveStartupForLiveHost` requires only `flaggedAlive`, nonzero hostPid, valid numeric extent and positive `livePidProbe(hostPid)`. Its inputs include **no sampleQpc, heartbeat, XR session generation or host creation time**.
4. `src/hooks_misc.cpp:832-845,847-905` preserves manual and command-line dimensions. Under AutoRenderResolution/PreferD3D9Ex it requests host startup and samples HostState inside a zero-/1250-ms bounded startup poll. A passing `ResolveStartupForLiveHost` immediately sets `Game::screen_resolution` and windowed mode at lines 885-894, **before logical UI scale initialization**; an older but valid-looking host state can end the poll immediately. The 1250-ms wait is for availability, not age validation.
5. `src/vr/d3d9/ex_device_upgrade.cpp:75-109,856-889` reuses precisely the same `ResolveStartupForLiveHost` predicate for its non-unified D3D9Ex CreateDevice resolution route and adds device-caps checks. The code explicitly disables this later resize in UnifiedEyeMenuSource/FollowGameResolution or with a manual/explicit size; do not claim both game config and CreateDevice resizes happen in one unified launch.
6. `src/vr/settings.cpp:48-67` currently defaults `VRUnifiedEyeMenuSource=true`, `VRFollowGameResolution=false`, `VRAutoRenderResolution=true`, `RenderWidth/Height=0`. This makes the pre-UI-scale route relevant when VR/D3D9Ex eligibility holds, but an actual user's launch flags, INI, host readiness, game config and measured source extent are unknown.
7. `vrhost/src/main.cpp:450-471` explicitly records `sampleQpc` and exact allocated L/R eye extents at startup, before the game D3D9 HWND exists. Thus the clock datum exists on the producer side. Separately `src/vr/game/outrun_renderer.cpp:799-832` rejects stale **runtime pose** via `sampleQpc` age; that later guard is not invoked by the startup extent resolver, and a stale startup dimension should not be characterized as an accepted stale head pose.
8. `src/vr/d3d9/stereo_renderer_r7.inc:1300-1340,1521-1560,1685-1744` independently validates direct target dimensions/current eye resources, physical stereo draw and game Present publication. `vrhost/src/main_r23.cpp:1440-1513,3559-3593` still renders and submits two final projection slices subject to its own source, pose and XR gates. None makes the original pre-UI-scale size selection retrospectively fresh. Archived `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:19-32` confirms original four SpriteNode routes but is NOT newly acquired REA.

- NEW_FINDING=STARTUP_XR_EYE_EXTENT_ACCEPTS_HEADER_VALID_HOSTSTATE_FROM_OS_LIVE_BUT_STALLED_HOST_WITHOUT_SAMPLE_QPC_AGE_OR_SESSION_PROOF.
- STATIC_CONFIRMED=Both startup consumers require a coherent v3 HostState snapshot, `HostAlive`, live process PID and numeric equal extents, but they never check `HostState.sampleQpc` or a host-start/session generation at extent admission. A still-alive writer that stopped updating can therefore satisfy these checks using an earlier valid published extent. This does not mean an ordinary healthy host supplies the wrong extent.
- HYPOTHESIS_ONLY=If the host is stalled long enough after publishing old eye dimensions and before/during a new game launch (or a PID is reassigned after crash), the game may lock an obsolete physical D3D9 source before creating the menu/HUD source coordinate scale; a later recovered host/current XR swapchain could use another extent. Symptoms *could* include mismatched menu source density/rescaling, copies and frame cost, but this does not prove user-reported duplicated GOAL glyphs, head-follow, stereo failure or 3440x1440 desktop dependence. An unchanged XR allocated extent may make the stale record harmless.
- FALSIFIERS=Show that every admitted HostState has a newly published sampleQpc and correct producer identity during actual launch, or that a host stall always terminates its PID before startup, or that post-recovery XR extent equals admitted game extent and all menu/race pixels are correct; any of these defeats the hypothesized stale-extent output defect. Also compare explicit -width/-height, paired manual RenderWidth/Height, FollowGameResolution and disabled VR modes, which avoid the auto admission path.
