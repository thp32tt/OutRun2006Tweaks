## NEW_FINDING — precisely bounded and falsifiable

- **Confirmed static fact:** application recenter can assign a new LOCAL handle/generation, whereas gameplay projection cache reuse sends existing projection view poses/FOVs as if they were authored relative to the currently supplied `projection.space`. Existing runtime-reference-change/session-stop invalidation is a separate event path.
- **Conditional path to test, not an observed incident:** old LOCAL L0 and frame F0 generate and release L/R images whose `cachedProjectionViews` were authored in L0. F10 or focus recenter succeeds and replaces `localSpace` with L1; no new eligible producer Frame.v2 arrives and no runtime LOCAL-change event clears the cache. R42 picks `projection-cached`, attaches the L0-authored view poses to L1, and calls `xrEndFrame`. Because the basis changed, head/world placement *might* transiently shift relative to intended recenter origin. Source code alone does not establish that all required predicates coincide on Quest3/VDXR, that the runtime accepts the unchanged layer geometry in a visually erroneous way, or that every normal head movement needs a cache refresh.
- **Falsification / contrary controls:** R46 recenter always causes a relevant runtime LOCAL event handled before cached submission; verified application recenter is always followed by a fresh eligible frame and successful pair render before `xrEndFrame`; an interception/compositor transform demonstrably rebases saved poses from L0 to L1; unchanged layer image/pose is legal and desired under the same LOCAL origin; recenter request rejected or pending, `shouldRender=false`, gameplay exits, session stops, or exact deployed build differs. Capture exact PID, request ID, R46 success/generation, old/new `XrSpace`, `sourcePoseSequence`, source frameId, cached pair owner and view poses/FOV, live `xrLocateViews`, `XR_TYPE_EVENT_DATA_REFERENCE_SPACE_CHANGE_PENDING`, final layer space/poses, each eye draw/release HRESULT, xrEndFrame status and two-eye HMD image before classifying optical failure.
- **Critical distinction:** merely holding old eye pose after ordinary head rotation/translation is not this finding; keeping the rendering-time pose can be required for correct OpenXR reprojection. The proposed risk requires *different LOCAL coordinate bases without a proven pose conversion*.
