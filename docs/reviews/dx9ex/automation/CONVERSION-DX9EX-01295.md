## EVIDENCE — checked-in GitHub code, REA and Microsoft D3D9 API

1. **Original producer != physical index format.** At pinned `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:1-45`, original game EXE SHA256 is `68ceb386829066f8455b9d027320af962584321f3e2e8a79c72841495a6134c3`. The 0x42D710 queue has distinct type-0 D3DX Draw 0x42A0A0, type-0 direct UP 0x42C0F0, type-1 quad 0x42A3A0, and type-1 mask/composite 0x42A800, plus 36 unresolved indirect calls. Thus the REA alone supplies neither a proven real INDEX32 DIP nor a MaxVertexIndex-sensitive physical call. `src/vr/game/render_semantics.hpp::SelectSpriteQueueNode:1789-1837` uses queue-epoch/canonical node scope; `src/hooks_uiscaling.cpp::VRHudQueueSemanticBridge:4154-4200` and `src/hooks_textures.cpp::TagDirectVrSpriteNodes:1017-1115` tag producers but do not establish final API. R64 D3DXSprite batch Draw/Flush/End may submit later.
2. **DIP indexed-VB owner and local arithmetic.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5379-5460` tries F11 external ImGui, R62 fixed-function D3DXSprite and only then `R30TryXyzrhwIndexedPrimitiveVB:4236-4500`, falling through to R29/native when R30 returns `E_NOTIMPL`. The VB candidate accepts an IB with `D3DFMT_INDEX16` **or** `D3DFMT_INDEX32` after `GetDesc` (~4270-4300). It bounds IB bytes, copies shadow indices, computes signed `physical=baseVertexIndex+raw`, rejects negative / >UINT_MAX, bounds the *compacted physical span* at 262144, and confirms VB shadow bytes (~4300-4385). It never consults `D3DCAPS9::MaxVertexIndex` before shadow-copy, transform and two native indexed-UP eye closures (~4455-4500). This is an inspected **lack of explicit preflight**, not a claim that the D3D9 driver permits an unsupported buffer.
3. **INDEX16 versus INDEX32 are materially different.** The indexed-VB path preserves the index format while rebasing: INDEX16 maps local indices after `minPhysical`, rejecting local >65535; INDEX32 copies 32-bit rebased local indices. With INDEX16, `maxRaw-minRaw<=65535`, hence a constant signed base cannot produce a larger compacted range than 65536; a MaxVertices=262144 overflow for a correctly captured INDEX16 span is not reachable solely by index spread. With INDEX32, distinct valid shadow indices such as `{0,1,65536}` have `vertexCount=65537` and satisfy the inspected scratch limits if backing VB/IB and all state gates qualify. A `TRIANGLELIST`, primitiveCount=1, base=0, INDEX32 index triplet `{0,1,65536}`, stride=24 has three indices and 1,572,888 source bytes for the compacted VB window, below 4 MiB; it is a **synthetic eligibility example** only. Its observed hardware draw acceptance and memory behavior are unknown.
4. **Separate indexed-UP path is not identical to 32-bit index-buffer usage.** `::DrawIndexedPrimitiveUPDestR30:5480-5525` tries `R30TryXyzrhwIndexedPrimitiveUP:3994-4118`, whose `r30_indexed_up_bounds.hpp:4-30` requires declared `minVertexIndex+numVertices<=262144`, valid 16/32-bit format, and *every* raw index in its declared window. It optionally copies/rebases indices, transforms used vertices, then calls the native `DrawIndexedPrimitiveUPHook` for L/R. This path does not bind an `IDirect3DIndexBuffer9`; do **not** naively apply a documented 32-bit **index-buffer** hardware restriction to UP memory pointers without separate source/API evidence. Conversely, its local window guard is not a GetDeviceCaps assertion.
5. **Official API contract / distinction.** Microsoft Learn `D3DCAPS9::MaxVertexIndex` describes the maximum index for hardware vertex processing, and explicitly warns that a 32-bit index buffer may be created yet cannot render using that buffer unless reported `MaxVertexIndex > 0x0000FFFF` (https://learn.microsoft.com/en-us/windows/win32/api/d3d9caps/ns-d3d9caps-d3dcaps9). Microsoft `CreateIndexBuffer` independently refers to `MaxVertexIndex` when determining index-buffer rendering validity (https://learn.microsoft.com/en-us/windows/win32/api/d3d9helper/nf-d3d9helper-idirect3ddevice9-createindexbuffer). `DrawIndexedPrimitive` defines `BaseVertexIndex`, `MinVertexIndex`, `NumVertices` and physical indexed-stream semantics (https://learn.microsoft.com/en-us/windows/win32/api/d3d9helper/nf-d3d9helper-idirect3ddevice9-drawindexedprimitive); `DrawIndexedPrimitiveUP` is an **index-pointer** API with independently specified Min/Num, accepts INDEX16/INDEX32 and is not itself proof of a bound index-buffer cap (https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-drawindexedprimitiveup). This hardware cap is a different predicate than 01294's `MaxPrimitiveCount==0xFFFF` unique-vertex constraint. Device-dependent software-vs-hardware vertex processing state remains unknown.
6. **Conditional synthetic cross-check, not reproducer.** Suppose a device reports `MaxVertexIndex==0x0000FFFF` with hardware vertex processing; an original DIP uses a 32-bit IB and a supported TRIANGLELIST. Per the referenced device-cap documentation, 32-bit IB render eligibility is not established. R30's inspected local acceptance does not check this cap, even if INDEX32 indices are small; later native `DrawIndexedPrimitiveUPHook` may accept or reject independently. Conversely, if actual `MaxVertexIndex>0xFFFF`, that specific 32-bit IB limitation does not apply, yet other driver/state bounds still apply. The source does not prove there is a broken real-game draw, and there is no evidence of which path the device actually takes.
7. **Stereo/restore/final-present simulation and limitations.** `::R30ExecuteXyzrhwStereo:3829-3944` calls the left physical draw first; a failed left HRESULT poisons/fallbacks before right. After left success, it switches right RT/depth/viewport, calls right, then restores tracked state; right/restore failure poisons. Indexed-VB wrapper restores stream-0 and IB after its UP eye calls (~4471-4500); direct indexed-UP does not have the same prior VB/IB binding ownership. `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:685-823` requires authoritative world + duplicated eyes + pose/resources and otherwise preserves guarded mono fallback; `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` and actual `xrEndFrame:3562-3635` own final eye projection and frame submission. A semantic tag, candidate success or Present log does not establish binocular user-visible pixels. Quest3/VDXR, hardware caps, exact physical index format, GPU HRESULT and performance counters were not measured.
8. **Baseline and novelty checks.** `AGENTS.md:1-10` and `CMakeLists.txt:97-108` select R26+HUD for new option-free builds (installed DLL/CMake cache unverified); protected baseline unchanged. Previous 01294 checked a *special primitive/unique-vertex count cap*; this pass checks the **separate INDEX32 index-buffer validity predicate and the distinction between IB and UP memory**. - **FACT:** inspected R30 indexed-VB candidate accepts INDEX32 IB from local GetDesc, bounds/counts and attempts a *replacement* indexed-UP path, without checking the live MaxVertexIndex capability. Official documentation limits 32-bit index-buffer rendering on devices whose cap is not greater than 0xFFFF. This is a capability-proof gap, **not** proof that R30 introduced a newly invalid GPU call or changed the original result.
- **HYPOTHESIS ONLY:** if an actually reached INDEX32 draw is unsupported by the live hardware cap yet accepted into R30 shadow/transform admission, the converter could pay avoidable CPU work before the native UP API responds; fallback/eye poisoning could depend on original versus replacement HRESULT. No synchronized original-vs-replacement result, real physical DIP or GPU timing exists.
- **FALSIFIERS / NEGATIVE CONTROLS:** actual hardware MaxVertexIndex > 0xFFFF; original game has no physical INDEX32 indexed-VB call; state is software vertex processing; F11/R62 owns the draw; missing IB/VB shadow or R30Prepare rejects first; original/native DIP and replacement DIPUP share HRESULT/pixels; no difference in per-eye/frame outcome; the UP memory API's format handling is independent of the 32-bit IB restriction. Do not infer a UP restriction from the buffer statement alone, and do not conflate this with 01294 unique-vertex sentinel.
