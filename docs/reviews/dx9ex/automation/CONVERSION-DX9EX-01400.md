- FACT: decoded index membership narrows which XYZRHW vertices are transformed, but not which bytes are copied: each accepted eye copies `numVertices*stride` from the declared window, and the per-eye size limit is applied to an already-multiplied `size_t` value. The independent `minVertexIndex*stride` guard does not prove that `numVertices*stride` fits on 32-bit. A sparse, overdeclared vertex window can therefore cause avoidable memory bandwidth; an abnormally large stride may defeat the intended 4 MiB bound on the 32-bit build. The code cannot establish caller backing-buffer length.
- HYPOTHESIS_ONLY: such a producer might lead to CPU memcpy overhead or invalid/aliased vertex access, potentially preceding any LEFT/RIGHT draw. None is attributed to sand, +TIME, result HUD or windshield without a physical draw fingerprint, and no actual game crash, HMD distortion or FPS drop has been measured.
- CONTRARY/FALSIFICATION: exact loaded x86 DLL/Win32 trace showing all admitted `numVertices*stride` products <=4 MiB **before** multiplication, acceptable caller buffer lengths, and small contiguous declared windows with dense referenced indices refutes the size-trigger and sparse-overhead hypotheses for those sessions. RIGHT draw or host presentation failure alone does not prove the copy mechanism.
