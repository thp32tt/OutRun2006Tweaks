4. **New game-eye allocation uses the XR extent, not desktop dimensions.** Host startup `vrhost/src/main_r23.cpp:2583-2636` uses both OpenXR view configs, calls `EyeExtent::ResolveHost`, publishes the common startup eye extent before the D3D9 game window, and verifies compositor allocation still equals startup. Game `src/vr/d3d9/stereo_renderer_r7.inc::DirectTransportTargetSize:1300-1350` reads two equal published eye sizes using a seqlock, calls `EyeExtent::ResolveGame` with D3D9 caps, and `EnsureDirectTransportResources:1353-1355` allocates **separate left/right 4-slot shared-eye textures**, selecting format/conversion and advancing direct resource generation. `src/vr/ipc/xr_eye_extent.hpp:30-43` explicitly **rejects**, rather than silently shrinks, any published extent above game texture caps. A genuine policy/caps mismatch therefore fails the DirectGPU eligibility path rather than quietly presenting lower-resolution ring descriptors. A transient four-attempt seqlock miss falls back to the current valid ring extent; this alone does not show a changed XR allocation in the same host session.
5. **DirectGPU copies are explicit and may scale between desktop source and XR eye sizes.** `stereo_renderer_r7.inc::ResolveDirectTransport:1357-1428` selects an eligible shared slot and `StretchDirectEye` copies the game left backbuffer/right eye surface into its target at the XR eye extent (linear filter first, point-filter fallback). On producer EVENT completion after native Present, `DirectTransportFrameReadyAfterPresent:1429-1454` controls publication; the 1 ms bounded wait avoids an unconditional flush, but does not prove acceptable 72 Hz pacing. This is a **potential sampling/blur diagnostic axis** when source and target sizes differ, not proof that a currently observed jagged HUD came from resizing. `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:693-811` requires completed world stereo, duplicated draw, valid pose/right eye and successful native Present for `StereoSbsActive`. `stereo_renderer_r7.inc::PublishRenderFrame:1491-1494` advertises the *DirectTransportWidth/Height* as `backbufferWidth/Height` for a direct-sized frame, alongside direct width/height, slot, both handles, format, generation and run generation. Thus `backbufferWidth` in **direct** Frame.v2 is the post-stretch eye texture extent, not necessarily the original D3D9 desktop backbuffer width.
6. **R23 has multiple positive identity/size gates for the new accepted source.** `vrhost/src/main_r23.cpp::R23UsableGameplayBootstrapFrame:205-250` checks completed flags and direct slot, handle, generation and width/height equality with Frame.v2 declared backbuffer dimensions. `::R23ValidateDirectResourceSize:1322-1397` requires producer PID/run-generation, both slot textures and declared dimensions, then compares physical D3D11 texture descriptors for **both eyes** including equal width/height/format/MSAA before caching the descriptor under a key containing slot, both COM identities/handles, resource generation, run generation and PID. `::R23CommitDirectAfterValidation:1412-1425` refuses and invalidates a failing source, and `::R23StageDirectHold:550-638` recreates host-owned L/R hold textures when extent/format changes, copies both eyes, and keys copy reuse to frame/generation/PID/run/slot/source identities. A new generation with different-sized textures is *not* accepted merely by recycling a slot number.
7. **Host final-eye proof remains separate.** `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` uses **full 0..1 UV per DirectGPU eye**, renders to independent D3D11 XR array-slice RTVs, restores/clears bindings on right-eye failure and releases the swapchain image; it assigns matched per-eye pose/FOV and XR projection image rects from the allocated projection extent (not the game desktop RECT). `main_r23.cpp:3240-3366` only treats a newly rendered/released image as fresh, while `:3562-3615` calls `xrEndFrame` and reads R24/R32 actual-final layer/frame interception. A **requested** projection, two CPU Draw calls, or equal descriptor sizes alone do not prove actual Quest3 binocular pixels; no matching physical draw -> R9 -> R23 -> R32/24 -> headset trace was available.
