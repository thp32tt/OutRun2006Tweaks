## NEW_FINDING / new boundary proof

- NEW_FINDING=CONDITIONAL_C993_CABE_SAME_PRESENT_INTER_SCENE_RAW_C64_ADMISSION; **static admission, NOT a confirmed optical defect**.
- **NEGATIVE CONTROL (new)**: A prior frame's recorded raw c64 cannot normally cross a completed **NotifyGamePresent -> next LatchFramePose/ResetFrameState** boundary: `NotifyGamePresent` invokes `InvalidateGameWvpWrite`, and `ResetFrameState` independently clears `LastGameWvpWriteValid` and `LastGameWvpPoseEpoch`. Thus unchanged-shader and <=12/128-draw tests alone are **not sufficient** to demonstrate cross-Present stale WVP on the inspected normal lifecycle. A different path that bypasses these lifecycle callbacks would need separate proof.
- **POSITIVE STATIC EDGE (new)**: `EndSceneDest` resets `LensCentrePartialWvp` and `HudQueuedPartialWvp` but **does not** retire `LastGameWvpWriteValid`; another successful `BeginSceneDest` before the same Present calls `ReusePresentPoseForScene` when `PresentPoseLocked` is true. That helper invalidates `LastVerifiedWvp` and resynchronizes culling camera, but not the last **raw** game WVP or the pose epoch. Under unchanged VS identity+serial, no overlapping game c64 write, a valid last source and a bounded outer draw serial, the next direct ProjectedScreenEffect2D C993/CABE may still accept that earlier scene's raw c64 from `R44GetOwnedRawOverlayWvp` (<=12 draws) or `R30GetExtendedRawWvpForExactSceneEffect` (<=128 draws).
- **IMPORTANT CONTRADICTION TEST**: D3D9 shader constants persist through EndScene/BeginScene. If the second scene intentionally reuses the identical shader/c64 and same projection, this is **correct original-device-state preservation**, not a stale read. A lens positioning failure further requires an observed changed intended object/camera matrix, or some game/native state update not represented by this captured raw record. Mere scene number, accepted WVP, two eye draws or zero disparity do not establish duplication/head-lock.
- **POSE LIMITATION**: The generic projected getters do not compare `GetLastGameWvpPoseEpoch()` with `GetCurrentLatchedPoseEpoch()`; however the inspected normal new-pose path already invalidates the record. The **strict** `R30GetExactLensCentreRawWvp` DOES compare these pose epochs. This is a difference in proof strength, not evidence that a normally completed prior-Present WVP leaks into the next frame.
- **COMPARISON**: Protected R26+HUD baseline `outrun_renderer.cpp:1280-1291,1526-1544,2262-2271` has the same scene/Present retirement pattern.
