## EVIDENCE — GitHub pinned read-only facts

1. **One mutable lookup window, not a per-producer queue.** `src/vr/game/ui_texture_lookup_window.hpp:1-65`: `TextureLookupWindow::Observe` shifts the *previous* sprite binding to mask then overwrites the current sprite binding; a null result clears both. `Consume` returns a copy and clears the entire pending state. It has no producer ID, generation/queue epoch, thread ID, queue of multiple submissions, or lock. `Submission::SpriteMatches/MaskMatches` check pointer identity only. The template's `TextureLookupSubmissionGuards` constexpr test covers an immediate two-lookup pair, one-shot consume, failed lookup and a plain second lookup, **not interleaved producers**.
2. **Live hook wiring and global lifetime.** `src/hooks_textures.cpp:943-969`: `pendingTextureLookups` is `inline static TextureLookupWindow<void>`, not `thread_local`; `get_texture_dest` records pointer/ID only when `UITextureReplacement` remains enabled. `src/hooks_textures.cpp:1727-1734,1776-1813` installs `get_texture` only for UI replacement; the ordinary sprite and ex2 hooks may also be present for HUD observation. This finding is conditional on those paths being active, not a generic R26 rendering claim.
3. **Exactly one binding consumed at the native submission.** `src/hooks_textures.cpp:1117-1160`: `put_sprite_ex2_dest` calls `pendingTextureLookups.Consume()` *before* the original native call; parent and child mask scaling require separate pointer matches and scale keys. UVs are returned to their original data after the native call; `src/vr/game/sprite_uv_transaction.hpp:11-103` uses an RAII restore guard and finite/positive validation. This is a correct safety veto against broad stale-pointer scaling but is **not** a producer transaction ID. A different producer's later two lookups can replace a prior incomplete binding even on one thread if re-entrant/overlapping call order is possible.
4. **Explicit invalidations are partial protection.** `src/hooks_textures.cpp:1163-1190` consumes an outstanding lookup on ordinary `put_sprite_ex`; `src/hooks_textures.cpp:1193-1206` clears pending on a changed xstset cursor; a failed `get_texture` clears as above. These gates avoid stale normal paths but do not store more than one outstanding owner before either submission. There is no evidence a crossed order actually happens in the stock menu.
5. **Regression coverage is sequential.** `vrhost/tests/ui_sprite_uv_transaction_smoke.cpp:1-84` tests 500 repeated transactions, finite checks, RAII restore and nested *UV transaction* reentry; it does not route simultaneous native texture-lookup owners through `TextureLookupWindow`. `ui_texture_lookup_window.hpp` embeds only the simple sequential constexpr fixture. These are source test bodies read but **not executed** on this review.
6. **Pixel-format path is independent.** `src/hooks_textures.cpp:460-481` expands 24-bit opaque `R8G8B8` to `X8R8G8B8`, preserves opaque X8 versus alpha A8, and declines unsupported requested-format fast-load so original D3DX can convert. `src/hooks_textures.cpp:1340-1348` stores old/new DDS scaling by xstset slot+texture index. ## NEW_FINDING — fact, hypothesis, falsification

- NEW_FINDING=UI_TEXTURE_LOOKUP_SINGLE_SLOT_CROSS_PRODUCER_INTERLEAVE_GAP.
- FINDING_CLASS=SOURCE_CONFIRMED_CAPACITY_AND_OWNER_BOUNDARY; RUNTIME_OCCURRENCE=UNPROVEN; PIXEL_DEFECT=NOT_ESTABLISHED; PERFORMANCE_GAIN=NOT_ESTABLISHED.
- SOURCE_CONFIRMED: the installed optional UI replacement hook stores **at most one** pending two-lookup snapshot globally. It does not bind that snapshot to the matching producer call stack, selected xstset serial or execution thread. Multiple producer lookup pairs before their corresponding put-sprite submission can replace the earlier pending binding; a later mismatched pointer generally **fails closed** by declining UV scaling. The source does not prove the actual native game generates that interleaving.
- CONDITIONAL_SIMULATION_ONLY: A does mask A and parent A lookups; B performs mask B and parent B before A submits; A's first `put_sprite_ex2` consumes B's pending window. If its parent/mask texture pointers differ, A's replacement-UV scaling is skipped; B's later native submission has an empty window. Missing parent/mask scaling *could* produce distorted selector art when replacement DDS dimensions differ. This is an abstract state-machine example, **not** a recorded car-selection trace, verified visual defect, thread race, or timing measurement. Separately, unsynchronized cross-thread access would be unsafe *if* the original game invokes these hooks concurrently; thread overlap itself remains unverified.
- FALSIFICATION: original exact-SHA game instrumentation proves `get_texture(mask)` → `get_texture(parent)` → corresponding `put_sprite_ex2` is serialized with no extra lookup, xstset switch, other producer or cross-thread callback across menu/selector/load/reset; or producer-bound lookup keys are already guaranteed elsewhere by uninspected original native code. For a **visual** hypothesis, a captured failing sprite must show the matching replacement texture ID, dimensions, UV source, mask pointer, observed physical D3DX/UP draw and submitted Quest3 L/R pixels. Merely finding global storage is not proof of an HMD-visible fault.
