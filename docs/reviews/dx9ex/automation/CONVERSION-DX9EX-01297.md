## REVIEW_SCOPE

Independent **end-of-frame SBS compositor state restoration order** on the protected R26+HUD chain. Unlike 01296, which inspected an **R62 per-DIP L/R RT switch** before Present, this pass examines `ComposeSbs()` on the **D3D9 frame compositor** path: after an eligible two-eye draw and per-eye resource resolve, does the `D3DSBT_ALL` scissor capture survive the **subsequent** `SetRenderTarget(savedRt)` that occurs *after* `stateBlock->Apply()`? This is a separate execution site/temporal boundary, not a restatement or runtime confirmation of the R62 issue. A scissor mismatch does not by itself prove +TIME, menu, lens or HMD artifacts.

Neither checked-in REA nor queue tag proves a particular real +TIME/result glyph used the SBS fallback or carried restricted scissor.
2. **Physical stereo gates/restore before composition (FACT).** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5379-5460` prioritizes F11 external ImGui, R62 fixed-function Sprite DIP, R30 XYZRHW indexed and then R29/native; `::R62TryFixedFunctionSpriteIndexed:5126-5347` calls both eyes with per-eye projection via `::R30ExecuteXyzrhwStereo:3829-3944`, which binds right-eye RT/depth and restores original RT/depth/viewport through `src/vr/d3d9/stereo_renderer_r7.inc::RestoreRightPassState:1462`. This is upstream of, not synonymous with, the present finding. Unknown final physical GPU owners must be identified by original producer + R64 batch/queue epoch + concrete DIP/UP and HRESULT; semantic class alone is insufficient.
3. **R9 SBS branch (FACT).** `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:~691-810` requires stereo requested/seeded, world and duplicate draw proof, no right/restore poison, matched pose and resources; `ResolveDirectTransport` may succeed without SBS composition if host transport is ready. If direct transport is unavailable and direct-only is false, or if DirectGPU transport exists but host is not ready and fallback is allowed, R9 calls `ComposeSbs(device)`. Failure poisons frame/uses mono where available. The game Present is normalized before a completed frame is published; no scissor-equivalence test is involved.
4. **Precise newly inspected SBS restore ordering (FACT).** `src/vr/d3d9/stereo_renderer_r7.inc::ComposeSbs:1498-1517` makes L/R resolve copies; at **1502-1507** creates `D3DSBT_ALL` and snapshots saved RT, depth, viewport; at **1509** binds `BackBuffer`, disables `D3DRS_SCISSORTESTENABLE`, clears and draws two halves via `DrawTextureHalf:1497`; at **1510** calls `stateBlock->Apply()`; only **after that** at **1511** calls `SetRenderTargetHook(..., savedRt)`, at 1512 restores depth, at 1513 restores viewport; 1514-1516 releases and returns `success && restoreOk`. There is **no GetScissorRect/SetScissorRect after the final SetRenderTarget** and no postcondition comparing the original rect. The successful `restoreOk` covers API HRESULTs, not scissor equality.
5. **Independent vendor contract (FACT).** Microsoft `Scissor Test (Direct3D 9)` explicitly says `IDirect3DDevice9::SetRenderTarget` resets scissor rectangle to the *full render target* (https://learn.microsoft.com/en-us/windows/win32/direct3d9/scissor-test). Microsoft `Saving All Device States with a StateBlock` explicitly lists the scissor rectangle and viewport in `D3DSBT_ALL` (https://learn.microsoft.com/en-us/windows/win32/direct3d9/saving-all-device-states-with-a-stateblock). Thus a state block `Apply` restores captured scissor at point 1510, but a successful RT bind **after Apply** may discard that restored rectangle by D3D9 contract; `SetViewport` at 1513 is not an explicit scissor restore. This differs in location and timing from 01296's R62 intra-draw RT switch.
6. **Bounded conditional simulation (INFERENCE, NOT observed).** Suppose SBS fallback actually executes in a game frame, `D3DRS_SCISSORTESTENABLE=TRUE` with original strict rect `{100,100,500,300}` on a 1920x1080 saved game RT, all HRESULTs pass and no later game/driver/stateblock action reapplies that rect. `CreateStateBlock(D3DSBT_ALL)` captures the restricted rectangle, composition disables scissor, `Apply()` restores it, and the final `SetRenderTarget(savedRt)` resets it to full RT. A later clipped original draw **in the next frame** (if it inherits enable=TRUE and does not reset rect) can render outside the originally intended crop. This predicts a state-persistence/next-frame artifact, *not* confirmed per-eye double text: `ComposeSbs` runs after the current L/R eye rendering and right before game Present. Actual source resolution, scissor live value, same-target driver behavior, affected game draws and visible pixels are **unknown**.
7. **Present to actual OpenXR (FACT / proof limit).** After `ComposeSbs`, `PresentDestR9:~773-823` invokes the original Present and publishes eligible frame metadata after success; host `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1513` selects DirectGPU per-eye SRVs or half-width SBS UV rectangles and draws two D3D11 projection swapchain eyes; `vrhost/src/main_r23.cpp:3569-3589` calls the real `xrEndFrame` and samples submitted-kind counters. Neither completed Present nor xrEndFrame success proves pixel correctness or scissor state of the next game draw. No synchronized trace or Quest3 capture was obtained.
