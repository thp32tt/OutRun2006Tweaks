Thirty-six indirect CALLs remain unresolved. None proves a particular format or texture allocation was used by +TIME, menu, result, or particles.
2. A legacy MANAGED `CreateTexture` reaches the R13 compatibility translation then R14 `CreateTextureCompatDestR14`. A successful original GPU texture may be DYNAMIC → tracked DirectOnly, or non-dynamic → attempted shadow. R14 checks `GetLevelCount` is 1..32 and computes a *logical* byte estimate by each level's `GetLevelDesc` width/height/format, with DXT1 ceil(Width/4)*ceil(Height/4)*8, DXT2-5 corresponding 16-byte blocks, selected 1-/2-/8-/16-byte texel cases, and **default four bytes per pixel for every other format**.
3. The estimator never reads `D3DLOCKED_RECT.Pitch`, and its 384-MiB check occurs before the real `D3DPOOL_SYSTEMMEM` `CreateTexture`; therefore an estimated reservation is not equivalent to a driver-backed allocation size or actual staging memory consumption. The successful SYSTEMMEM peer uses the same width, height, mip count and format as GPU level 0. Entry registration repeats the same estimator for budget accounting. Unsupported/zero level sizes fail the logical estimate. More than 32 levels is rejected before registration; any apparent 32-level truncation of the estimator is not a reachable successful-shadow counterexample without bypassing that guard.
4. A **concrete conditional format-accounting discrepancy** exists in source: `D3DFMT_R16F` and `D3DFMT_L16` are not in the explicit 2-byte cases, so they take the four-bytes-per-texel default. Where driver and adapter actually permit such a SYSTEMMEM texture, the logical estimate is twice the unpadded 16-bit texel payload. Example, one 4096×4096 mip is logically 64 MiB by R14 versus 32 MiB packed pixel payload; actual locked pitch/padding and native acceptance remain unknown. This can trigger the *logical* 384-MiB gate earlier than a packed-payload model, but does not establish real memory pressure or a gameplay fault. Conversely some row pitches/driver storage can exceed payload even for accurately sized formats.
5. If estimate/preflight or SYSTEMMEM allocation fails, `CreateTextureCompatDestR14` can preserve the original successfully translated GPU texture through `R14TrackDirectOnly` **only if** resource hooks are ready and registry succeeds. It then delegates CPU locks to the R13/native path, which can itself fail. If shadow allocation succeeds but later R14Track/reservation fails, this is a distinct fail-closed hard failure (documented in 01261), not proof the format estimator is wrong.
6. On tracked Shadow `LockRect`, level-specific CPU Lock owns a validity/dirty mask; a writable final `UnlockRect` first tries same-mip `GetSurfaceLevel`+internal `UpdateSurface`. R15's partial-RECT override rejects destructive whole-mip fallback on partial upload failure. Whole-level R14 `R14CopyWholeLevelByLock` uses physical *source and destination Pitch* and `min(abs(srcPitch),abs(dstPitch))` per scanline, using `ceil(height/4)` rows for DXT and plain height rows otherwise. This differs from the logical estimator; success/visible pixels require actual lock/upload HRESULT and same-mip bound sampling. Row padding and differing pitch merit diagnostics, but there is **no observed overwrite or incorrect texture**.
7. Only a matching surviving texture identity/mip bound at the actual GPU primitive may connect format accounting to a visual symptom. `PhysicalDrawCommand` records immutable producer/scope/queue node/epoch at DP/DIP/UP; D3DX `FlushDest/EndDest` can reestablish owner only for exact homogeneous batches, otherwise fail closed. R30 indexed dispatch tests F11 ImGui → R62 fixed-function candidate → XYZRHW → R29/native; `R62 E_NOTIMPL` is not final draw failure. Actual eye callbacks/primitive HRESULT, StateBlock/RT0..N/depth/viewport/texture restore, R9 stereo-vs-mono Present publication and x64 host's final `xrEndFrame` layerCount/submitted frame ID/source and cadence remain unverified. CPU allocation estimates cannot alone prove a missing menu sprite, wrong result-HUD, or headset FPS.
