## REVIEW_SCOPE — XST pack/texture index → DDS chosen bytes → SpriteNode/semantic → deferred D3DX/native GPU → R30/R62 eyes → state restore → Present/OpenXR

1. **Producer identity.** The original-game static resource/REA record at docs/automation/OUTRUN_VR_REA_RESOURCE_EVIDENCE_20261018.md reports original XST and selector/sumo/GUI DDS-to-XXH32 mapping, not a fresh execution or original game asset read in this task. src/hooks_textures.cpp::LoadXstsetSprite_dest (1193-1205) accepts the original XST filename from ECX and its game slot from EAX. UiTextureCursor.Select compares *filename contents + slot*, so a repeated identical pack does not automatically reset. SceneTextureCursor is separate (945-947, 1643-1653); an XMT object index is not a UI XST slot.
2. **Source-confirmed index reset condition.** src/vr/game/texture_pack_cursor.hpp::Cursor::Select (57-70) restarts on changed name/slot; NextIndexForGameTexture (82-92) *also* sets next_=0 whenever selected_, nonnegative gameTextureIndex, lastGameTextureIndex_ > gameTextureIndex and gameTextureIndex <= 1, even if Select did not observe a pack change. src/hooks_textures.cpp::HandleTexture (1255-1264) feeds the original game's texture-number memory at EXE RVA 0x55B25C into this heuristic for UI only, while scene XMT continues with NextIndex. There is no separate load-epoch proof within this helper for distinguishing a genuine new pass from a same-pass backward seek. The source fact is the heuristic, not proof that the original engine makes such a seek.
3. **Minimal symbolic counterexample, not game observation.** For identical XST name and slot, hypothetical consecutive original texture indices [0, 2, 1, 2] yield UI replacement ordinals [0, 1, 0, 1] instead of monotonic [0, 1, 2, 3]. The third index=1 causes the reset despite no independently observed pack restart. Conversely, the sequence [0, 1, 2] does not reset, and a true new pass returning from 2 to 0 is exactly the scenario this heuristic seeks to handle. Neither symbolic sequence nor wrong sprite was captured in a shipped game/HMD trace.
4. **Consequence depends on optional replacement and matching files.** src/hooks_textures.cpp::HandleTexture (1257-1301) builds an indexed DDS filename from ordinal, original XXH32, and original W/H; it first probes indexed paths before nonindexed hash/dimension fallback, including pad-family selection. A synthetic extra low-number backseek can select a different indexed replacement or miss the intended indexed replacement **only if the corresponding filenames/files exist**. This does NOT prove texture mapping changes for an ordinary pack, nor imply scene textures or native nonreplacement assets are corrupt. DDS header/format/mip checks (1302-1343) validate decoding boundaries, not the intended logical ordinal.
5. **Load/UV transaction.** src/hooks_textures.cpp (1345-1499) stores optional UI scaling and restores original DDS header/ratio on unsuccessful replacement/decode, with success/fallback paths to native D3DX. src/hooks_textures.cpp::get_texture_dest and put_sprite_ex2_dest/put_sprite_ex_dest (954-973, 1117-1190) use a bounded lookup window and scoped UV edits, then restore game SPRARGS after original native sprite production. These guards preserve ownership when their predicates hold, but do not themselves verify that an indexed replacement's ordinal corresponds to the expected original pack entry. Successful D3DX texture creation is not visual correctness evidence.
6. **Original queue and physical submission.** Checked-in REA docs/automation/OUTRUN_REA_RENDERING_ARCHITECTURE_20261018.md (5-50, 83-101) maps original 0x00417B20 game loop → 0x00449050 scheduling → priority queue consumer 0x0042D710.
