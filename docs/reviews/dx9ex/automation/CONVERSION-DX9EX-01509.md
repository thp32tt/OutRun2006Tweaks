## REVIEW_SCOPE — original source -> exact semantic -> queue/D3DX/native GPU -> R30/R62 L/R -> restore -> Present/OpenXR

1. Original game 640x480 UI/sprite source and its priority scheduler 0x449050 -> 0x42D710 have different native physical arms (archived REA: D3DX 0x42A0A0, direct UP 0x42C0F0, animation 0x42A3A0, masked 0x42A800). The source attribution/queue epoch and native Flush remain prerequisites; no claim that every HUD primitive takes fixed-function R62.
2. The current CMake option-free target sets `OUTRUN_VR_R26_HUD_COMPARE` default ON and selects `stereo_renderer_r30_r26_safe.cpp`; `stereo_renderer_r33.cpp` is HEADER_FILE_ONLY for that configuration. An earlier candidate audit of R33's optional GPU-water profiler is **not active R26** and is not this finding. Explicit comparison build flags/cached options may select a different TU; no binary manifest was supplied.
3. For a physically accepted gameplay `ScreenHud` owner, R26 `R30ConfigureXyzrhwWorldEffect` / `R30BuildHudPlaneCoefficients` rebuild a finite world-stable HUD plane from the game/base projection and latched eye poses. `R30HudContainScale` obtains `VRHudScale` (clamped) and, **when `VRHud1080pReference` is ON**, multiplies both X and Y by `OutRunVRHud1080p::ContainedScale(BackBufferDesc.Width, BackBufferDesc.Height)`. This is uniform X/Y per draw; no anisotropic squeeze is asserted.
4. `ContainedScale` uses only the **actual current GAME backbuffer aspect**, not a fixed 1920x1080 physical resolution, desktop/window client size, original sprite logical 640x480 bounds or recommended XR swapchain extent: `clamp((16/9)/(gameWidth/gameHeight), 0.50, 1.0)`. Its comments explicitly state no 1080p render-target allocation. This is a policy choice, not a malformed math operation.
5. Source-equivalent pure-JavaScript arithmetic (not C++ build/game test), with requested `VRHudScale=0.55` and reference option ON: backbuffer `3440x1440` -> fit `0.7441860465`, effective finite-HUD X=Y scale `0.4093023256`; `2496x2688` -> fit `1`, scale `0.55`; `1920x1080` -> fit `1`, scale `0.55`. With the reference option OFF, all three retain `0.55`. The direct result is a **scale parameter discontinuity across aspect changes** with constant user setting, not a proved on-HMD zoom: viewport/projection and source pixels may also change.
6. R26 finite-HUD source obtains actual physical command scope/producer via render_semantics, including queued node/epoch and D3DX homogeneous Flush/End where relevant. The XYZRHW and FVF=0x142 indexed D3DX variants have independent admission guards (target/VS/FVF/pose); R62 reconstructs per-eye projection from the scale-dependent HUD coefficients before raw LEFT and RIGHT native GPU submissions. Failed eye setter/draw or restoration follows the existing R30 frame poison, not an automatic second replay.
7. The shared R7 `BackBufferDesc` is populated from the real game `GetBackBuffer(...)->GetDesc`, and R7 Present publishes new SBS/DirectGPU only after valid world+duplicated stereo, pose/resources and non-poisoned eye state. No XR `xrEndFrame`, actual source sprite extent, or Quest3 pixel placement was sampled for this review.
8. Archived 2026-10-26 user session recorded desktop startup 3440x1440 later superseded by XR source 2496x2688, but the installed DLL/host exact SHA is unknown and the log does **not** record this reference-containment setting/effective scale on both sides. Therefore it proves source-extent changes can occur, not that this pinned code caused an observed HUD size jump.
