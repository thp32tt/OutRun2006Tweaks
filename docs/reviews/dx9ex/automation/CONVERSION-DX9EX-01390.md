- FACT: the central C993 original Draw may be skipped by its exact opt-out while CABE rings and R30's per-eye SkyGlow remain separately eligible. The first actual ScreenHud/ScreenOverlay2D primitive consumes the clean-scene capture opportunity even if current eye pair/glow gate cannot copy a usable snapshot, so Present can intentionally omit SkyGlow despite later eligible rendering; that is a documented **fail-closed behavior**, not proof of a bug. A clean pre-HUD snapshot that contains some other bright source may still be blurred independently of whether C993 ran.
- HYPOTHESIS_ONLY: apparent residual or duplicated 'centre' with C993 opt-out might be CABE/other original optical emitter, bloom from a prior eligible scene sample, unmatched old DLL/setting, or OpenXR safe-frame reuse. A missing bloom after UI could instead reflect the early capture eligibility latch. The original per-pixel producer and chronological ordering have **not** been established; none of these is claimed as the real symptom mechanism.
- FALSIFY: on identical installed exact-SHA R26+HUD control and **separately selected** R84_TEST, record `VREnabled`, live centre flag, hook installed, C993 hidden/normal counters, CABE object/alpha counters and physical API fingerprints. Capture earliest ScreenHud/ScreenOverlay2D, `R30SkyGlowScreenDrawEpoch`/`SceneCaptureEpoch`, stereo eligibility at that moment, both clean source images before/post Bloom, resource/restore results, final eye textures, frameId/pose and host freshness. If flag=false and the exact selected hook truly fires yet there is no C993 native Draw, reject C993-as-current-emitter and trace outer/sky/host. If the source pair was valid at screen boundary but the alleged missing bloom still occurs, reject the early-latch explanation.
