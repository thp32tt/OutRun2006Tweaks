## EVIDENCE — static code trace and controls

1. **Historical original-EXE producer map, not fresh GPU capture.** `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:19-32` records `0x449050 -> 0x42D710`; the type-0 D3DX exit `0x42A0A0` may defer physical submission to Flush/End, distinct from type-0 direct UP `0x42C0F0`, type-1 quad `0x42A3A0` and mask `0x42A800`. Thirty-six indirect CALLs remain unresolved. The documented canonical x86 queue-node/epilogue bridge `src/hooks_uiscaling.cpp::VRHudQueueSemanticBridge:4154-4184` invokes `BeforeQueueNode` before `SelectSpriteQueueNode` and `BeforeQueueEnd` before `EndSpriteQueueRender`. The original B9200 post-CALL/+5 midhook is forbidden; the reviewed code does not introduce it.
2. **The pending command is a per-thread semantic ledger, not physical evidence.** `src/hooks_uiscaling.cpp::VRProjectedD3DXSpriteIsolationR64:3365-3376` declares `inline static thread_local HudBatch`; `::DrawDest:3882-3941` samples `CapturePhysicalDrawCommand` before original Draw and compares scope, token, queued node and epoch on return. `src/vr/game/hud_command_batch.hpp::Ledger:16-59,77-141,144-216` uses `sprite`, `generation` and `mutationSerial` to protect new native Begin/Draw/Flush ownership. `SelectSpriteQueueNode:1789-1837` in `render_semantics.hpp` supplies queue selection epochs but cannot certify a D3DX physical GPU call.
3. **Existing direct-result safeguards are real.** `src/hooks_uiscaling.cpp::DX9ExD3DXSpriteLifetime::CanFlush/OwnsLifecycle:3194-3214` requires the same candidate/tracked/live sprite for a vtable Flush, but allows an OnLost/OnReset callback on the tracked *old* sprite even if `0x55B218` became null/replaced. `::FlushDest/EndDest:3432-3508` rebinds only proven homogeneous direct +TIME/GOAL ownership and invokes native Flush/End, while `::FlushTracked:3543-3562` refuses a replaced sprite before dereferencing vtable. Queue boundaries `::BeforeQueueEnd:3810-3832` require exact matching node+epoch; unknown/mixed work remains native.
4. **NEW static lifecycle ordering distinction.** At `src/hooks_uiscaling.cpp::LostDeviceDest/ResetDeviceDest:3525-3540`, `ownsBatch = OwnsLifecycle(self, HudBatch.sprite, liveSprite)` is sampled **before** the original `LostDevice_hk` / `ResetDevice_hk` invocation. After that original returns, `InvalidateForDeviceLifecycle(ownsBatch)` calls `HudBatch.invalidate()` whenever the *old* sampled boolean was true. No second check of sprite, `generation`, `mutationSerial`, or post-callback `HudBatch.snapshot()` occurs there. Compare `BeginDest:3407-3429` (checks the before-Begin generation) and `Ledger::completeNativeFlush/End/Draw:77-141` (checks same generation). This confirms an **unconditional post-callback invalidation rule**, not an observed reentrant device-loss event.
5. **Conditional nested-callback counterexample (hypothesis).** (A) Sprite S1 holds active generation G with one homogeneous GOAL/Stage batch; (B) original game enters `OnResetDevice(S1)`, making the hook's pre-native `ownsBatch=true`; (C) while the *native* callback runs, a nested `Begin(S1)` or valid new `Begin(S2)` updates this same thread-local ledger to generation G+1 and later Draw may register new commands; (D) the outer lifecycle callback returns and its stale pre-native boolean causes unconditional `invalidate()`, retiring G+1 even if it is a valid new active session. Outcome would be loss of **mod-side exact HUD ownership**, not proof that the driver discarded its draw or that a headset frame doubled/disappeared. If native lifecycle callbacks never reenter game Begin/Draw on the same thread, or no new valid batch can exist until after callback return, this case cannot happen. Another-thread callbacks cannot directly mutate this thread-local ledger; that is a separate scheduling/provenance question, not a proven failure.
6. **One-time hook coverage is a separate conditional replacement seam.** `src/hooks_uiscaling.cpp::InstallThread:4055-4109` reads the initial game pointer `0x55B218`, hooks vtable[8..13] (Begin, Draw, Flush, End, Lost, Reset) as one enabled set, then **returns after successful installation**. No post-Reset rearm/rebind loop appears in that function. The old and new D3DXSprite instances may share the same implementation addresses (in which case the code hook still covers both), so a replaced object alone is **not** proof of a blind spot. It would require a new live object's vtable[8..13] function addresses to differ and real calls bypassing the old inline targets. Failed/partial install clears all hooks and does not establish coverage. No new vtable snapshot or device log was acquired.
7. **R13 Reset and semantics do not settle callback order.** In the protected comparison build, `src/vr/d3d9/stereo_renderer_r13.cpp::ResetDestR13:425-463` retires semantic tags through `EndSpriteQueueFrame(true)`, may delegate to R9, or executes `R13ResetCommonPre` and `ResetCompatDevice`, followed by stereo-resource recovery only if successful. `R13ResetCommonPre:380-423` resets stereo/depth/host ACK/query epoch; it does not itself call R64's `HudBatch.invalidate`. These source paths do not show whether the original game calls the sprite's OnLost/OnReset before or after successful ResetEx, or whether the same native Sprite instance survives. Thus 01282's in-flight queue TLS hypothesis and this lifecycle callback-order hypothesis are independent.
8. **The physical GPU route remains conditional.** `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::R30SafeStereoBase:75-92` requires actual game device/main backbuffer, seeded stereo, ready pose/depth and excludes unsafe query/MRT/recovery. `DrawPrimitiveDestR30:5349-5375` attempts XYZRHW then guarded R29/native draw; `DrawIndexedPrimitiveDestR30:5377-5452` also tries separate fixed-function R62 indexed-DIP ownership. `R62TryFixedFunctionSpriteIndexed:5126-5157` requires TRIANGLELIST, exact HUD/projected semantic and safe backbuffer; `E_NOTIMPL` is a rejection of this route only, not the final physical draw. `src/vr/d3d9/stereo_renderer_r13.cpp::R13GuardedDraw:592-650` can force single execution/mono shadow for unsafe target/query/MRT instead of duplicating. No actual `DrawPrimitive/DrawIndexedPrimitive/UP` fingerprint, native HRESULT or eye RT/depth/viewport/projection restore was observed; no assertion that the D3DX batch made two eye draws follows.
9. **Present and XR are separate gates.** `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:759-823` restores mono on incomplete stereo, calls native Present, publishes active or fallback state, and retires its frame epoch; successful Present does not retroactively prove that the prior D3DX owner survived callback return. `vrhost/src/main_r23.cpp:3562-3610` performs actual `xrEndFrame` and checks submitted source/frame/layer. This review has no joined frame, GPU fingerprint, Quest 3/VDXR capture or frame-time series. GitHub Issue #6 is an existing review inbox, not independent evidence of the hypothesized device callback reentry.

## NEW_FINDING / falsifiers

- **NEW_FINDING=LIFECYCLE_POST_CALLBACK_INVALIDATION_NOT_GUARDED_BY_NEW_BEGIN_GENERATION**.
- **CONFIDENCE=CONFIRMED_SOURCE_STATIC_CONTROL_BOUNDARY; RUNTIME_MANIFESTATION=HYPOTHESIS_ONLY; HMD_PASS=NO.** The verified property is the stale *pre-native* owner boolean controlling an after-native unconditional ledger invalidation, contrasted with generation-aware Begin/Draw/Flush/End completion. A fresh generation would be revoked *if and only if* the native lifecycle callback or replacement path reenters a successful same-thread Begin/Draw before the outer callback returns. A hypothetical later D3DX Flush might therefore lack exact +TIME/GOAL semantics even if the native implementation still submits; actual visible doubling, missing glyphs, crash, or p95/p99 loss are **not established**.
- **REFUTATION:** bounded trace proves no same-thread Begin/Draw reentry in any successful OnLost/OnReset path; all new Begin happen only after callback invalidation; native OnLost/Reset rejects or retires pending GPU commands before new Begin; or observed physical draws after replacement use correctly proven semantics despite the rule. For the vtable-replacement secondary question, comparing live method addresses before/after reset and confirming they remain identical refutes that hook-coverage mechanism; function-address difference *without* executed bypass still does not prove a user-facing bug.
- **MISSING_EVIDENCE:** exact EXE, binary and ZIP SHA plus default-build flags; ResetEx/Reset HRESULT and the real original game D3DX lifecycle call order; thread ID, old/new `0x55B218` value and vtable[8..13] addresses; before/after `HudBatch.sprite/generation/mutationSerial/active/drawCount/producer/queueNode/queueEpoch`; reentrant Begin/Draw/Flush/End HRESULT and depth; R13 overlay readiness and current physical target, draw API plus VS/PS/FVF/texture/depth/stencil/pose; actual L/R native draw and restore HRESULT, normalized game Present and joined host `xrEndFrame` frame ID/layer. Use bounded opt-in, non-mutating evidence only; no new risky midhooks.
