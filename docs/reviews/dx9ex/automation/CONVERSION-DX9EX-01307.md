## REVIEW_SCOPE

An independent follow-up to 01306's **application LOCAL recenter versus R42 cached pose epoch**: here the risk is **the backing projection swapchain image's latest-release epoch after a failed two-eye refresh**, even when the LOCAL reference space is unchanged and a successful prior projection cache exists. Inspect both session/extent construction and the narrower post-Acquire/Wait/Release path. No automatic code changes.

End-to-end static simulation: original +TIME/result producer -> SpriteNode semantic and queue cutoff/ProducerToken -> type0 D3DX Sprite Draw/Flush/End or type0 direct UP/type1 animation quad/mask physical draw -> R30/R62/native R29 stereo interception with L/R, viewport and GPU-state restore -> R9 game Present and Frame.v2 -> host source/pose validation, classic SBS or DirectGPU commit -> per-eye D3D11 projection RenderTo -> xrAcquireSwapchainImage/xrWaitSwapchainImage/xrReleaseSwapchainImage -> R42 projection-fresh or projection-cached selection -> xrEndFrame. The existence of any +TIME visual artifact in this route is NOT established.

## EVIDENCE — static code and normative API

1. **Original producer/queue evidence**: `docs/research/REA_ORIGINAL_SPRITE_GPU_FOUR_PATHS_20261018.md:3-39` pins original EXE SHA256 `68ceb386829066f8455b9d027320af962584321f3e2e8a79c72841495a6134c3`, six +TIME CALL RVAs and 0x42D710's four physical branches: D3DX 0x42A0A0, direct UP 0x42C0F0, animation quad 0x42A3A0, masked animation 0x42A800; 36 indirect calls remain unresolved. `src/vr/game/render_semantics.hpp::SelectSpriteQueueNode:1789-1837` uses safe first-node 0x2D762 and maintains queue cutoff, epoch and producer. Semantic identity alone does NOT prove physical GPU submit. No dangerous B9200 +5 or 0x2D734 entry mid-hook is proposed.
2. **Actual D3D9 GPU and producer transport**: `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::DrawIndexedPrimitiveDestR30:5377-5462` tries separate F11 fixed-function, R62 and XYZRHW, then native/R29 guarded fallbacks; R62 `E_NOTIMPL` means route declined, not final failure. `src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:695-807` checks stereo completion, pose and resource, composes classic SBS or DirectGPU, can restore mono, and only publishes completed Frame.v2 after normalized Present. The later XR layer is still a distinct submission boundary.
3. **Session/view extent control (important negative control)**: `vrhost/src/main_r23.cpp:2586-2638` enumerates the runtime's recommended/max eye extents, computes and publishes startup eye allocation, and fails closed if the initialized compositor allocation differs. `vrhost/src/main.cpp::SwapchainSet:1030-1057`, `StereoCompositor::Initialize:1117-1148`, `CreateProjectionSwapchain:1924-1943`, `CreateSwapchain:1955-1997` allocate a two-slice array swapchain once with validated common extent and two RTV slices per image. This reviewed run found NO independent evidence of a subsequent swapchain recreation while gameplay continues; therefore do NOT claim an observed dynamic-resize/generation bug.
4. **Explicit XR image lifetime**: `vrhost/src/main.cpp::StereoCompositor::Acquire/Release:2001-2015` wraps `xrAcquireSwapchainImage`, blocking `xrWaitSwapchainImage` and `xrReleaseSwapchainImage`. Khronos OpenXR 1.1 specification (`https://registry.khronos.org/OpenXR/specs/1.1/html/xrspec.html`, swapchain image management/frame submission): an `xrEndFrame` composition layer consumes the **most recently released image index** for the referenced swapchain, not a separately named image index from the layer's pose/FOV cache; both array slices are within that image index.
5. **Two-eye failure release is unconditional after acquisition**: `vrhost/src/main_r23.cpp::R23RenderProjection:1440-1514` acquires one array image; invokes left and right `RenderTo` separately; cleans up deferred bindings on first-eye success/second-eye failure; sets `ok = firstEyeOk && secondEyeOk`, schedules pixel probe only if ok, yet invokes `c.Release(c.projection_)` **before** `if (!ok) return false`. Therefore a failed post-Acquire eye submission can still advance the swapchain's most-recently-released image. It does **not** publish fresh `pv` on failure.
6. **Concrete reachable local failure gate**: `vrhost/src/main.cpp::StereoCompositor::RenderTo:2183-2263` returns false on missing RTV/SRV/constant buffer or failed D3D11 `Map` of changed per-eye blit parameters before that eye's `Draw(3,0)`. Left-eye success and right-eye pre-draw Map failure is a code-permitted asymmetrical result; the right Map path requires an upload (`NeedsUpload`). No claim is made that this failure occurred on Quest3.
7. **Cached-view fallback does not track the image-release epoch**: `vrhost/src/main_r23.cpp:3280-3409` stores `cachedProjectionViews=pv` and `cachedProjectionValid=true` only on a successful new pair. If `newStereoCommitted=true` and an attempted refresh returns false, `else if (cachedProjectionValid && (grace || cachedHold))` selects `projection-cached`, assigning old `cachedProjectionViews.data()` to the current projection. Those view structs hold `projection_.handle`, pose/FOV and array slices, but no prior image index or last-release serial. Since an unsuccessful refresh may already have released a *different*, partly filled array image, the old view metadata and the image sampled by the runtime need not remain an atomic previously verified pair.
8. **Existing lifecycle controls**: `main_r23.cpp:2720-2754,2779-2793` invalidates cached projection and source history on XR STOPPING and due LOCAL reference-space change, and `::main:2874-2905,2968-2988` protects gameplay transitions and DirectGPU run-generation rollover. Those guards are valid, but none proves rollback of the just-released OpenXR image on a post-Acquire two-eye failure. `::main:3562-3590` carries the final XR end-of-frame submission and distinct requested/actual-layer telemetry. Issue #6 is a review inbox, not a same-SHA HMD/GPU trace.

- **Precise conditional scenario**: frame F0 succeeds, releases intact two-slice projection image I0, and sets `cachedProjectionValid=true` with view metadata V0. A later committed frame F1 triggers new L/R projection on acquired image I1. Left `RenderTo` submits D3D11 Draw, while right `RenderTo` returns false on its needed Map (or another pre-draw gate). `R23RenderProjection` releases I1 and returns false. Gameplay fallback chooses `projection-cached` with V0; `xrEndFrame` is permitted to sample most recently released I1. Depending on I1 contents, the displayed slices/pose provenance **may disagree** (one fresh eye, one older/uninitialized eye, or stale geometry), despite cache metadata still asserting last successful pair.
- **Bounds / contrary evidence**: a failure *before* Acquire (missing stereo source, failed UV) has no new projection release and does not satisfy this finding. A successful two-eye draw publishes a fresh matched pair and is not this finding. A first-ever failed projection has no prior valid cache for the stale fallback. If deployed runtime and build never hit an after-Acquire one-eye failure, no observable fault follows. A device/runtime-specific mechanism could suppress the failed image's submission or terminate the frame; this requires actual API capture, not inference. Old projection reuse without a new Release is the intended R42 optimization and must be preserved.
- **Falsification**: demonstrate a failure path that avoids release or aborts the projection layer before `xrEndFrame`; prove the runtime intentionally selects last *successful* two-eye completed image rather than last released under exact conditions; demonstrate exact deployed binary adds a success/generation fence not present at SOURCE_HEAD; or demonstrate no post-Acquire failure reaches cached layer in runtime traces. Capture swapchain handle, acquired image index, prior successful released index/serial, left/right RenderTo result/Map HRESULT, cache owner frameId/sourcePoseSequence/pose/FOV, latest released image, final layer and `xrEndFrame` result, and both eye pixels to determine failure.
