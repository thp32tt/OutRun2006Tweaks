3. **Hard scratch caps are not device caps.** `src/vr/d3d9/r30_indexed_up_bounds.hpp:4-30` defines `MaxIndices=524288`, `MaxVertices=262144`, with `PrimitiveElements(D3DPT_TRIANGLELIST,p)=3*p` on safe unsigned arithmetic, and `DeclaredWindow(min,num)` rejects only empty or end>262144. `::R30TryXyzrhwIndexedPrimitiveUP:3994-4118` validates pointers, INDEX16/INDEX32, type element-count and vertex window, then an index-in-window mask, eye transforms and native DrawIndexedPrimitiveUP left/right callbacks. `::R30TryXyzrhwIndexedPrimitiveVB:4236-4500` validates live IB/VB shadows and physical min/max, constructs a new contiguous vertex span, and similarly issues native indexed-UP calls. Neither inspected candidate reads `D3DCAPS9::MaxPrimitiveCount`, nor computes **number of distinct referenced indices** for cap compatibility. The scratch used-mask tracks selected vertices for transform; it is not tested against an API-specific 0xFFFF unique-vertex ceiling.
4. **Official D3D9 contract has a special cap case.** Microsoft Learn `D3DCAPS9::MaxPrimitiveCount` says when the value is exactly `0xFFFF`, draws are limited both to 65535 primitives **and to no more than 65535 unique vertices**; other MaxPrimitiveCount values apply their ordinary primitive-count ceiling. References: https://learn.microsoft.com/en-us/windows/win32/api/d3d9caps/ns-d3d9caps-d3dcaps9 ; https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-drawindexedprimitiveup ; https://learn.microsoft.com/en-us/windows/win32/api/d3d9helper/nf-d3d9helper-idirect3ddevice9-drawindexedprimitive . This is a capability-dependent API constraint, not proof that the current RTX device reports the 0xFFFF sentinel.
5. **Independent synthetic supported-type boundary:** suppose an otherwise admissible `D3DPT_TRIANGLELIST`, `primitiveCount=21846`, `indexFormat=INDEX32`, `minVertexIndex=0`, `numVertices=65538`, indices `{0,1,2,...,65537}` (65538 distinct referenced vertices), stride 24, valid readable backing memory and compatible state. Arithmetic: `21846*3=65538` indices (below 524288); declared vertex window 65538 (below 262144); vertex bytes `65538*24=1572912` (below R30 4-MiB per-transform ceiling); `primitiveCount=21846<65535`. Therefore both R30 indexed candidates' *inspected arithmetic* can pass and build left/right indexed-UP callbacks **if all other renderer/shadow/VR gates pass**. On a hypothetical device reporting `caps.MaxPrimitiveCount==0xFFFF`, 65538 unique referenced vertices would exceed the documented 65535-unique-vertex ceiling despite its accepted primitive count. The real device may also restrict MaxVertexIndex or fail other state gates; do not imply the complete tuple is hardware-valid, reaches this route in OutRun, or returned a specific HRESULT. INDEX16 cannot express 65538 distinct indices and is a negative control.

Left success switches right RT/depth/viewport and attempts right then restores; right/restore failure poisons/safe-fallback.
