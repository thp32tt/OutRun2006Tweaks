3. At `CreateTextureCompatDestR14`, translated MANAGED `D3DUSAGE_DYNAMIC` resources take `R14TrackDirectLockable` (DirectOnly, zero CPU-shadow reservation). For non-dynamic success, R14 attempts `R14CreateCpuShadow` before `R14Track`; a failed SYSTEMMEM create may preserve the working DEFAULT texture through `R14TrackDirectOnly`. Conversely, when SYSTEMMEM creation **succeeds** but `R14Track` later fails, this DirectOnly fallback branch is **not** eligible (`FAILED(shadowHr)` is false): the success-created GPU texture and temporary CPU shadow are released and the game receives `D3DERR_NOTAVAILABLE`. This is a deliberate fail-closed lifetime-coverage policy, not a confirmed bug.
4. `R14EstimateShadowBytes` sums at most 32 mips using DXT block calculations or fixed/format-dependent bytes-per-pixel; returns zero for invalid descriptions and budget+1 if total exceeds 384MiB. This estimate is *logical budget accounting*, not the observed SYSTEMMEM texture allocation size (no pitch/driver allocation trace). `R14CreateCpuShadow` checks `R14ShadowBytes.load` plus estimate, then calls `device->CreateTexture(... D3DPOOL_SYSTEMMEM ...)`; **it does not atomically reserve bytes before allocation**.
5. `R14Track` computes the estimate again, then `R14ReserveShadowBytes` uses `compare_exchange_weak` to enforce the logical 384MiB aggregate. If two resource creations pass the earlier load-based preflight, both CPU allocations may be attempted before either reservation; the later contender can be rejected despite having successfully allocated a CPU peer. On reservation failure `entry->shadowBytes=0`, `R14ShadowBudgetRejects++`; unsuccessful registration never transfers CPU ownership, so the caller releases it and the GPU texture. The strong logical reservation limit does **not** imply a peak physical allocation limit, nor has concurrent creation been observed in-game.
6. Registered entries hold a device COM reference; the registry holds shared_ptr entries until the final GPU texture Release. `R14AdoptCompatDevice` snapshots old-device entries, updates `R14RegistryDevice`, detaches unlocked shadows and defers locked ones until corresponding Unlock. Bytes are subtracted upon detach under the entry lock, before separate `cpu->Release()`; short-lived in-flight shared entries and deferred old-device locked entries therefore change timing/availability of the **logical** budget across replacement. Allocation size, allocator peak, old-device COM Release latency and impact on new GPU resources remain unknown. Registry mismatch/duplicate insertion also fails closed and is a separate negative control from the budget CAS rejection.
7. If texture creation succeeds, attribution continues only through a corresponding actual DP/DIP/UP. For indexed draws R30 gives F11 external ImGui first consideration, then R62 fixed-function candidate, then XYZRHW, then guarded R29/native original; `E_NOTIMPL` from R62 means candidate rejection only. Native D3DX End/Flush, R7/R13/R9 actual left/right callbacks and HRESULT, texture bindings, RT0..N/depth/viewport/StateBlock restores are indispensable. A resource failed at step 3 would not be assumed to reach those draws; any displayed scene after that might use a different resource or fallback.
