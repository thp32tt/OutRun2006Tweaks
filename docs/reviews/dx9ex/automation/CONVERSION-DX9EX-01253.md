## NEW_FINDING — confirmed static fallback policy; runtime consequence conditional

- NEW_FINDING=CONFIRMED_STATIC_R15_FAILED_SYNCHRONOUS_STEREO_HANDOFF_LATCHES_EX_PROMOTION_OFF_AND_FORCES_CLASSIC_FALLBACK_FOR_LATER_WRAPPER_CALLS.
- FACT: When R15's compatibility install reaches a failed synchronous stereo handoff, R15 explicitly stores FinalCompatOverlayReady=false before returning false; the wrapper releases that unexposed Ex device and tries classic CreateDevice. On subsequent calls through a still-existing wrapper while the flag remains false, CreateDevice skips Ex; new Direct3DCreate9 callers also skip wrapper creation. This fail-closed policy is directly supported by source. It is **not** proof of a bug: preventing partial Reset/stereo ownership from escaping may be necessary.
- FACT: A classic fallback can be successfully created without proving R7/R9/R13 policy readiness for that **new** game device, since process-scoped callback workers use their saved Ready/Failed identities. The exact physical callback coverage on that new device is unknown.
- HYPOTHESIS A: If a **second distinct device** is created in the same process after an earlier successful install, R7 Ready pointer mismatch (01252 precondition) can cause R15 to disable future Ex promotion and route this CreateDevice and later attempts to classic. Potential effects are a source-resolution/transport-mode change, mono fallback, lost L/R eligibility, query-health mismatch or wasted creation attempts; none has a reproducer here.
- HYPOTHESIS B: A first failed install can also disable Ex until the final overlay state is reinitialized, but the initial R7 failure and classic first-device installer races are separate cases requiring tracing.
- CONTRARY/REFUTATION: OutRun may never create a second device, using Reset/ResetEx only; a failed Ex device may always be rejected before any gameplay; a process restart may reset the gate; a deliberate classic-only session may be correct; vtable hooks may apply safely on both devices, and the host may still present valid frames. No runtime regression, frame stutter, FPS change or Quest3 optical defect is established.
- FALSIFY / BOUNDED EVIDENCE REQUEST: With opt-in exact executable/build SHA logs, capture sequence of Direct3DCreate9 and CreateDevice invocations (same wrapper identity), old/new device pointer + vtable target addresses, *real* Release and recreation events, R15 final overlay state before/after attempted handoff, R14/R15 compat reset disarm/rollback result, R7 Ready/Failed and saved pointer, synchronous return, final CreateDevice HRESULT and provider/Ex-vs-classic pointer, R9/R13 readiness, new query Issue hook target and BEGIN/END cardinality, one bounded original +TIME/GOAL producer/semantic/queue epoch and **actual** D3DX Flush/End or other DP/DIP/UP native callback, R30/R62 acceptance vs fallback, R13/R9/R7 L/R HRESULT, RT/depth/viewport/StateBlock restores, game Present output and host actual xrEndFrame frameId/layer/fresh/cached. Compare (A) initial successful Ex only + ResetEx, (B) second pointer with different methods, (C) same-pointer reuse, (D) first install failure then classic, (E) classic fallback with shared vtable targets, (F) reinitialization/restart. The practical failure hypothesis is refuted if the second-device case never occurs or the new device consistently has complete hook/eye/host ownership despite the fallback.
