It does **not** scope an individual queue entry or PMT.
2. At `src/hooks_graphics.cpp:703-749`, scene origins `SceneD44B`/`SceneD79B` make `trace=true` whenever both `VREnabled` and `VRTelemetry` are true, **even if** `CurrentLensOriginalCall.sourceSerial==0` **and** `CurrentLensDeferredPhysical.sourceSerial==0`. The code allocates a nonzero global `LensOpaqueFlushSerial` and installs it in the thread-local receipt. It can therefore truthfully report a scene **flush-call** serial with no authenticated flare **source**.
3. `src/vr/game/render_semantics.hpp:896-945` explicitly describes the receipt as an original opaque **queue transaction**, not render ownership or material identity. `patchCount` is read from `0x464F14`; `patchLedgerHash` hashes up to 128 pointer/old-value pairs from `0x4995A0` at `hooks_graphics.cpp:684-700,716-746`. Neither is a unique queued PMT fingerprint, texture hash or frame-invariant draw ID. Identical values across independent flushes are possible, and different values do not prove distinct flare lobes.
4. `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:4214-4233` captures `CurrentLensOpaqueFlush` at a physical R30 route trace and computes `trace.lens = (producer==LensFlareCentre) || (lensOpaque.serial!=0) || (inline serial!=0) || (deferred serial!=0) || (scope==ProjectedScreenEffect2D) || (scope==SceneEffect)`. It then prints `family=LENS` whenever `trace.lens` is true. **Conditional negative control:** a non-flare GPU Draw executed inside an observed scene flush with producer=None, scope=Other, no inline/deferred source receipt still receives `family=LENS` solely because `lensOpaque.serial!=0`. The same boolean is repeated in the R7-family diagnostic path, `src/vr/d3d9/stereo_renderer_r7.inc:1620-1637`. This is a source-proved **possible false-positive classification**, not a claim that the original scene queue really contained that draw in a captured game frame.
5. IMPORTANT DISTINCT GATE: `R30TryScreenSpaceFovDraw` at `src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp:6094-6107,6240-6248` defines `lensPhysicalCandidate` from `VRTelemetry && (EffectiveScope==ProjectedScreenEffect2D || EffectiveScope==SceneEffect)` **without** consulting `lensOpaque.serial`. Consequently `family=LENS` in an XYZ/RHW eye receipt (`:4261-4312`) does not imply a `VR TRACE LENS PHYSICAL RESULT FULL` at `:6852-6915`. Conversely a generic scene-effect PMT can enter the latter category without being the visually doubled second flare. Source/call-stack and actual eye-DRAW/HRESULT/ROI must be joined independently.
6. A scene flush without an eligible inline/deferred source can emit `sourceCallSerial=0, sourceObj=0, ordinal=0, flushSerial>0, opaquePmtIdentity=UNVERIFIED`. The new PRE/POST pair is **one flush-invocation bracket**, not one image-layer contribution or a count of 5–6 user-visible flare components. If a real queued flare draw occurs outside an instrumented 4052C0 scope, `opaqueFlushSerial=0` likewise does **not** disprove it.
7. This does not change rendering eligibility: the receipt lives in diagnostic TLS, and the separate R30 native route's scope, FOV, WVP, HRESULT and fallback still decide whether it physically draws. The source review finds a risk of **misreading trace labels**, not an established source regression, extra emitter, double compositing, or same-eye duplicate.
