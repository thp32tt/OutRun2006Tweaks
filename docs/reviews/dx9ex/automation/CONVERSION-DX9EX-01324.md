## REVIEW_SCOPE — new geometry/denominator safety boundary, distinct from 01323

01323 audited R62 physical result-glyph *texture/sampler/sRGB* diagnostic coverage. This run inspects a different boundary: original +TIME/GOAL/result sprite game-pixel and logical 640x480 composition -> exact producer + D3DX queued ownership -> live fixed-function R62 GPU indexed draw -> projective finite HUD L/R matrices with non-zero eye cant -> restore -> R9 Present/Frame.v2 -> host xrEndFrame. It compares the *R62 fixed-function projective vertex clip-W admission* with a separate, bounded CPU pixel-projection helper's guard, without assuming R84 is the default or claiming the two physical paths are interchangeable.

1. **Original producer and source pixels (reused REA, not new disassembly).** Historical mapping: +TIME original 0x00498670 has three animation and three number CALLs; 0x004973C0/0x004974E0 and glyph 0x004B9200 feed distinct siblings. GOAL progress 0x004979E0 and 19 separately bracketed B9200 result-text caller edges can coexist. Original D3DXSprite Begin/Draw may defer native D3D9 submission until Flush/End. One original 640x480 logical sprite/number CALL is not one DIP, a known vertex span, or proof of a particular HMD pixel.
2. **Logical/game viewport is upstream of optical eye mapping.** src/hooks_uiscaling.cpp:455-510 contains a guarded original logical-UI contain-scale path using Game::screen_scale, screen_resolution and original_resolution, but it is a mode-specific scaling branch and is *not evidence* that every GOAL result glyph traverses that exact matrix. R62 consumes an already prepared game/D3DX native indexed draw; it fetches the actual D3D9 viewport and original fixed-function projection. The separate game viewport and XR recommended swapchain pixel extents must not be silently identified with each other.
3. **Semantic/queue/batch.** src/hooks_uiscaling.cpp GOAL/ResultProgress enter/exit and direct +TIME bracketing isolate only verified producer and homogeneous live D3DX batches; queued child nodes retain queue-root/node/epoch identity. CapturePhysicalDrawCommand records semantic, token and queue epoch, not source corner pixels. R30IsExactResultHudDraw requires exact finite-result producer and, for queued work, a nonnull node plus nonzero epoch. A mixed/unknown source must remain on native D3DX/older renderer fallback; never hook B9200 post-CALL/+5.
4. **R62 actual physical admission.** src/vr/d3d9/stereo_renderer_r30_r26_safe.cpp::R62TryFixedFunctionSpriteIndexed:5171-5394 accepts only game backbuffer, safe stereo seed, corroborated HUD/projected marker, live VS=null, FVF=0x142, nonempty D3D9 viewport, latched matching pose and valid R30BuildEyeAffine. For exact ScreenHud it reconstructs a finite world-locked HUD plane using renderer base projection and head inverse. Only exact result content calls BuildStageEyePoses to retain OpenXR eye-local non-zero orientation/cant; other HUD remains on its existing identity-eye policy. This demonstrates that source *has* a cant-aware formula, not that Quest3 produced correct pixels.
5. **Projective denominator comparison — source-confirmed.** R30BuildHudPlaneCoefficients:2745-2824 produces per-eye hudClipX/Y/W from headInverse * eyeInverse * ProjectionFromFov, then R62:5276-5316 forms per-eye clipMap and tests only whole-matrix finiteness before calling native DrawIndexedPrimitive per eye. For this bounded R62 indexed function there is no per-original-vertex CPU test that reconstructed `W(x,y)=hudClipW[eye][0]*ndcX + hudClipW[eye][1]*ndcY + hudClipW[eye][2]` stays **strictly positive** over every referenced glyph quad vertex. This is *not* proof of a renderer bug: the original D3D9 vertex pipeline still performs clipping and the actual glyph vertex positions/clip-W may all be safe.
6. **Different CPU and R84-only proof surface.** The separately defined src/vr/d3d9/stage_extension_eye_plane.hpp::SourcePixelNdc/ProjectNdcEye/ProjectPixelPair:70-175 validates source viewport/pixel finiteness, explicitly rejects nonfinite or W<=1e-5 per evaluated source point, and transactionally publishes neither eye on a pair failure. The R30 XYZRHW CPU transform at stereo_renderer_r30_r26_safe.cpp:3788-3834 likewise rejects each selected vertex when clipW<=1e-6. Portable vrhost/tests/stage_extension_eye_plane_smoke.cpp:244-325 exercises synthetic viewports (640x480, 1920x1080, 3440x1440, 720x1280), canted quaternions and zero-W rejection **for that helper**, not for the R62 native DIP hardware clipper. Hence the safety contracts are measurably different; it is invalid to cite the R84 helper smoke as end-to-end R62/HMD acceptance.
7. **Actual L/R and restore.** R62 submits original DIP with left/right eye-specific projections through R30ExecuteXyzrhwStereo, which switches RT0/depth/viewport for the right eye and restores saved state; R62 also restores the original projection. Failed HRESULT/restore invokes R9 poison/safe fallback. R62 result-eye telemetry includes pose, viewport, left/right HRESULT and restore but **not** min(W), per-corner clip distribution, source original_resolution, logical viewport or host per-eye recommended size. A successful HRESULT alone cannot prove that hardware clipping yielded every expected glyph pixel.
8. **Present/OpenXR.** src/vr/d3d9/stereo_renderer.cpp::PresentDestR9:675-822 requires seeded world stereo plus duplicated draw, completed pose/metadata and successful normalized native Present before active Frame.v2; otherwise mono/fallback. vrhost/src/main_r23.cpp:3550-3615 checks actual xrEndFrame submission frame/layer identity, not each glyph quad's clipped coverage. No Quest3/VDXR capture, physical source-to-DIP fingerprint, eye images or measurable performance result was obtained.

## NEW_FINDING — physical fixed-function projective W proof is not equivalent to CPU HUD pixel projector

- **Confirmed:** R62 checks matrices for finiteness and submits two native DIPs, but unlike CPU pixel paths does not inspect every quad's resulting homogeneous denominator before native submission. The reference R84 helper rejects W<=1e-5 and the R30 XYZRHW path guards clipW for mapped vertices. Non-zero cant contributes to the projective eye transform through valid current-source code.
- **Hypothesis only:** If a specific original glyph's NDC footprint combined with an eye-canted view produces zero/negative projected W for one eye, clipping could shorten/discard a glyph while R62 logs successful API calls. Nothing here proves any actual OutRun glyph reaches that condition. The D3D9 fixed-function clipping machinery may already provide correct behavior without extra CPU checks, and HMD geometry may never approach W=0.
- **Falsification / proof plan:** On the protected R26+HUD exact binary reproduce an affected GOAL 0-99/result or +TIME glyph. Pin original 0x97xxx CALL(s), D3DX Flush/End batch/queue epoch and actual FVF=0x142 DIP. Capture original vertex-position min/max or bounded four corners, game's source pixel/physical D3D9 viewport and logical contain affine, both eye projections/cant, clipW minima/sign per eye (read-only, off hot path), RT/depth/viewport/projection restore and both HRESULTs, exact R9 frame and host submitted layer. Compare side-by-side exact Quest3/VDXR image coverage and p95/p99. If all actual W values stay safely positive and both eye glyphs are complete, **reject** the hypothesis; if GPU clips correct near-plane content, still do not rewrite projected geometry without proven symptom.
