## Cycle 1 — R74-OUTRUN-PLUS-TIME-PRODUCER-001

**USER_SYMPTOM**  
OutRun checkpoint extension-time white text remains stereo-doubled and head-following.

**RUNTIME_EVIDENCE**  
The R73 session contains no `VR R71 OUTRUN STAGE HUD` hit. The three currently bracketed R71 direct-call RVAs therefore did not own the visible +TIME in this tested session. The lower HUD trace has many generic `put_sprite_ex2` observations, but no caller-of-caller identity that binds visible +TIME to one producer.

**DISASM_EVIDENCE**  
`0x975EE`, `0x97727`, and `0x977FB` are all direct calls inside `FUN_00497560` (RVA `0x97560..0x978FA`) to `FUN_0042CDD0`. `FUN_0042CDD0` is a variadic formatted-text path: it calls `__vsnprintf`, then text/glyph helpers. `FUN_00497560` references the string `PLAYER` and is reached from functions around `0x98670/0x99020`. This proves that the three RVAs are valid text calls, but not that they are the visible checkpoint +TIME producer.

**OWNERSHIP_HYPOTHESIS**  
The current R71 ownership hypothesis is incomplete: visible +TIME is produced by another caller of the shared formatted-text/glyph path.

**FALSIFICATION_SIGNAL**  
A bounded runtime caller-of-caller trace during +TIME shows one of `0x975EE/0x97727/0x977FB` as the actual parent producer and newly queued nodes are tagged/consumed as expected.

**MINIMAL_PATCH_POINT**  
None yet. First capture the parent return-RVA above the shared glyph/printf helper during the exact +TIME interval.

**REGRESSION_BOUNDARY**  
Do not widen `0x97300..0x97F00`, do not promote all `FUN_0042CDD0` callers, and do not use a stage/frame timer as semantic ownership.

**VERDICT**: `ANALYSIS_ONLY / NOT_PROVEN`.

## Cycle 2 — R74-OUTRUN-RESULT-PROGRESS-OWNER-001

**USER_SYMPTOM**

**RUNTIME_EVIDENCE**

The sampled argument evolves as `0 -> 3.33333 -> 10 -> 23.3333 -> 50 -> ... -> 98.5915`, directly matching a progress/percentage animation.

**DISASM_EVIDENCE**  
`0x97BB7` and `0x97DA7` are inside `FUN_004979E0` and call `FUN_0042D280` (the known `put_clip_sprite` wrapper). The same result function has paired calls `0x97BE4` and `0x97DEC` to `FUN_0042D200`. `FUN_0042D200` calls the canonical SpriteNode allocator/enqueue function `FUN_0042CFE0` at `0x2D26C`. Ghidra has exactly two callers of `FUN_0042D200`: `0x97BE4` and `0x97DEC`, both in `FUN_004979E0`. Therefore the runtime UNKNOWN `0x2D26C` result-stage progress rows are statically bound to these two exact result producer edges.

**OWNERSHIP_HYPOTHESIS**  
The final progress companion nodes from `0x97BE4/0x97DEC` are missing exact SCREEN_HUD queue-node ownership. The already tagged `0x97BB7/0x97DA7` pair covers only part of the composite result widget.

**FALSIFICATION_SIGNAL**  
After exact bracketing/tagging only `0x97BE4/0x97DEC`, stage-14 `0x2D26C UNKNOWN` rows remain or the progress bar still follows the head/doubles while those exact nodes are observed as SCREEN_HUD at queue consumption.

**MINIMAL_PATCH_POINT**  
Bracket the two exact five-byte calls `0x97BE4` and `0x97DEC`, snapshot SpriteNode queue tails, and pin only nodes appended by those calls to SCREEN_HUD. Do not tag `FUN_0042D200` globally.

**REGRESSION_BOUNDARY**

**VERDICT**: `PROVEN_READY_FOR_MINIMAL_FIX`.

## Cycle 5 — R74-SELECTOR-TEXTURE-LIFETIME-001

**USER_SYMPTOM**  
Vehicle selector improves partially, but tire/body/light material regions remain white and vary by vehicle.

**RUNTIME_EVIDENCE**  
R73 log:
- 2048x2048 fmt=21 translated MANAGED texture: CPU shadow unavailable, DirectOnly.
- 2048x1024 fmt=21 companion: emergency/aux budget reject, DirectOnly.
- translated MANAGED LockRect failure: `level=1`, descriptor `64x32`, DXT1, `levels=4`.
- multiple `spr_sprani_selector_cvt_Exst/*_1024x1024.dds` replacement files are reported as 64 MiB and skipped by the 64 MiB VR file cache.

**DISASM/SOURCE EVIDENCE**  
R73 `R72IsSelectorReserveCandidate` classifies a compressed material by **level-0** descriptor `128x64 DXT1, levels=4`. A failing **level-1** descriptor of `64x32` is exactly consistent with that mip chain; the earlier interpretation that “128x64 was wrong” is therefore rejected by this re-review. The missing evidence is whether that exact pointer was admitted to the selector aux reserve or had already fallen into DirectOnly before the level-1 lock.

The replacement-cache warnings are a separate path. `hooks_textures.cpp::FileDataCache::cacheFile` logs the actual file byte size from `ifstream::tellg()`; it is not estimating a 1024x1024 texture as 64 MiB. If a file exceeds the cache ceiling, `getFileData` returns null and optional replacement is not applied. This path concerns replacement DDS files under `textures/load/spr_sprani_selector_cvt_Exst`, not proof that the 3D vehicle material texture itself failed.

**OWNERSHIP_HYPOTHESIS**  
At least two independent mechanisms exist: D3D9Ex MANAGED compatibility/lifetime pressure and optional replacement-file cache misses. The white vehicle material cannot yet be assigned to either without pointer/create/bind correlation.

**FALSIFICATION_SIGNAL**  
Correlate the exact texture pointer across translated CreateTexture -> reserve admission/DirectOnly -> LockRect(level) -> SetTexture(stage) during `STATE_SELECTOR`, including base-level descriptor. If a failing DirectOnly pointer is bound to the white tire/body draw, MANAGED compatibility is proven. If not, inspect texture-stage/material state next.

**MINIMAL_PATCH_POINT**  
Diagnostic only: add bounded selector-only pointer/caller logs at shadow admission/reject, LockRect, and SetTexture for tracked DirectOnly/shadow entries. Keep existing budgets unchanged.

**REGRESSION_BOUNDARY**  
Do not increase global cache/shadow budgets, do not force all selector textures into CPU shadow, and do not treat UI replacement-cache misses as proof of 3D car-material failure.

**VERDICT**: `ANALYSIS_ONLY / NOT_PROVEN`.
