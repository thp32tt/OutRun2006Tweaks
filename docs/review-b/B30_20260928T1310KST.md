## Lens 5 — DXVK selector/backend identity

### NEW: VR-BACKEND-VARIANT-COMPAT-001
Status: STATIC_CONFIRMED / D_IMPLEMENT_NEXT
Severity: test-identity and wrong-payload risk; no claim of current HMD regression.

Current `tools/Select-OutRunVRBackend.ps1` validates `Backend` and `VariantId` independently,
but never validates that the pair is compatible. `$src` is selected from the explicit
VariantId before any backend-family guard.

Therefore an explicit mismatched invocation can create a mixed session. Example:
`-Backend dxvk-safe -VariantId F_DX12_STRICT` selects the F_DX12 slot's game/host payload while
installing the global DXVK SAFE d3d9.dll and recording Backend=dxvk-safe with
VariantId=F_DX12_STRICT. Similar cross-family combinations are accepted for DXVK/DX12/D3D9.
The manifest records the mismatch rather than preventing it.

The new `Test-VRDXVKBackendContract.ps1` covers the normal matching SAFE/MULTIVIEW pairs and
x64 provider rejection, but contains no negative backend/variant compatibility test.

D_IMPLEMENT_NEXT:
1. Add a fail-closed backend/variant compatibility check before `Seal-PendingSessionLogs` and
   before any root payload is copied/removed.
2. At minimum constrain DXVK SAFE -> E_DXVK_SAFE, DXVK MULTIVIEW -> E_DXVK_MULTIVIEW,
   DX12 -> F_DX12_STRICT, and 2D -> CONTROL_2D; keep the explicit documented D3D9 slot family.
3. Add deterministic negative tests proving every cross-family pair throws before filesystem
   or session-state mutation.
4. Re-run DX9Ex Active Validation. This is control-plane only; HMD is not required for the guard.

Relation: new exact static evidence supporting the already-known class of backend
test-identity/routing risk; it does not attribute historical non-focus DX12/DXVK sessions to
this current-focus selector.
